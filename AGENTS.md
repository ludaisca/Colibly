# AGENTS.md

## Stack
- **Next.js 16** (App Router, Turbopack) + **Tailwind CSS v4** (CSS-based, `@theme inline`)
- **NextAuth v5** beta (Credentials + JWT only, no adapter)
- **Prisma 5** (PostgreSQL + pgvector)
- **Redis 7** + **BullMQ** (job queues for async processing)
- React 19, lucide-react, zod, bcryptjs, next-themes, openai, @google/generative-ai, ioredis, recharts, @dnd-kit/core
- WhatsApp **multimodal** (image/audio/video/document/sticker) inbound + outbound on Meta Cloud API — see "Media handling" below. Canales adicionales: Telegram (bot API) y Messenger/Instagram (Graph API page-linked) — see "Canal genérico" below. Feedback loop de Ads vía Meta Conversions API — see "Meta Ads" below.

## Development

Everything runs in containers (`docker compose` or `podman compose` — same CLI; the shared dev server uses Podman rootless, hence `:z` on bind mounts). Never install dependencies or databases on the host.

```bash
docker compose up --build   # dev server + postgres + redis, hot reload, port 15100
docker compose down -v      # full teardown including volumes
npx tsc --noEmit            # type check
npm run build               # production build check
npx prisma generate         # after schema changes
```

- **docker-compose.yml** is production (used by Coolify). **docker-compose.override.yml** adds dev overrides (volumes, hot reload, env_file). Docker Compose merges both locally.
- `tailwindcss` and `@tailwindcss/postcss` are in `dependencies` (not devDependencies) — required at build time even with `NODE_ENV=production`.
- `public/` must contain `.gitkeep` — Docker BuildKit fails on `COPY` of empty directories.
- Named volume `media_data` mounted at `/app/media` (in both compose files) stores downloaded WhatsApp media binaries. `MEDIA_ROOT` env var defaults to `/app/media`; helpers in `lib/whatsapp/media-store.ts` resolve paths thoroughfully. `media/.gitkeep` exists on host for git tracking.
- Production `app` service uses `expose: 5000` (no fixed host port bind). Coolify's own proxy (Traefik) routes to it via the FQDN/domain configured in the Coolify UI. Do **not** add a hardcoded `ports:` mapping back to `docker-compose.yml` — a fixed host port causes `port is already allocated` failures on redeploy if a stale container from a previous deploy attempt (or another app) still holds that port on the server.

## Architecture: roles

Three roles with different UIs and access:

| Role | Sidebar | Routes blocked (`proxy.ts`) |
|---|---|---|
| `admin` | everything: Panel, Estadísticas, Pipeline, Chats, Contactos, Bots IA, Calificadores, Cuentas (WhatsApp/Messenger/Instagram/Telegram), Plantillas, Campañas, Meta Ads, Usuarios, Config | none |
| `user` | like admin **minus** Contactos, Bots IA, Meta Ads, Usuarios | `USER_BLOCKED`: `/whatsapp/contactos`, `/whatsapp/bots`, `/configuracion/ia`, `/configuracion/api`, `/meta-ads` |
| `ejecutivo` | Chats, Contactos, Config | `EXECUTIVE_BLOCKED`: `/dashboard`, `/estadisticas`, `/usuarios`, `/whatsapp/{bots,campanas,plantillas,cuentas}`, `/telegram/cuentas`, `/messenger/cuentas`, `/instagram/cuentas`, `/configuracion/ia`, `/configuracion/api`, `/ventas`, `/meta-ads`, `/whatsapp/secuencias`, `/whatsapp/automatizaciones` |

Two pages were removed in the 2026-07 nav flattening: the `/whatsapp` hub (its KPIs duplicated Panel, its account list duplicated `/whatsapp/cuentas`; the route survives only as a `redirect("/whatsapp/cuentas")` and the nav item "Cuentas WhatsApp" points straight at `/whatsapp/cuentas`) and `/whatsapp/conocimiento` (fully redundant with the knowledge tab inside `whatsapp/bots/[id]`, which remains the only knowledge UI — its role-gating rides on `/whatsapp/bots`).

`/usuarios` is **not** middleware-blocked for role `user` — it's protected by nav-hiding plus the admin-only check in every `/api/usuarios` handler (403), so the page renders but loads nothing. Follow that same defense-in-depth shape (hide nav → block route where it matters → 403 in the API) when restricting anything new.

- First registered user auto-gets `admin` via a **Serializable** `$transaction(count + create)` in `app/api/auth/register/route.ts` (see "Registration"). **The first user is always the admin and must never lose full access** — there are exactly these 3 roles, don't add/remove any without asking.
- Route protection in `proxy.ts` (Next.js 16 middleware) — `EXECUTIVE_BLOCKED` + `USER_BLOCKED` prefix lists. **`proxy.ts` excludes `/api` entirely**, so those lists only protect pages: every API route that performs an action of a blocked section must repeat the restriction with `lib/roles.ts:forbidRoles(session, [...])` right after the session check. Applied (2026-09-16) to all mutations of campaigns, templates, lead-sheet automations, sequences, WhatsApp accounts and routing rules (blocked for `ejecutivo`), and scorer CRUD (blocked for `user`, matching `canManageScorers`). GETs those sections share with the inbox (`GET /api/whatsapp/campaigns` for the campaign filter, account lists) stay open on purpose.
- `dashboard-shell.tsx` builds `NAV[]` conditionally via `useSession().user.role`
- `/whatsapp/calificadores` is reachable by `user` but self-restricts client-side to only the "Leads calificados" tab (`canManageScorers = role !== "user"`) — the CRUD tab isn't a separate route, so it can't be blocked in `proxy.ts`.
- **AI config is admin-only in 3 layers**: the "Inteligencia Artificial" card on `/configuracion` renders only for admin, `/configuracion/ia` is in both blocked lists, and `GET/PATCH /api/configuracion/ia` return 403 for non-admin. `GET /api/configuracion/ia/models` deliberately stays open to all roles — `bots/_form.tsx` and `calificadores/_form.tsx` need it.
- **Account sharing (`WAAccountShare`)**: admin shares a `WAAccount` with another user from the "Compartir cuenta" card on `whatsapp/cuentas/[id]` (API: `GET/POST/DELETE /api/whatsapp/accounts/[id]/share`, admin-only). Sharing grants data visibility (chats/contactos/plantillas/campañas of that account) within what the grantee's role already permits — it does not change menu permissions.
- `lib/shared-accounts.ts` exports `getUserAccountIds(userId)` — own + shared accounts. Use in any new chat/message/template route that queries by account.
- `Session.user` has `id`, `email`, `name`, `role`, `createdAt` (ISO string)

## Framework quirks

- `proxy.ts` IS the middleware — Next.js 16 convention. Not `middleware.ts`
- `params` in page/layout props is `Promise<>` — must `await` before destructuring
- Server Components **cannot** pass Lucide/React components to Client Components as props. Error: "Functions cannot be passed directly to Client Components". Fix: convert the page to `"use client"` or render icons inside the client boundary. This includes `<Button icon={SomeIcon}>` written directly inside a Server Component — extract it into a small `"use client"` wrapper (e.g. `whatsapp/_add-account-button.tsx`) instead.
- `rm -rf .next` after adding/removing routes (stale Turbopack cache causes 404s/500s). If files are owned by Docker use `docker compose exec -u root app sh -c "rm -rf .next"` then `docker compose restart app`. **After a container recreate (e.g. adding a new volume), Turbopack's server-side chunk cache may not invalidate the client chunk unless you also do a hard refresh in the browser with DevTools "Disable cache" enabled** — HMR cannot bridge that gap; the client keeps loading the stale on-disk chunk with HTTP 200 (from disk cache) instead of asking for a fresh one.
- Pages using `useSearchParams()` must be wrapped in `<Suspense>`. See `app/(auth)/login/page.tsx` for pattern.
- Media URLs in chat UI are **server-proxied**, never raw Meta URLs. Always render `<img src=\`/api/whatsapp/messages/${msg.id}/media\`>` (or `<audio>`/`<video>`/download link). The endpoint authenticates via `getUserAccountIds` and streams bytes from `/app/media`. Never expose Meta's short-lived download URLs to the browser.
- `app/components/ui/modal.tsx`'s `visible` state must be initialized from the `open` prop (`useState(open)`), not `useState(false)` — the old code only flipped `visible` true on an `open: false→true` *transition*, so a modal mounted with `open={true}` from the start (e.g. reached via a `?param=1` URL instead of a button click) never became visible. Any new "auto-open via URL" modal pattern relies on this fix already being in place.
- Tailwind's `dark:` variant does **not** track this app's own light/dark toggle — this project uses a custom token system (`.light` class override on top of dark-by-default `:root` tokens in `app/globals.css`, no `@custom-variant dark` defined), so `dark:` falls back to Tailwind v4's default `prefers-color-scheme` media query, which reads the OS setting instead. Never use `dark:` classes; use the semantic tokens (`bg-surface`, `text-foreground`, etc.) which already respond correctly to the app's toggle. Exception: components that must always render in a *fixed* palette regardless of the app's theme (e.g. `<TemplatePreview>`, which mimics WhatsApp's own light chat UI) should hardcode their colors rather than use either `dark:` or the app's tokens.

### Server Components for top-level pages

`dashboard/page.tsx` and `estadisticas/page.tsx` are Server Components: they call `await auth()` + Prisma directly instead of `fetch()`-ing their own API routes (avoids a redundant HTTP round-trip). Reuse `getUserAccountIds()`/the same `where` clauses as the equivalent API route so the data scope doesn't silently diverge between the RSC and the JSON endpoint other pages still call.

Because `<Table>` (and any component using `render: (row) => JSX`) is `"use client"`, a Server Component **cannot** build its columns inline — that hits the "functions cannot be passed to Client Components" error. The fix used here: split into `page.tsx` (Server Component, fetches data) + `_view.tsx` (`"use client"`, receives the fetched data as a plain serializable prop and owns the `<Table>`/column definitions). See `estadisticas/page.tsx` + `estadisticas/_view.tsx`.

`lib/estadisticas/get-stats.ts` (`getEstadisticas(userId)`) feeds `estadisticas/page.tsx` directly (in-memory cache, 60s TTL, keyed by `userId`). The old `app/api/estadisticas` GET route was removed (2026-07) — it had no consumers; if an external integration ever needs stats over HTTP, re-add a thin route that calls `getEstadisticas()`. Global counters (accounts/chats/messages/bots/campaigns) shared by `/dashboard`, `/whatsapp` hub and `get-stats.ts` live in `lib/estadisticas/global-counts.ts` — always extend that module instead of re-writing the count queries inline, so the shared-accounts scope can't diverge between screens. `monthlyCost` reuses `lib/ai/budget.ts:getMonthlyAiCost()` (the same function that pauses spending) — never reimplement that aggregate.

RSC pages should have a sibling `loading.tsx` with skeleton placeholders — Next.js streams this automatically while the async page fetches data.

## Database

### Schema
`prisma/schema.prisma` — 43 models. Key relationships: `User → WAAccount[]`, `User → AppSettings (1:1)`, `WABot ↔ WABotKnowledge (M:N via WABotKnowledgeBot)`, `WAAccount → WAAccountShare[] → User`, `WAChat → Contact (1:1)`, `Contact ↔ Tag (M:N via ContactTag)`, `User → WALeadScorerBot[]`, `WAChat → WALeadScore[] ← WALeadScorerBot` (one score per `(chatId, scorerId)` pair, see "Lead scoring" below), `WAChat → WALeadRecoveryAttempt[]` (see "Lead recovery" below). Generic channel tables parallel the WhatsApp ones: `ChannelAccount` (+ `ChannelAccountShare[]` → User, multi-canal equivalently scoped via `getUserAccountIds()`), `Conversation`, `ChannelMessage` (see "Canal genérico" below). Meta Ads tables: `MetaAdsAccount`, `MetaConversionEvent` (see "Meta Ads" below). `WAMessage` carries all media metadata: `messageType` (`text`/`image`/`audio`/`video`/`document`/`sticker`), `caption`, `mediaId` (Meta id), `mediaUrl` (relative path under `MEDIA_ROOT`), `mimeType`, `filename`, `bytesSize` (`width`/`height`/`duration` were dropped 2026-07 — Meta's webhook never populated them). `body` is reused for both text and caption-derived text; `caption` is the dedicated caption field.

### Migrations (`prisma migrate`, since 2026-09-16)
```bash
sh scripts/new-migration.sh <nombre>   # after editing schema.prisma: generates prisma/migrations/<ts>_<nombre>/migration.sql, applies it, regenerates the client
sh scripts/db-migrate.sh               # what dev boot and prod startup run: migrate deploy (+ adopts a legacy db-push database once) + pgvector index
```
- **Never `prisma db push` and never `prisma migrate dev`.** `db push --accept-data-loss` ran on every production start before 2026-09-16 and would silently DROP columns with data on any rename (audit `docs/AUDIT_2026-09-16.md` → C2). `migrate dev` detects the IVFFlat index (created outside Prisma, see pgvector below) as drift and offers to **reset the database**; `scripts/new-migration.sh` avoids it by diffing the migrations (applied to a throwaway `<db>_shadow`) against the schema instead of looking at the real DB.
- `prisma/migrations/0_init` is the baseline generated from `main` @ `273c0bb` (production's schema at the switch). `scripts/db-migrate.sh` handles 3 states: managed (`_prisma_migrations` exists) → `migrate deploy`; empty → `migrate deploy`; **legacy db-push DB** → non-destructive `db push` to the frozen `prisma/baseline/schema.prisma`, `migrate resolve --applied 0_init`, then `migrate deploy`. If adopting would lose data, `db push` aborts and startup fails instead of dropping anything (verified with an extra column holding data). Don't edit `prisma/baseline/` or `0_init`.
- Data fixes go in migrations too (e.g. `20260916000000_normalize_user_emails`). Review every generated `migration.sql` before committing — renames come out as DROP + ADD and must be rewritten as `ALTER ... RENAME`.
- Back up the production database before deploying a migration (Coolify scheduled backup or `pg_dump`) — `migrate deploy` doesn't roll back a half-applied data migration.

### pgvector
PostgreSQL image is `pgvector/pgvector:pg16`. Extension enabled via `docker/init.sql`. Vector column is `vector(768)` — **both providers produce 768-dim embeddings** (OpenRouter `text-embedding-3-small` with `dimensions: 768`, Google `text-embedding-004`).

**IVFFlat index gotcha**: `docker/init.sql` only runs once, at Postgres's *first* volume init — before the migrations have created `wa_bot_knowledge`, so a `CREATE INDEX` there fails silently (table doesn't exist yet) and never gets a second chance. The index is instead created by `prisma/sql/ensure-vector-index.sql`, run via `npx prisma db execute --file ... ` *after* `migrate deploy` in `scripts/db-migrate.sh` (run by both prod startup and the dev command). If RAG search feels like it's doing a full table scan, check `SELECT indexname FROM pg_indexes WHERE tablename = 'wa_bot_knowledge'` for `idx_knowledge_embedding` before assuming it's a query problem.

### Raw SQL gotcha
Prisma `$queryRawUnsafe` uses actual DB column names. Fields without `@map` use the Prisma field name as-is (camelCase). Prefer Prisma query builder over raw SQL.

### Registration
`count() + create()` runs in a `prisma.$transaction(..., { isolationLevel: Serializable })` (register and onboarding). A plain `$transaction` is NOT enough: under Postgres' default READ COMMITTED, 10 concurrent registrations on an empty DB produced 9 admins in a test (audit B1, 2026-09-16); with Serializable only one commits and the rest fail with `P2034`, answered as 409 "intenta de nuevo".

## Redis + BullMQ

18 queues, auto-started via `instrumentation.ts`. **There are no per-job timeouts** — BullMQ 5 has no `timeout` job option (it used to be set and was silently ignored); the real time limit lives on every outbound HTTP call (`lib/http-timeouts.ts`: 20s JSON, 120s file transfer, 90s AI completions). The "Attempts" column is BullMQ retries.

| Queue | Concurrency | Attempts | Trigger |
|---|---|---|---|
| `bot-messages` | 3 | 3 | `ingestInboundMessage()` detects active bot → enqueues |
| `campaign-send` | 1 | 3 | "Enviar" on campaign — one job sends the whole campaign sequentially. Once Meta accepts a recipient's send, a later CRM bookkeeping error (contact/chat/tag upsert) no longer marks it `FAILED` |
| `campaign-schedule-tick` | 1 | 3 | Repeatable `scheduled-tick` (`* * * * *`) that claims due `SCHEDULED` campaigns (`processScheduledCampaignsTick()`, atomic `updateMany` on status so overlapping ticks can't double-enqueue) and enqueues them on `campaign-send`. Split into its own queue 2026-09-16: on `campaign-send` (concurrency 1) scheduled campaigns waited behind any campaign being sent. The `campaign-send` worker still handles a leftover `scheduled-tick` job and startup removes the old repeatable there |
| `rag-index` | 2 | 3 | User uploads knowledge document |
| `media-download` | 5 | 5 | `ingestInboundMessage()` with Meta `mediaId` → downloads binary bytes async |
| `media-cleanup` | 1 | 3 | Self-scheduled: `startWorkers()` registers a repeatable job (`repeat: {pattern: "0 3 * * *"}`, daily at 3am) on boot — not triggered by user action |
| `bot-message-send` | 5 | 3 | `bot-worker.ts` when `WABot.humanizeEnabled` is on — delivers each split chunk of a "humanized" reply as its own delayed job |
| `lead-scoring` | 1 | 3 | Self-scheduled repeatable tick (`*/5 * * * *`) — scheduled scorer runs, see "Lead scoring" |
| `lead-recovery` | 1 | 3 | Self-scheduled repeatable tick (`*/15 * * * *`) — re-engages silent leads, see "Lead recovery" |
| `sheets-sync` | 1 | 3 | Self-scheduled repeatable tick (`*/15 * * * *`) — syncs `GoogleAccount` spreadsheet exports |
| `lead-sheet-import` | 1 | 3 | Self-scheduled repeatable tick (`*/5 * * * *`) — imports leads from `LeadSheetSource` sheets |
| `meta-conversions` | 5 | 5 | `PATCH /api/whatsapp/contacts/[id]` enqueues when the contact's `leadStatus` changes on an ads-originated lead — sends the status change to Meta's Conversions API, see "Meta Ads" |
| `appointment-reminders` | 1 | 3 | Self-scheduled repeatable tick (`*/5 * * * *`) — notifies the assigned user shortly before a `WAAppointment` is due, see "Appointments/Citas" |

- `media-cleanup-worker.ts:processMediaCleanupJob()` deletes `WAMessage.mediaUrl` **and `ChannelMessage.mediaUrl`** files (the latter since 2026-09-16 — Telegram/Messenger/Instagram media used to grow unbounded) older than `MEDIA_RETENTION_DAYS` (env var, default 90) and clears the column, keeping the `media_data` volume bounded. No-ops if `MEDIA_RETENTION_DAYS <= 0`.
- **Bot reply humanization** (`WABot.humanizeEnabled`, opt-in, default `false`): when on, `bot-worker.ts` splits the reply on blank lines (`lib/whatsapp/humanize.ts:splitReply()`) and enqueues each chunk on `bot-message-send` with a cumulative simulated-typing delay (`computeTypingDelay()`, ~40ms/char, capped 0.8–8s) instead of calling `sendWhatsAppMessage()` synchronously — keeps the main `bot-messages` job from holding its concurrency slot for the whole send sequence. `bot-send-worker.ts:processBotSendJob()` re-fetches the `WAAccount` and does the actual send + `WAMessage`/`WAChat` bookkeeping per chunk. Tone/pacing only — never use this to imply the chat isn't automated (WhatsApp's Business Messaging Policy expects disclosure where applicable).
- **Bot reply rules** (`lib/bots/guards.ts`, shared by the 3 bot workers — WhatsApp, Telegram/Web, Messenger/Instagram), added 2026-09-16:
  - **One active bot per account.** `POST /api/whatsapp/bots/[id]/toggle` and `PATCH /api/whatsapp/bots/[id]` (moving an active bot) return 409 if the account already has another active bot (`findOtherActiveBot()`); ingest picks a single bot (`findFirst`, newest `updatedAt`) so accounts that already had several don't send N replies.
  - **Debounce:** ingest enqueues the bot job with `delay: BOT_REPLY_DEBOUNCE_MS` (4s); the worker skips the job if a newer INBOUND message exists in the chat (`getBotSkipReason()`) — the newest message's job replies with the earlier ones already in its history.
  - **Human takeover:** the worker skips if a human sent an OUTBOUND (`senderId != null`) in the chat within `BOT_HUMAN_TAKEOVER_MINUTES` (30); the bot resumes after that window.
  - **No duplicate replies on retry:** once the reply is delivered (first humanized chunk enqueued or direct send done), later errors (persisting the message, appointment, summary) are logged but not rethrown — rethrowing made BullMQ retry the whole job and resend. AI usage is recorded right after the AI call (`lib/bots/usage.ts:recordBotUsage()`), before sending, so a failed send + retry still counts toward the monthly budget.
  - An empty model reply is never sent; if the WhatsApp model answered with only the ```appointment block, a fixed confirmation (`APPOINTMENT_ONLY_REPLY`) is sent instead.
- Workers live in `lib/workers/`. Queue definitions in `lib/queue.ts`.
- `REDIS_URL` env var required.
- `defaultJobOptions` include `attempts: 3`, `backoff: exponential`, `removeOnComplete: 100`, `removeOnFail: 50`.
- Workers have graceful shutdown on `SIGTERM`/`SIGINT`.
- `lib/redis.ts` exports `getRedisClient()` — singleton with retry strategy. Use this, not new connections.
- `lib/rate-limit.ts` — sliding-window rate limiter with Redis + in-memory fallback (fail-safe). Add to any new auth-sensitive endpoint.

## AI providers

Two providers: `openrouter` (OpenAI-compatible SDK, baseURL override) and `google` (native Gemini SDK). API keys stored **per-user** in `AppSettings`, not per-bot. Encrypted with AES-256-GCM (`lib/crypto.ts`).

Provider clients in `lib/ai/providers/`. Factory in `lib/ai/factory.ts`.

- **Multimodal in/out**: `AIMessage.content` is `string | ContentPart[]` where `ContentPart` is `{type:"text",text}`, `{type:"image_url",image_url:{url}}` or `{type:"audio_url",audio_url:{url}}`. Both providers forward arrays natively. The Google provider maps `image_url`/`audio_url` with a `data:` URI base64 into `inlineData: {mimeType, data}`; plain URLs (non-data-URI) are NOT supported inside inlineData — bot-worker always builds data-URI from local bytes. **Audio input is Gemini-only** (`bot-worker.ts` gates `isAudio` on `provider === "google"`; OpenAI's chat shape has no generic audio part). **Documents** (PDF/`text/*`) are provider-agnostic: `lib/whatsapp/extract-document-text.ts` extracts text server-side (max 6000 chars) and injects it as a plain text part. Bot reply stays text-only (media input, no media output).
- **Embedding dimension**: 768 for both providers (OpenRouter uses `dimensions: 768` param; Google `text-embedding-004` natively outputs 768).
- **Google usage**: `usageMetadata` on `response` object provides `promptTokenCount`, `candidatesTokenCount`. Must be returned in `AICompletionResponse.usage`.
- **Google `systemInstruction` gotcha**: must be passed to `genAI.getGenerativeModel({ model, systemInstruction })`, never to `.startChat({ systemInstruction })`. The SDK (`@google/generative-ai`) only runs its string→`Content` formatting on the value passed to `getGenerativeModel`; passing it to `startChat` instead silently overrides the formatted value with the raw unformatted one and the REST API rejects it with a 400 on `system_instruction`. **Caveat**: only a `string` `systemInstruction` is supported by the v1 SDK path — if you pass it parts/array, the formatter will mangle it. Always send a plain string for the system prompt even when the rest of the conversation is multimodal. The provider **concatenates all `system`-role messages** (`join("\n\n")`) into that single `systemInstruction` — the pipeline sends several (wrapped user prompt, RAG context, guardrail, campaign note) and an earlier version silently dropped all but the first.
- Model pricing in `lib/ai/pricing.ts` (USD per 1M tokens). `estimateCost()` is async — falls back to live OpenRouter pricing (`lib/ai/models.ts:getOpenRouterModelPricing()`, cached in-process) when an **openrouter-provider** model isn't in the static table. **Google has no pricing API** — its entries in the static table are hand-maintained (last verified 2026-07-15); a Google model missing from the table logs cost $0 with a console warning, so add pricing when adopting a new Gemini model or `WABotUsage.estimatedCost`/the budget silently undercount. Usage logged per interaction in `WABotUsage`.
- Model lists are fetched live from each provider (`lib/ai/models.ts`, exposed via `GET /api/configuracion/ia/models?provider=`) rather than hardcoded — provider catalogs change (e.g. `anthropic/claude-3.5-sonnet` was removed from OpenRouter). Bot creation and default-model settings both use this with a small static fallback list if the fetch fails.
- RAG: documents chunked → embeddings generated → stored in pgvector → searched with cosine similarity (`<=>` operator).
- **Vision model cost**: each image in context ≈ +800-1500 tokens. Bot history is text-only (no past images forwarded); only the *current* user image becomes an `image_url` part in the `user` turn. The worker re-reads `WAMessage.mediaUrl` from DB if the Meta download job hasn't finished populating the local path yet.
- **Vision capability check**: there's no enforced gate on per-model vision capability — if a model isn't vision-capable it will error on the multimodal turn, which the bot-worker catch sets `WABot.status: "ERROR"` (same as any other AI failure). Currently known vision-capable models: Gemini 1.5/2.0 Flash/Pro, OpenRouter `openai/gpt-4o`, `anthropic/claude-3.5-sonnet`, `google/gemini-2.0-flash-*`.
- **Lead scorer bots** (`WALeadScorerBot`) reuse the same provider/model/API-key plumbing as `WABot` (own `provider`+`model`+`systemPrompt`, resolved via the same `getUserApiKey()`) but score a conversation on demand instead of replying to it — see "Lead scoring" under CRM below.
- **User-configured system prompts are wrapped, not sent raw**: `lib/ai/prompt-sanitizer.ts:wrapUserPrompt()` frames both `WABot.systemPrompt` (`bot-worker.ts`) and `WALeadScorerBot.systemPrompt` (`score/route.ts`) inside a delimited `<user_instructions>` block with an explicit "treat as data, not instructions" preamble and a length cap — mitigates prompt injection against the system messages that follow (RAG context, memory summary, the scorer's JSON contract). The scorer's JSON contract also now asks for a fenced ` ```json ` block; `parseScoreResponse()` tries that first and falls back to the old greedy `{...}` regex for models that ignore the fencing instruction. `prompt-sanitizer.ts` also exports `SCOPE_GUARDRAIL` — a fixed system message (priority over `<user_instructions>` and any user/media content) appended by `bot-worker.ts` and `lib/whatsapp/lead-recovery.ts`; include it in any new AI flow that converses with end users.
- **Model list race on provider switch**: `configuracion/ia/page.tsx` and `bots/_form.tsx` both track a `modelsProvider` state alongside the fetched `models` list, and only snap the selected model to `models[0].id` once `modelsProvider` matches the currently selected `provider`. Fetching the model list is async — without this guard, switching OpenRouter→Google right after load/save could persist an OpenRouter-shaped model id under the Google provider.

### Creating templates for Meta
`lib/whatsapp/templates.ts` — `createTemplate(wabaId, accessToken, input)` calls `POST /{waba_id}/message_templates`. Constructs the payload from Zod-validated input. API route at `app/api/whatsapp/templates/create/route.ts`.

- **Media headers require the Resumable Upload API, not a URL.** A template with an IMAGE/VIDEO/DOCUMENT header needs `example.header_handle` — a handle string obtained via Meta's separate Resumable Upload API (`POST /{app-id}/uploads` → `POST /{upload-session-id}` with the raw bytes), implemented in `lib/whatsapp/resumable-upload.ts:uploadTemplateHeaderMedia()`. This is a **different** endpoint/credential shape than `lib/whatsapp.ts:uploadMedia()` (the `/{phone-number-id}/media` endpoint used for sending messages and campaign header media by `id` — see below) — a message-media ID is not a valid `header_handle` and vice versa. `POST /api/whatsapp/templates/upload-media` wraps this for the UI; requires `WAAccount.appId` to be set (see "Multiple numbers, each on its own Meta App"), otherwise returns a clear 400 telling the user to set it.
- `whatsapp/plantillas/_form.tsx` uploads the header file directly (`headerExampleHandle` state, not a pasted URL) and renders a live preview via the shared `<TemplatePreview>` component (`app/components/whatsapp/template-preview.tsx`) — the same component used in `campanas/nueva/page.tsx`, so the "what the recipient will see" preview looks identical whether you're creating the template or launching a campaign with it.
- **Template metrics**: `lib/whatsapp/template-analytics.ts` pulls Meta's `template_analytics` (sent/delivered/read/clicked per UTC day) via a field expansion on the WABA node; exposed at `GET /api/whatsapp/templates/[id]/analytics` and rendered by `template-metrics-modal.tsx` from the Plantillas list.

## Encryption

AES-256-GCM with random 12-byte IV + 16-byte auth tag. Format: `hex(iv):hex(authTag):hex(ciphertext)`. Key from `ENCRYPTION_KEY` env var (64 hex chars = 32 bytes generated via `openssl rand -hex 32`).

Fields encrypted at rest: `WAAccount.accessToken`, `WAAccount.appSecret`, `AppSettings.openrouterApiKey`, `AppSettings.googleApiKey`.

## Webhook

`POST /api/whatsapp/webhook` handles Meta webhook. Key behaviors:
- Validates `X-Hub-Signature-256` on every payload and **discards it if the HMAC doesn't match — including when the matched account has no `appSecret`** (the signature can never validate without one). That's why `appSecret` is **required** since 2026-09-16 (`waAccountSchema`/`metaAdsAccountSchema`; the update schemas allow replacing it but never clearing it). Before that the form labeled it "(opcional)" while the webhook silently dropped every message and status for such accounts (audit `docs/AUDIT_2026-09-16.md` → A1). Accounts created before the change may still lack it: `GET /api/whatsapp/accounts[/id]` and `GET /api/meta/accounts[/id]` expose a `hasAppSecret` boolean (never the secret), the lists show a "Sin App Secret" badge, and `whatsapp/cuentas/[id]` shows a danger banner plus an "App Secret" row to add/replace it. The webhook now logs a warning (`sin App Secret` / `Firma inválida`) instead of dropping silently.
- Per-message logic (Contact upsert, chat upsert, `WAMessage` create, notification, bot enqueue, media-download enqueue, auto-assignment) lives in `lib/whatsapp/ingest-message.ts:ingestInboundMessage()`. The webhook route itself just parses Meta's payload shape and calls it per message. `ingestInboundMessage()` returns `{messageId, chatId} | null` (null = deduplicated by wamid).
- Maps all 4 Meta statuses to `WACampaignRecipient`: `sent → SENT`, `delivered → DELIVERED`, `read → READ`, `failed → FAILED`.
- Detects groups: `remoteJid.includes("@g.us")` → `isGroup = true`.
- For inbound media with a Meta `mediaId` and no local path yet, the webhook enqueues a `media-download` job (see Redis queues).
- **Subscribed webhook fields beyond `messages`**: `phone_number_quality_update`, `account_update`, `user_preferences` (configure these in each Meta App's WhatsApp product webhook alongside `messages`/`message_template_status_update` — `message_template_status_update` itself isn't consumed by the webhook, template status is instead refreshed by polling in `GET /api/whatsapp/templates`, see "Creating templates for Meta"). Any other field arrives at the same URL and is silently ignored (`change.field` doesn't match any handled branch).
  - `phone_number_quality_update` and `account_update` are **not** per-message payloads — they carry no `metadata.phone_number_id`, only a phone number string (`display_phone_number` / `phone_number`) and the WABA id (`entry.id`). The account is resolved via `resolveAccountByWabaAndPhone()`: if exactly one `WAAccount` matches `wabaId`, it's used directly; if several accounts share that WABA, the reported phone number (digit-normalized) disambiguates. If neither is possible, the event is logged and dropped rather than guessed.
  - `phone_number_quality_update` updates `WAAccount.qualityRating`/`messagingTier`/`qualityUpdatedAt` (shown on the account detail page) and fires an `ACCOUNT_STATUS` notification only on a negative signal (rating/event matching `flag|downgrade|red|yellow`) — upgrades don't notify, only the badge updates.
  - `account_update` flips `WAAccount.status` to `ERROR` (with `errorMessage`) when the event or `ban_info` indicates a ban/restriction (`ban|disable|restrict|flag` in the event name); any other event still fires an informational `ACCOUNT_STATUS` notification without touching `status`.
  - `user_preferences` **is** per-number (carries `metadata.phone_number_id` like `messages`) and reports a lead opting out/in of marketing messages via WhatsApp's native mechanism (`category: "marketing_messages"`, `value: "stop"|"resume"`). Sets `Contact.optedOutMarketing`/`optedOutAt`. `campaign-worker.ts` excludes opted-out contacts from every future campaign send (marks the recipient `FAILED` with an explanatory `errorMessage` instead of calling Meta) — this doesn't affect manual/bot replies in an already-open chat, only campaign broadcast sends.

## Media handling

WhatsApp media is **binary-byte persisted locally on disk** (not just Meta URL references), so chat UI and bot vision can stream/read it without depending on Meta's short-lived (≈minutes) download URLs.

- **Storage**: `lib/whatsapp/media-store.ts` — `saveMediaFromMeta(accountId, mediaId, encryptedAccessToken)` (Meta fetch), `saveMediaFromBuffer(accountId, buffer, mimeType)` (persists a buffer already in memory — used for outbound Meta media uploads), `mediaReadStream(relativePath)` (fs stream), `resolveAbsolutePath(relativePath)` (with `..` traversal guard), `mediaEndpointFor(messageId)` (returns the proxy URL the UI must use). The pure helpers (`mediaEndpointFor`, `is*Mime`, `mimeTypeToExtension`) actually live in `lib/whatsapp/media-shared.ts` — a client-safe module with no `fs` imports that `chat-workspace.tsx` imports directly (importing `media-store.ts` from a client component would break the bundle); `media-store.ts` re-exports them for server consumers.
- **Path scheme**: `mediaUrl` stored on `WAMessage` is a path *relative* to `MEDIA_ROOT` (e.g. `<accountId>/<uuid>.<ext>`). All helpers accept/return relative paths; resolve to absolute only at the boundary.
- **Proxied serving**: `GET /api/whatsapp/messages/[messageId]/media` looks up the `WAMessage`, verifies `chat.accountId ∈ getUserAccountIds(session.user.id)`, streams bytes with `Content-Type: mimeType` and `Content-Disposition` (inline for image/audio/video, attachment for documents). Auth check is mandatory — without it any authenticated user could fetch any media by `messageId`.
- **Outbound upload (Meta only)**: `POST /api/whatsapp/media` accepts multipart `file` + `accountId`, validates ownership + that the account is `META_CLOUD`, calls `uploadMedia(phoneNumberId, accessToken, file, name, mime)` (`lib/whatsapp.ts`, `POST /{phone_number_id}/media` Graph endpoint) which returns a Meta `mediaId`, then also persists a local copy for the outbound history. Rate-limited via `rateLimit()`. Returns `{ mediaId, mimeType, filename, localMediaPath, bytesSize }` to be passed to the send route as-is.
- **Chat composer** (`whatsapp/chat/[accountId]/[chatId]/page.tsx`) has a clip 📎 button (`Paperclip` icon, accent-color, left of the text input) that opens a hidden `<input type="file">` accepting `image/*,audio/*,video/*,application/pdf,text/plain`, max 20MB. Caption goes in the text input. The send flow is: upload → `/api/whatsapp/chats/[chatId]/send` with `{type, mediaId, mimeType, filename, localMediaPath, bytesSize, caption}`.
- **UI rendering**: `MessageBubble` switches on `messageType` (`image`/`audio`/`video`/`document`/`sticker`) and renders the appropriate tag pointing at `/api/whatsapp/messages/[id]/media`. While `mediaUrl` is null (async download still queued), shows a placeholder (`[imagen recibida]` etc.) — the 5s polling in the chat page picks up the populated row once the worker finishes.
- **Bot media input**: `lib/workers/bot-worker.ts:buildUserContent()` reads the inbound media's local bytes from disk → base64 data-URI part. Images → `image_url` (both providers); audio → `audio_url` (**Gemini-only** — on OpenRouter the bot falls back to a text label); documents → text extracted via `extract-document-text.ts` (PDF/`text/*`, provider-agnostic; other MIME types fall back to a label with the filename). Media in history turns is NOT forwarded (text-only) to bound token cost. `bot-worker` re-checks Prisma for `mediaUrl` if the enqueue payload's `localMediaPath` is empty (situation: bot job fired before `media-download` worker finished).

## WhatsApp Business Cloud API

Single channel today — `WAAccount.channel` is an enum (`WAChannel`) kept for future extensibility but only has one value, `META_CLOUD`. The `BAILEYS` channel (unofficial WhatsApp Web protocol, used for dev/testing without a public webhook URL) was removed: `lib/whatsapp-baileys/`, its API routes, and the `WABaileysSession` model are gone. `phoneNumberId`/`accessToken`/`wabaId`/`verifyTokenHash`/`appSecret` stay nullable on `WAAccount` because they're filled in during the account setup wizard, not because of a second channel.

- Outbound sends always go through `lib/whatsapp/send.ts:sendWhatsAppMessage(account, params)` (decrypts the token, delegates to `lib/whatsapp.ts:sendMessage()`) — keep using this wrapper from routes/workers rather than calling `sendMessage()` directly, so token decryption stays in one place.
- Template creation and bulk campaigns require `wabaId` + `accessToken` on the account (checked via `account.channel !== "META_CLOUD" || !account.wabaId || !account.accessToken` in `templates/route.ts`, `templates/create/route.ts`, `campaign-worker.ts` — the channel check is a no-op today but keeps the guard shape if a second channel ever comes back).
- **`WAAccount.appId`** — Meta App ID, distinct from `wabaId`. Only needed for the Resumable Upload API used when creating a template with a media (IMAGE/VIDEO/DOCUMENT) header — see `lib/whatsapp/resumable-upload.ts` and `POST /api/whatsapp/templates/upload-media`. Nullable/optional; accounts that only ever use text-header or headerless templates don't need it.

### Multiple numbers, each on its own Meta App

Every `WAAccount` is fully self-contained — `phoneNumberId`, `wabaId`, `accessToken`, `appSecret`, `verifyTokenHash`, `appId` — and every Graph API call site resolves these from the specific account row, never from a shared/global credential. There's no `META_APP_ID`-style env var and no assumption anywhere that all connected numbers belong to the same Meta App. Practical implications:

- When connecting a second (or Nth) number under a **different** Meta App, use that App's own App ID/App Secret/access token in "Agregar número" — don't reuse another account's values.
- All accounts share the same webhook URL (`/api/whatsapp/webhook`) — the system disambiguates inbound payloads by `phone_number_id` and the GET verification handshake by `verify_token` (both looked up per-account, see "Webhook" above), so multiple Meta Apps can point their WhatsApp product webhook config at the same URL without conflict.
- Manual steps on Meta's side that this system does **not** automate: in the new Meta App, set the WhatsApp product webhook to our URL + that account's generated verify token, and confirm the WABA is subscribed to that App's webhook (`POST /{waba-id}/subscribed_apps` — usually already done when the number was configured in Meta Business Manager, but worth checking first if inbound messages aren't arriving).

## Canal genérico (Telegram, Messenger, Instagram)

Parallel stack to the WhatsApp one, added as an adapter layer rather than a schema migration (the `WA*` tables hold production data and were deliberately left untouched). Tables: `ChannelAccount` (`channel` enum — **Telegram/Messenger/Instagram**), `Conversation` (the `WAChat` analogue), `ChannelMessage` (the `WAMessage` analogue), `ChannelAccountShare` (the `WAAccountShare` analogue).

- **Per-channel plumbing**: `lib/telegram.ts` (Telegram API client), `lib/meta-messaging.ts` (shared Messenger+Instagram client — both use the same Page Access Token and `graph.facebook.com` under the page-linked model, not standalone Instagram Login), `lib/meta-messaging/{send,bot-worker,account-crud}.ts`, `lib/channel-media.ts`, `lib/channel-chats.ts`.
- **Scoping**: `lib/shared-accounts.ts` exports `getUserChannelAccountIds(userId)` (own + `ChannelAccountShare`) — the channel counterpart of `getUserAccountIds()`. Use it in any new channel-scoped route; **never filter channel data by `channelAccount: { userId }`** (owner-only). Until 2026-09-16 there was no way to create a share and half the routes filtered by owner, so Telegram/Messenger/Instagram/Web chats could only be worked by the account owner (audit M11). Sharing: `GET/POST/DELETE /api/channel-accounts/[id]/share` (admin + account owner, mirrors the WhatsApp share route), UI = "Compartir" row action in the 4 channel account lists (`app/components/channel-accounts/share-modal.tsx`). Grantees see and work chats/contacts, appear as assignees (`getEligibleChannelAssignees()`, also used by channel auto-assign), but editing/deleting the account stays owner-only. `lib/chat-resolver.ts:resolveChatChannel()` lets the WhatsApp chat routes (`/api/whatsapp/chats/[chatId]/...`) serve both channels: a `chatId` may be a `WAChat.id` *or* a `Conversation.id` — new per-chat routes should follow this shape instead of being duplicated under `/api/telegram/`.
- **Webhooks**: `/api/telegram/webhook/[accountId]` (URL identifies the account; `X-Telegram-Bot-Api-Secret-Token` header authenticates, rate-limited) and `/api/meta/webhook/messaging` (Messenger/Instagram — validates `X-Hub-Signature-256` against the account's `appSecret`, same mechanism as the WhatsApp webhook).
- **Bots**: `WABot.waAccountId` XOR `WABot.channelAccountId` (mutually exclusive at the application level — a bot serves exactly one account). The `bot-messages` queue carries both kinds of jobs; `lib/workers/index.ts` routes on payload shape (`conversationId` present ⇒ channel) rather than a flag. Telegram's bot worker (`lib/telegram/bot-worker.ts`) mirrors the WhatsApp one but deliberately lacks: multimodal input, campaign context, and RAG media (textual RAG yes). Messenger/Instagram get AI replies through `lib/meta-messaging/bot-worker.ts`.
- **Media**: `ChannelMessage.mediaUrl` uses the same local-disk scheme under `MEDIA_ROOT`; proxied via `/api/telegram/messages/[messageId]/media` and `/api/instagram/...`-style endpoints with the same auth checks. Messenger/Instagram outbound media is a two-step (upload → `attachment_id` reference, `uploadMetaAttachment()` in `lib/meta-messaging.ts`) — Meta's URL-alternative doesn't apply since our media isn't publicly fetchable.
- **Lead recovery**: `lib/telegram/lead-recovery.ts` — Telegram re-engages silent leads with the account's active bot (no 24h window restriction like WhatsApp's; Telegram allows free-form outbound anytime).
- **Telegram deliberately lacks** (guarded in the UI, not merely absent): campaigns/templates (Meta-specific concepts), lead scoring, chat tags, outbound media, multimodal AI input. Messenger/Instagram share the same limitations plus no campaigns/lead scoring/tags.
- **Comment-to-inbox (roadmap P3-c, Facebook Page only)**: `/api/meta/webhook/messaging` also handles `entry[].changes` with `field: "feed"` (`value.item === "comment"`, `value.verb === "add"`) — a comment on a Page post becomes a normal `Conversation`/`ChannelMessage` (same `Contact` upsert as a DM, keyed by the commenter's PSID in `value.from.id`), tagged `ChannelMessage.isFromComment: true`. `subscribePageToApp()` additionally subscribes to `feed` for `MESSENGER` accounts only (`account-crud.ts`) — **existing accounts created before this shipped need to be reconnected once** to pick up the new subscribed field; there's no backfill. Deliberately scoped to Facebook Page only — Instagram post/reel comments use a different webhook field, left for a future iteration (see `docs/ROADMAP_PANCAKE.md` → "P3-c").
  - **Bots skip comment-origin messages**: `ingestChannelMessage()` never enqueues `bot-messages` when `isFromComment: true` — an autonomous reply would go through the normal Send API, which Meta rejects for a PSID that never opened a real Messenger thread (see next point). Manual replies from a human agent are unaffected.
  - **Private Reply for the first response**: Meta requires a dedicated endpoint (`POST /{comment_id}/private_replies`, `lib/meta-messaging.ts:sendPrivateReplyToComment()`) to message someone who only commented — the normal Send API with their PSID fails without an already-open thread. `sendMetaChannelReply()` (`chats/[chatId]/send/route.ts`) detects this case (`conversation.firstResponseAt === null` + the conversation's most recent INBOUND has `isFromComment: true`) and calls `sendMetaChannelPrivateReply()` instead of `sendMetaChannelText()`, using that message's `externalMessageId` (the Meta `comment_id`) as the recipient. Every reply after the first uses the normal path — Meta treats the conversation as a regular Messenger thread from then on.
  - **UI**: the chat bubble for a comment-origin message shows a small "Desde un comentario" tag (`chat-thread-panel.tsx`) — no other UI change; the conversation looks and behaves like any other Messenger chat otherwise.

### Live chat widget (`Channel.WEBCHAT`, roadmap P3-f)

Fourth generic channel, added 2026-08-06 — an embeddable chat bubble for the client's own website. Structurally different from Telegram/Messenger/Instagram in one key way: those three authenticate inbound webhooks from a real external provider (Meta, Telegram); here **we are the provider** — there's no external platform to trust, so the entire security model is self-issued.

- **Visitor identity** (reworked 2026-09-16, audit M3): the **server** assigns the `visitorId` (`lib/webchat/session-token.ts:generateVisitorId()`, crypto-random) and it becomes the `Conversation.externalId`. It used to be generated by the widget (`Math.random`) and `/session` signed any id the client sent — anyone who knew a visitor's id could read that conversation.
- **Session token**: `base64url(payload).hex(HMAC-SHA256)` signed with `ENCRYPTION_KEY`, carrying `{visitorId, channelAccountId, iat, exp}` (24h). `POST /api/webchat/[accountId]/session` issues a new visitor, or — when the widget sends its stored `renewToken` — the same visitor, accepting an expired token up to `WEBCHAT_RENEW_WINDOW_SECONDS` (30 days); a tampered token gets a brand-new visitor. The widget keeps only the token in `localStorage` and sends it as `Authorization: Bearer` (query/body still accepted for already-open tabs; `readWebchatToken()`), renewing on 401/403. The `Origin` check against `allowedOrigins` only stops *browsers* on other sites — scripts can spoof it — so abuse is bounded by limits: 30 sessions/min and 20 new visitors/h per IP, 20 msgs/min per visitor and 60/min per IP, 200 new conversations/h per account (each can trigger paid bot replies).
- **`ChannelAccount` for WEBCHAT**: `credentials` (same encrypted-JSON field as other channels, `lib/webchat/account.ts:WebchatCredentials`) holds only `{allowedOrigins: string[]}` — no provider secret exists to store. `externalAccountId`/`verifyTokenHash` stay null (no webhook handshake to disambiguate). Account creation (`POST /api/webchat/accounts`) skips the "validate against provider, then connect" two-step Telegram/Messenger do — there's no provider to validate against, so the account is `CONNECTED` immediately.
- **Public routes** (all under `/api/webchat/[accountId]/`, all outside any NextAuth session, all rate-limited): `POST session` (above), `POST/GET messages` (send / poll — same polling pattern as the rest of the app, no websockets; inbound messages reuse `ingestChannelMessage()` exactly like Telegram/Messenger), `GET widget.js` (the embeddable script itself, served as plain vanilla JS with no build step and no framework dependency — it runs inside an arbitrary third-party page we don't control). All three besides `widget.js` require real CORS handling (`lib/webchat/account.ts:corsHeaders()` + explicit `OPTIONS` handlers) since the visitor's browser calls them cross-origin from the client's own domain.
- **MVP scope, deliberately narrow**: text-only — no media upload/rendering in the widget, no interactive buttons, no lead scoring, no AI copilot (`score`/`scorers`/`suggest-reply` routes explicitly reject `WEBCHAT` alongside `MESSENGER`/`INSTAGRAM`). The chat composer disables the attach-media button for a `WEBCHAT` chat (`attachmentsDisabled` in `chat-workspace.tsx`) since the backend would reject media anyway.
- **Bots work, agent sending is a no-op call**: `WABot.channelAccountId` can point at a WEBCHAT account exactly like Telegram — `lib/telegram/bot-worker.ts` is reused as-is (same simple profile: plain text, no service-window restriction) rather than writing a fourth bot-worker. The only real branch point is *sending*: `lib/channel-send.ts:sendChannelReplyText()` and `bot-send-worker.ts:sendChannelChunk()` both special-case `channel === "WEBCHAT"` to skip any outbound API call — there's nothing to call, the `ChannelMessage` row created right after **is** the delivery; the widget picks it up on its next poll. Manual agent replies follow the same shape (`sendWebchatReply()` in `chats/[chatId]/send/route.ts` just persists the row).
- **Widget UX detail that already caused a bug**: the widget must NOT optimistically render the visitor's own outbound message and then also show it again when the next poll brings it back from the server (confirmed) — that duplicated the bubble. Fixed by never rendering optimistically; `sendMessage()` triggers an immediate `poll()` right after the POST resolves instead.
- **UI**: `/webchat/cuentas` (nav "Cuentas Web" under Canales, same EntityList-based CRUD shape as `/telegram/cuentas`) — creating/editing an account shows the copy-paste `<script>` snippet (`app/(dashboard)/webchat/cuentas/_form.tsx`), not a webhook URL + verify token like WhatsApp's flow (there's no provider-side webhook to configure — the snippet itself is the entire integration).
- **Not built yet**: Instagram-style story/comment capture doesn't apply here (no such concept for a website); a visible "typing..." indicator or read receipts back to the visitor; per-account branding (widget color/greeting are hardcoded, teal to match the app's own accent).

## Eventos de dominio, API pública y webhooks (2026-09-25)

Three pieces sharing one scope model. **Admin-only in 3 layers** (card on `/configuracion` only for admin, `/configuracion/api` in both blocked lists, every `/api/configuracion/{api-keys,webhooks,integration-accounts}` handler 403s via `lib/integrations/admin-session.ts:requireAdmin()`).

- **Event bus** (`lib/events/`): `emitDomainEvent(input)` only enqueues on `domain-events` and **never throws** (the fact already happened). Types in `lib/events/types.ts` (`DOMAIN_EVENT_CATALOG` is the public list). Each event carries `account` (`{kind:"whatsapp"}` or `{kind:"channel", channel}`), `contactId`, `chat` and typed `data`. Emitted from: both ingests (`message.received`, `contact.created`, `lead.ad_captured` for CTWA, auto `conversation.assigned`), `chats/[chatId]/{send,assign,status,tags}`, contacts PATCH/tags (through `lib/contacts/side-effects.ts`), appointments POST/PATCH and the bot's AI appointments, `scoreChatWithScorer` (`lead.scored` with `previousLabel`), the leadgen webhook. **New code that changes one of these facts must emit the event** — and for lead status / contact tags call `afterLeadStatusChanged()` / `afterContactTagAdded()` instead of repeating Meta CAPI + sequences + event inline.
- **Integration scope** (`lib/integrations/account-scope.ts`): an `ApiKey`/`WebhookEndpoint` sees what its owner sees **today** (`getUserAccountIds` + `getUserChannelAccountIds`, recomputed each use) intersected with its own `accountIds`/`channelAccountIds` (both empty = no restriction). Keys stop working immediately if the owner stops being admin or is disabled.
- **Public API** (`/api/v1/*`, outside NextAuth — `proxy.ts` excludes `/api`): `Authorization: Bearer sk_live_…`, only the sha256 is stored (`ApiKey.keyHash`), secret shown once. Every handler: `withApiErrors(async (req) => { const ctx = await authenticateApiKey(req, "<scope>"); … })` (lib/api). Errors are `{error:{code,message}}` (`ApiError`); ids outside the scope answer **404, never 403**. Resource lookups go through `lib/api/resources.ts` (`findScopedContact`, `findScopedConversation`). Cursor pagination is keyset `(date, id)`; `/conversations` merges `WAChat`+`Conversation` with the same cursor. 120 req/min per key. `lib/api/openapi.ts` is hand-written — **update it in the same change as any `/api/v1` route**.
- **Outbound sends** (`lib/messaging/outbound.ts:sendOutbound()`): text/buttons/template for any channel, enforces the WhatsApp 24h window (templates exempt), persists the message, emits `message.sent`. Used by the API (and phase 2 automations); the inbox composer keeps its own route because of uploaded media.
- **Webhooks**: fan-out in `lib/webhooks/fanout.ts` (one `WebhookDelivery` per matching endpoint, `@@unique([endpointId,eventId])` makes retries idempotent), delivery in `lib/webhooks/deliver.ts` signed `X-Sunday-Signature: t=<unix>,v1=hex(hmac_sha256(secret, "t.body"))`. 20 consecutive final failures ⇒ endpoint disabled + `INTEGRATION_ERROR` notification. Deliveries are purged after 30 days by the daily `media-cleanup` job.
- **SSRF**: any HTTP to a user-supplied URL goes through `lib/net/safe-fetch.ts` — the IP is checked in the socket `lookup` (no DNS-rebinding window), no redirects, blocks private/loopback/link-local/CGNAT/reserved and IPv4-mapped IPv6. `NODE_ENV=development` additionally allows loopback + RFC1918 (for local receivers), never 169.254/metadata.

## Automatizaciones (motor único, 2026-09-25)

One engine for button chatbots ("flows"), event→action rules and drip follow-ups, in every channel. `/whatsapp/automatizaciones` (nav "Automatizaciones", admin + user; `ejecutivo` blocked in 3 layers — nav, `EXECUTIVE_BLOCKED`, `lib/automations/access.ts:requireAutomationSession()` 403). Chat-level actions (the inbox chip, manual start) are authorized **by chat access** (`lib/automations/chat-access.ts`), so ejecutivos can pause/resume/start from the chat.

- **Graph = tree** (`lib/automations/types.ts`): a step with branches (buttons, list, wait-for-reply, condition, AI classify) must be the **last** of its column and branches never rejoin — so a run's position is just a `nodeId` and "next" is the next sibling. `validate.ts` (pure, used by the editor in the browser too) enforces structure, Meta limits (3 buttons × 20 chars, 10 list rows) and warns when a free-form WhatsApp message would land >24 h after the customer's last message. `publish.ts:validateForPublish()` adds the DB checks (template of THIS account and approved, assignee has access, custom field and scorer exist, `safe-fetch` URL).
- **Versions**: editing touches `Automation.draftGraph`; publishing creates an immutable `AutomationVersion` and runs are pinned to theirs — editing never breaks a run in flight (the old sequences only warned about it).
- **Executor is pure** (`executor.ts`): all effects go through `ExecutorAdapters`. Real runs use `adapters.ts` (Prisma + existing modules: `sendOutbound`, `afterLeadStatusChanged`/`afterContactTagAdded`, auto-assign, `scoreChatWithScorer`, `safe-fetch`); "Probar" uses `simulate.ts` (nothing sent, CRM untouched, AI real); tests use fakes (`__tests__/helpers.ts`). **Add a step type = types.ts + validate.ts + executor.ts + labels.ts + editor form + tests.**
- **Runner** (`runner.ts`): `startRun()` guards inside a Serializable transaction — one live run per (automation, contact), `allowReentry`, **one conversational run per chat**, and max 20 run starts per contact per hour (stops automations that trigger each other). `advanceRun()` takes a row lock (`lockedAt`), executes, persists; a reply that arrives mid-advance bumps `inputSeq` and is processed right after. Send failures: `window_closed` → EXPIRED (or the step's fallback template), upstream → backoff 15/30/60/120 min then FAILED.
- **Entry points**: `dispatch.ts:dispatchInboundMessage()` is called by **both ingests before enqueuing the bot** — a waiting run takes the reply, else keyword > first_message > message_received; if it returns `suppressBot`, the bot doesn't answer. Event triggers (tag added, lead status, appointment completed, score label change, ad lead) come through the `domain-events` worker (`handleDomainEvent`). An agent's manual reply pauses conversational runs in that chat (`PAUSED_BY_AGENT`); `lib/bots/guards.ts` keeps the bot quiet while a conversational run holds the chat and for 24 h after a "Pasar a humano" step.
- **Interactive messages in every channel** (`lib/messaging/outbound.ts`): WhatsApp buttons/list, Telegram inline keyboard (`callback_query` ingested as text + `interactiveReplyId`, `answerCallbackQuery`), Messenger/Instagram quick replies (`quick_reply.payload`), web widget buttons (`interactivePayload` rendered by `widget.js`, tap sends `replyId`). Replies match by id → option text (accent/case-insensitive) → number ("2") → optional AI.
- **AI steps** use the account owner's default provider/model, respect `isMonthlyBudgetExceeded()` and log `AutomationAiUsage` — summed by `getMonthlyAiCost()` and shown in the chat cost badge.
- **Public API**: `POST /api/v1/automations/{id}/runs` (scope `automations:run`) starts a `manual` automation for a contact, with `vars`.
- **Sequences** (`WASequence`) still run side by side until they are converted (phase 3); don't add features to them.

## Meta Ads (feedback loop de calificación de leads)

Closes the loop between CRM lead scoring and ad optimization: when an ads-originated lead changes `leadStatus`, the system reports the change to Meta's **Conversions API** so the algorithm can optimize for quality.

- **`MetaAdsAccount`** (`/meta-ads`, admin-only — credentials are sensitive business config with no `ChannelAccountShare`/`WAAccountShare` equivalent): a Facebook Page + Business config, deliberately separate from `WAAccount` (a Lead Ads page isn't a WhatsApp number — it can feed leads to an existing number via `waAccountId` without being one). Fields: `pageId`, `pageAccessToken`, `appSecret`, `verifyTokenHash`, `datasetId` (Pixel/Dataset id), `capiAccessToken`, `status` (`WaAccountStatus`), `mode` (`TEST`/`LIVE`), `testEventCode`. **Safety**: `lib/meta/conversions.ts` rejects sending an event unless `testEventCode` (TEST mode) or `mode: LIVE` is explicitly confirmed — a bug can't emit events "into the air" that would pollute the ad account.
- **`Contact.leadOrigin`** (`ORGANIC`/`INSTANT_FORM`/`CTWA`, default `ORGANIC`) + `metaLeadId` (Instant Forms) + `ctwaClid`/`adId` (click-to-WhatsApp referral captured in `lib/whatsapp/ingest-message.ts`). `LeadOrigin` decides which payload builder runs (`buildInstantFormPayload` with `action_source: "system_generated"` + `lead_id` vs `buildCtwaPayload` with `action_source: "business_messaging"` + `ctwa_clid`).
- **Webhooks**: `/api/meta/webhook/leadgen` (Instant Forms — creates the `Contact` on the `waAccountId` configured on the `MetaAdsAccount`, first-touch attribution) and `/api/meta/webhook/messaging` (Messenger/Instagram messages). Both validate `X-Hub-Signature-256` via `lib/meta/webhook-signature.ts`.
- **Trigger**: `PATCH /api/whatsapp/contacts/[id]` (the pipeline Kanban drop + contact edit) enqueues `meta-conversions` when `leadStatus` changes on a non-`ORGANIC` contact. `lib/meta/send-conversion.ts:sendLeadConversionEvent(contactId, leadStatus)` is the single business entry point (shared by the automatic trigger and any future manual resend — same pattern as `scoreChatWithScorer()`); `lib/meta/lead-status-mapping.ts:mapLeadStatusToMetaEvent()` decides which statuses get reported and with what `event_name`/`value` (business decision, 2026-08-05: `NEW` isn't reported — it adds no new quality signal over the initial click/form; `CONTACTED`/`QUALIFIED`/`CUSTOMER`/`LOST` are, as `Contact`/`Lead`/`Purchase`/`LeadLost` respectively, no `value`/`currency` yet — occurrence-only). If a Meta Events Manager funnel mapping is configured later with different event names, update the strings in that file to match.
- **`MetaConversionEvent`** logs every send attempt (`@@unique([contactId, leadStatus])`, upsert so a contact passing through the same status twice re-sends; `status`: PENDING/SENT/FAILED + `errorMessage` + `metaEventId` for Meta-side dedup). Queue: `meta-conversions` (concurrency 1).

## CRM & team collaboration

- `Contact` (tags via `Tag`/`ContactTag`, `leadStatus`, notes via `WANote`) is auto-upserted per remote JID inside `ingestInboundMessage()` — one per `(accountId, remoteJid)`, 1:1 with `WAChat` via `WAChat.contactId`. Surfaced through `ContactDrawer` (`app/components/whatsapp/contact-drawer.tsx`) from both chat views and `/whatsapp/contactos`. **Name never regresses**: `ingest-message.ts:isFallbackName()` treats a name equal to the remote JID/phone number as "no real name" — `Contact.name`/`WAChat.name` only get overwritten with a new value if it's a real name or the existing one was itself a fallback, so a previously-learned name can't be clobbered by a later payload where Meta omits `profile.name`. `/whatsapp/contactos` also shows a Teléfono column (always) and a Cuenta column (only when the user has 2+ accounts).
- Chat assignment: `WAChat.assignedToId` restricted to the account owner + `WAAccountShare` grantees (`lib/chat-assignees.ts:getEligibleAssignees()`, the shared candidate pool used everywhere assignment/mentions/auto-assign need "who can touch this account"). Assigning manually triggers no side effect by itself; a `CHAT_MESSAGE` notification fires on the *next* inbound message if the chat is already assigned (or gets auto-assigned, see below).
- `Notification` model + polling bell (`app/components/ui/notification-bell.tsx`, polls `GET /api/whatsapp/notifications` every 25s). Types: `CHAT_MESSAGE`, `CAMPAIGN_COMPLETED`, `CAMPAIGN_FAILED`, `BOT_ERROR`, `BUDGET_EXCEEDED`. No websockets in this app — polling is the established pattern for anything "live."
- Monthly AI budget: `AppSettings.monthlyBudgetUsd` (optional) + `budgetAlertMonth` (guards against re-notifying within the same month). Checked in `bot-worker.ts` after every logged `WABotUsage` row. **All three AI consumers gate on `isMonthlyBudgetExceeded()` before spending**: lead-scoring and lead-recovery skip their tick, and `bot-worker.ts` skips the reply (logs, no `ERROR` status — it's not a bot failure) once the budget is spent.
- **Campaign sends create CRM records**: a successfully delivered campaign recipient now upserts a `Contact`/`WAChat`/`WAMessage` (`direction: OUTBOUND`, `messageType: "template"`) and tags both the contact and chat with `Campaña: <campaign name>` (`lib/workers/campaign-worker.ts`) — so campaign leads show up in `/whatsapp/contactos` and the chat list, not just in `WACampaignRecipient`. A recipient that fails to send leaves no CRM trace (no phantom contact). `WAMessage.body` for this record holds the real rendered template text (`lib/whatsapp/template-variables.ts:renderTemplateText()`, substitutes `{{n}}` the same way `<TemplatePreview>` does for display), and `WAMessage.campaignId` (FK to `WACampaign`) attributes the message so `bot-worker.ts` can inject a one-line "this chat started from campaign X, template Y" system note when the most recent outbound message in the chat came from a campaign — regardless of `bot.memoryType`. A campaign's image/video header is persisted locally **once per campaign** (not re-downloaded per recipient) and each recipient's `WAMessage` points at that copy, so the header renders in the chat via the same `<MediaContent>`/media-proxy path as any other media.
- **Campaign template variables** (`whatsapp/campanas/nueva/page.tsx`): `lib/whatsapp/template-variables.ts:getTemplateVariables(components)` (shared by the UI and `campaign-worker.ts`) inspects a template's raw Meta `components` JSON to detect what needs a value — body `{{n}}` count (per-recipient, `WACampaignRecipient.parameters`), header text/media (campaign-wide, `WACampaign.headerParam` — media headers hold a Meta message-media `id`, uploaded via `/api/whatsapp/media`, not a URL), and a URL button's dynamic suffix (campaign-wide, `WACampaign.buttonParam`). Footer never has variables in Meta's template model. The worker resolves the button's array index from the template's own `BUTTONS` component so the `sub_type: "url"` component always targets the right button.
- **Recipient CSV import** (`lib/whatsapp/parse-csv.ts`) expects a header row (`telefono`/`nombre` recognized by name, any other columns become body parameters in file order) and shows a read-only, paginated (10/page) preview via the shared `<Table>` — imported rows are kept in a separate array from manually-typed rows rather than rendered as hundreds of editable inputs.

### Lead scoring (`WALeadScorerBot` / `WALeadScore`)

Distinct from the AI reply bots (`WABot`): a `WALeadScorerBot` (own `name`/`provider`/`model`/`systemPrompt`, CRUD at `/whatsapp/calificadores`) scores a *conversation transcript* on demand rather than replying to it. `POST /api/whatsapp/chats/[chatId]/score` requires a `scorerId` in the body, loads that scorer's config + the chat's messages, and asks the AI for `{score (0-100), label: "frio"|"tibio"|"caliente", summary, reasons[]}` via a fixed JSON-contract system message appended after the scorer's own system prompt. The result is upserted on `@@unique([chatId, scorerId])` — **a chat can carry one score per scorer**, not a single global score; don't assume `WALeadScore` is 1:1 with `WAChat`. `GET` on the same route returns all scores for the chat (one per scorer that has run so far). `GET /api/whatsapp/chats/[chatId]/scorers` lists the account owner's active scorers for the picker. `LeadScoreBadge` (popover in the chat header) lets the user pick a scorer, re-run it, and flip between scorers' past results.

The actual scoring logic (transcript build, AI call, JSON parse, `WALeadScore` upsert, usage logging) lives in `lib/whatsapp/lead-scoring.ts:scoreChatWithScorer(chatId, scorer)`, shared by both the manual "Calificar" button and the scheduled tick worker below — don't duplicate this logic inline in a route handler.

`/whatsapp/calificadores` has two in-page tabs (client-side `useState`, same idiom as `bots/[id]/page.tsx`): **Calificadores** (CRUD list; hidden entirely for role `user`, see roles) and **Leads calificados** (`GET /api/whatsapp/lead-scores`, all `WALeadScore` rows across the user's accounts) — the latter is the cross-chat view of everything any scorer has produced so far. The Leads tab filters client-side by scorer/label/account/phone/date range, paginates client-side (`<Pagination>`, slice over the filtered array), opens a per-lead detail modal, and exports CSV via a column/scope-picker modal (`lib/csv.ts:toCsv()/downloadCsv()` — reuse these for any new CSV export).

Beyond `{score, label, summary, reasons[]}`, the JSON contract asks for a structured `details` object (buying signals, objections, next steps, product of interest — the 5-phase methodology prompt in `lib/whatsapp/lead-scoring.ts` dictates its shape), persisted as `WALeadScore.details Json?` — a flexible blob on purpose, don't normalize it into columns.

**Scheduled/periodic scoring**: `WALeadScorerBot.scheduleEnabled` + `scheduleIntervalMinutes` (one of `LEAD_SCORER_SCHEDULE_INTERVALS` in `lib/validations.ts` — 15/30/60/180/360/720/1440) + `scheduleAccountIds` (`String[]`, empty = all the owner's accounts) let a scorer re-run itself unattended instead of only via the manual button. A single BullMQ repeatable job (`lead-scoring` queue, `lib/workers/lead-scoring-worker.ts`, cron `*/5 * * * *`, registered in `lib/workers/index.ts`) ticks every 5 minutes — the shortest resolution needed since 15 min is the smallest selectable interval — and for each due scorer (`now - lastRunAt >= scheduleIntervalMinutes`) re-scores up to 15 of its owner's `OPEN`/`PENDING` chats that either have never been scored by it or have new messages since the last score (`WAChat.lastMessageAt > WALeadScore.updatedAt`), then stamps `lastRunAt`. Before running, it checks `isMonthlyBudgetExceeded()` (`lib/ai/budget.ts`) and skips the whole scorer for that tick if the user's monthly AI budget is already spent — unattended runs don't get to blow through a budget the way a human clicking a button implicitly self-limits. The channel-accounts branch explicitly filters `scheduleChannelAccountIds` down to `channel: "TELEGRAM"` before querying `Conversation` — lead scoring is deliberately not extended to Messenger/Instagram yet (same limit `POST .../score` enforces with a 400), so this filter keeps the scheduled tick's data layer consistent with what the manual API allows; don't drop it thinking `getUserChannelAccountIds()` alone is enough, it returns all three channels undifferentiated.
- **Usage/cost tracking**: unlike the original manual-only flow, every scored chat now logs a `WALeadScorerUsage` row (mirrors `WABotUsage` — tokens + `estimatedCost`), and `lib/ai/budget.ts:getMonthlyAiCost()`/`checkBudgetAlert()` sum **both** `WABotUsage` and `WALeadScorerUsage` — the monthly budget and the `BUDGET_EXCEEDED` notification reflect total AI spend, not just reply-bot spend. `lib/estadisticas/get-stats.ts`'s `totalCost`/`totalTokens`/`monthlyCost` were updated the same way. If you add a third kind of AI usage in the future, extend `getMonthlyAiCost()` rather than adding a parallel budget check.

### Lead recovery (`WALeadRecoveryAttempt`)

Autonomous re-engagement of leads that went silent ("en visto"). Config lives **per user** on `AppSettings` (`leadRecoveryEnabled` — default `false`, `leadRecoveryFirstMessageHours`/`leadRecoverySecondMessageHours` (`null` = only 1 attempt), business-hours window `leadRecoveryBusinessHourStart/End` + `leadRecoveryTimezone`), edited from the admin-only `/configuracion/ia` page. The `lead-recovery` queue ticks every 15 min (`lib/workers/lead-recovery-worker.ts:processLeadRecoveryTick()`):

- Per enabled user: skips the whole tick if `isMonthlyBudgetExceeded()` or outside business hours (checked in the user's configured timezone).
- Candidates (WhatsApp): `OPEN`/`PENDING` chats across `getUserAccountIds()` whose **last message is OUTBOUND** and that have at least one INBOUND message ever (a campaign recipient who never replied is not an "abandoned" lead). Bounded per tick: `CANDIDATE_POOL = 200`, `BATCH_SIZE = 20` sends max, **shared across channels** (Telegram candidates consume the same `sentCount` budget).
- Attempt logic: hours of silence measured from the lead's last inbound; `WALeadRecoveryAttempt` rows created *after* that inbound count as attempts (so a lead who replies resets the sequence). Max 2 attempts.
- The message is **generated by the account's active `WABot`** (`lib/whatsapp/lead-recovery.ts:sendRecoveryMessage()` for WhatsApp / `lib/telegram/lead-recovery.ts:sendTelegramRecoveryMessage()` for Telegram / `lib/meta-messaging/lead-recovery.ts:sendMetaChannelRecoveryMessage()` for Messenger and Instagram — all three share the same generator, `lib/ai/recovery.ts:generateRecoveryReply()`, coherent with the conversation, wrapped prompt + `SCOPE_GUARDRAIL`); accounts without an active bot are skipped. `lead-recovery-worker.ts` dispatches to the right sender based on `ChannelAccount.channel` — don't reintroduce a hardcoded call to the Telegram sender for every non-WhatsApp channel account (that shipped as a real bug: Messenger/Instagram credentials have no `botToken`, so the send failed silently and recovery never happened for those two channels until this was fixed).
- **Meta 24h window**: for WhatsApp, only free-text messages inside Meta's 24h customer-service window (from the lead's last inbound) are sent — past 24h it sends nothing (no reactivation template configured yet). Telegram/Messenger/Instagram have no such window and send freely.

This runs unattended and messages real leads — treat `leadRecoveryEnabled` and the hour thresholds as production-sensitive settings; never flip them in the DB while testing without telling the user.

### Appointments/Citas (`WAAppointment`)

Agenda feature added to close a real product gap against social-commerce CRM competitors that sell into service verticals (spas, clinics, schools) via manual call-center scheduling — SundayCRM's version stays inside the "conversational CRM" scope (no telephony/call center itself, just the scheduling + reminder domain hanging off a `Contact`).

- **`WAAppointment`** hangs off `Contact` only (`contactId`, cascade delete) — deliberately **not** duplicated onto `WAChat`/`Conversation`, since `Contact.chat`/`Contact.conversation` already resolve "which thread this is" 1:1; unlike `ChatTag`, which needs its own soft `chatId`/`conversationId` because a tag isn't contact-scoped. Fields: `title`, `notes`, `scheduledAt`, `durationMinutes` (default 30), `status` (`SCHEDULED`/`COMPLETED`/`CANCELLED`/`NO_SHOW`), `source` (`MANUAL`/`AI_BOT` — `AI_BOT` reserved for a not-yet-built phase 2 where the reply bot proposes appointments during a chat, see the roadmap plan), `assignedToId`/`createdById` (both → `User`, two named relations since both FKs point at the same model), `originMessageId` (soft ref, no FK, phase-2 traceability), `reminderMinutesBefore` (default 60), `remindedAt` (one-shot dedup timestamp — not a multi-attempt log like `WALeadRecoveryAttempt`, a reminder only fires once), `cancelReason`.
- **API**: `/api/whatsapp/appointments` is a **flat** resource (`GET`/`POST`), not nested under `/contacts/[id]/appointments` like `WANote` is — unlike notes, the agenda needs a cross-contact view from day one (today's schedule, overdue). `GET` supports `?contactId=`/`?assignedToId=`/`?status=`/`?dateFrom=`/`?dateTo=`/`?upcoming=true`/`?limit=` (default+cap 500, same `TAKE` pattern as `GET /api/whatsapp/lead-scores`). `/api/whatsapp/appointments/[id]` for `GET`/`PATCH`/`DELETE`. Scoping helpers live in `lib/appointments.ts`: `getContactScopeIds()` (the `Contact`-shaped equivalent of `getUserAccountIds()`+`getUserChannelAccountIds()` combined, since a `Contact` can come from either world) and `canAssignToContact()` (checks a candidate `assignedToId` actually has access to the contact's account before letting it be set — reuses `getUserAccountIds`/`getUserChannelAccountIds` in reverse instead of duplicating `lib/chat-assignees.ts`'s eligibility logic). `ejecutivo` is forced to `assignedToId = session.user.id` server-side on every write, and can only read/touch appointments assigned to themself — same defense-in-depth shape as everywhere else. Rescheduling (`scheduledAt` changes via `PATCH`) resets `remindedAt` to `null` so the reminder recalculates against the new time instead of staying silent or firing on the old one. Cancelling is a `PATCH` to `status: CANCELLED` (+ optional `cancelReason`), not a `DELETE` — `DELETE` is reserved for cleaning up accidental entries, kept out of the normal cancel UX so history stays auditable.
- **Reminders**: `appointment-reminders` queue (`lib/workers/appointment-reminder-worker.ts:processAppointmentReminderTick()`, cron `*/5 * * * *`), same bounded-candidate-pool shape as `lead-recovery`/`lead-scoring`. Because `reminderMinutesBefore` varies per row, "due" can't be a single SQL inequality — the query pulls `status: SCHEDULED, remindedAt: null, scheduledAt` within a 24h lookahead window, then filters the exact `scheduledAt - now <= reminderMinutesBefore` condition in JS. Creates a `Notification` (`type: APPOINTMENT_REMINDER`) for `assignedToId ?? createdById` and stamps `remindedAt` — one pass, no retry sequence.
- **UI**: `ContactDrawer` shows a compact "Próxima cita" section (next upcoming appointment + "Agendar cita" button), not an inline scrolling list — no tab primitive was introduced for this, kept deliberately light. `/whatsapp/citas` (`page.tsx` is a thin `Suspense` wrapper, `_view.tsx` is `"use client"` and owns everything — **not** the RSC `page.tsx`+`_view.tsx` split `/ventas` uses; `citas` needs `useSearchParams()` for `?contactId=`/`?id=` deep links from `ContactDrawer`/notification clicks, same reason `app/(auth)/login/page.tsx` wraps in `Suspense`, and is filter/CRUD-heavy like `/whatsapp/contactos`, not drag-drop like `/ventas`) is the primary agenda view: fetches up to 500 appointments once and filters/paginates entirely client-side (same precedent as the "Leads calificados" tab's `GET /api/whatsapp/lead-scores`), grouped by day and rendered with `EntityRow` inside manually-built day sections — not `<EntityList>` itself, since it has no built-in day-group-header mechanism; not a calendar-grid widget either (no such component exists and a filterable list already covers the need). Reachable by all three roles (added to nav, **not** added to `EXECUTIVE_BLOCKED`/`USER_BLOCKED` in `proxy.ts`) — role scoping happens API-side instead (`ejecutivo` forced to their own `assignedToId`). The create/edit modal (`app/components/whatsapp/appointment-form-modal.tsx`) is a shared component used from both surfaces, not colocated under the route, since `ContactDrawer` also needs it — an intentional deviation from the usual `_form.tsx`-colocated convention. Its contact picker (only shown when no contact is already fixed) hits `GET /api/whatsapp/appointments/contacts-search`, a narrow search endpoint deliberately separate from `GET /api/whatsapp/contacts` — that route 403s for role `user` (see "Role guards live in the APIs too" in the gotchas), and scheduling an appointment shouldn't inherit the Contactos-page restriction.
- **Phase 2, not built yet**: the AI reply bot proposing an appointment mid-conversation (`source: AI_BOT`). Deliberately deferred rather than bundled with the MVP — see the roadmap plan for the recommended approach (a structured marker in the model's reply, not real function/tool-calling, since `lib/ai/providers/openrouter.ts` and `google.ts` shape tool-calling differently and no other feature justifies building that infra yet).

### Custom fields (`ContactCustomFieldDefinition` / `ContactCustomFieldValue`)

Roadmap P2 — configurable fields per account (e.g. "Talla preferida", "Fecha de nacimiento") so the CRM can flex into the same service verticals (spas, clinics, schools) `Contact`'s fixed schema doesn't otherwise support, without normalizing new columns onto `Contact` per business.

- **Schema**: `ContactCustomFieldDefinition` — same dual `waAccountId`/`channelAccountId` pattern as `CannedResponse`, `@@unique([waAccountId, key])`/`@@unique([channelAccountId, key])`. `key` is a stable slug (`^[a-z0-9_]+$`) fixed at creation — renaming only ever touches `label`, so a value already saved against a definition can't be orphaned by a display-name edit. `type` (`TEXT`/`NUMBER`/`DATE`/`BOOLEAN`/`SELECT`) + `options String[]` (only meaningful for `SELECT`) decide how the value renders/validates client-side; the stored value itself is always a plain string (`ContactCustomFieldValue.value String? @db.Text`) — casting is the UI's job, not the column's, same reasoning `WALeadScore.details` documents for why some things stay loosely typed. **Deliberately normalized, not a `Json` blob on `Contact`**: definitions need to be listed/ordered/edited/deleted with referential integrity (a deleted definition cascades its values; a `Json` blob per contact would leave orphaned keys across every contact instead).
- **API**: `/api/whatsapp/custom-fields` (`GET`/`POST`, dual `?waAccountId=`/`?channelAccountId=` filters, same shape as `/api/whatsapp/canned-responses`) manages definitions; `/api/whatsapp/custom-fields/[id]` (`PATCH`/`DELETE`) — `PATCH` never accepts `key`. Values live under the contact: `GET /api/whatsapp/contacts/[id]/custom-fields` returns `{definitions, values}` in one call (`values` keyed by `definitionId`) so the UI doesn't have to cross-reference two fetches; `PUT` does a bulk upsert from `{values: {[definitionId]: value}}` — `null`/`""` deletes the row instead of persisting an empty string, and every `definitionId` in the payload is re-validated against the contact's own account before writing (a definition id from another account is silently dropped, not trusted from the client).
- **UI**: managed from `/configuracion` → "Campos personalizados" section (`_campos-personalizados.tsx` + `_campos-personalizados-form.tsx`), an account-scoped `Table` CRUD list — structurally a copy of `_respuestas-rapidas.tsx`/`_respuestas-rapidas-form.tsx` (same account-selector-then-table shape), not admin-gated (mirrors `CannedResponse`: shared with everyone who has access to that account). Values are edited from `ContactDrawer`'s "Campos personalizados" section (only rendered when the contact's account has ≥1 definition) — one dynamic input per definition (`Select` for `SELECT`/`BOOLEAN`, typed `Input` for `TEXT`/`NUMBER`/`DATE`), saved as a single batch via the `PUT` endpoint on a "Guardar campos" button rather than per-keystroke autosave.

### Sequences (automatización lineal, `WASequence`)

Roadmap P3-a — drip campaigns simples: un trigger inscribe un `Contact`, y un tick de BullMQ va mandando cada `WASequenceStep` en orden respetando su `delayMinutes`. Deliberadamente **sin ramas condicionales ni builder visual** (decisión de producto 2026-08-06, ver `docs/ROADMAP_PANCAKE.md` → "P3-a") — a diferencia del builder completo que ofrecen Botcake/respond.io/HubSpot, esta primera versión es una lista ordenada de pasos, punto.

- **Schema**: `WASequence` (dual `waAccountId`/`channelAccountId`, mismo patrón que `CannedResponse` — alcance WhatsApp + Telegram únicamente, ni Messenger ni Instagram: el motor solo sabe mandar por esos dos canales, ver `lib/sequences.ts`) → `WASequenceStep[]` (orden + `delayMinutes` + `message`, texto plano con placeholder `{{nombre}}`) → `WASequenceEnrollment` (una por `(sequenceId, contactId)`, `@@unique` — un contacto pasa por una secuencia como máximo una vez, aunque el trigger vuelva a cumplirse después; simplificación deliberada para no arriesgar espamear). `SequenceTriggerType`: `TAG_ADDED` (`triggerValue` = `Tag.id`), `LEAD_STATUS_CHANGED` (`triggerValue` = valor de `LeadStatus`), `APPOINTMENT_COMPLETED` (`triggerValue` null). `WASequence.exitOnReply` (default `true`) detiene la secuencia si el contacto manda un INBOUND después del último paso mandado (o de inscribirse, si ninguno se mandó aún) — evita seguir con el guion a alguien ya en conversación activa.
- **Motor**: todo vive en `lib/sequences.ts` (no en `lib/whatsapp/`, es cross-canal — mismo criterio que `lib/appointments.ts`/`lib/chat-resolver.ts`). `enrollContactInTrigger(triggerType, triggerValue, contactId)` se llama desde los 3 puntos donde el trigger real ocurre (`POST /api/whatsapp/contacts/[id]/tags`, `PATCH /api/whatsapp/contacts/[id]` en la transición real de `leadStatus`, `PATCH /api/whatsapp/appointments/[id]` en la transición real a `COMPLETED`) — no-opea si el contacto no tiene `chat`/`conversation` todavía (mismo criterio que lead-recovery excluye leads sin ningún inbound: no hay ventana de servicio de Meta que evaluar ni forma segura de mandar un primer mensaje proactivo). `processSequenceTick()` (cola `sequence-tick`, cron `*/5 * * * *`) procesa hasta 200 inscripciones `ACTIVE` vencidas por corrida, cada una en su propio try/catch.
- **Ventana de 24h de Meta**: para WhatsApp (no aplica a Telegram), antes de mandar un paso se reutiliza `lib/whatsapp/lead-recovery.ts:isWithinServiceWindow()`. Sin ningún INBOUND registrado o fuera de la ventana: con `exitOnReply` activo la inscripción pasa a **`EXPIRED`** de inmediato (la ventana solo se reabre si el lead responde, y eso detiene la secuencia — antes quedaba `ACTIVE` para siempre reintentando cada hora); sin `exitOnReply` se reintenta cada 60 min hasta 7 días desde el último paso/inscripción y luego `EXPIRED`. El form de secuencias avisa cuando la cuenta es de WhatsApp y los retrasos acumulados superan 24h.
- **Envíos fallidos** (2026-09-16): `sendAttempts` + `lastError` en la inscripción; backoff 15 → 30 → 60 → 120 min y **`FAILED`** al quinto fallo seguido (`SEQUENCE_MAX_SEND_ATTEMPTS`) — antes se reintentaba cada 5 min para siempre. Tras un envío exitoso la inscripción avanza ANTES de registrar el mensaje, para que un error al guardarlo no provoque un reenvío. El tick procesa por `nextRunAt` ascendente (sin orden, inscripciones que fallaban siempre acaparaban el lote de 200). `GET /api/whatsapp/sequences` devuelve `stoppedEnrollments` (FAILED + EXPIRED) y la lista lo muestra como badge "N sin completar".
- **API**: `/api/whatsapp/sequences` (`GET`/`POST`, recurso plano — igual que `canned-responses`, no nested bajo `/accounts/[id]`, porque la UI lista secuencias de todas las cuentas del usuario a la vez) + `/api/whatsapp/sequences/[id]` (`GET`/`PATCH`/`DELETE`). `PATCH` reemplaza los pasos por completo en vez de diff — advertencia en el código: si la secuencia tiene inscripciones `ACTIVE` en curso, cambiar el número/orden de pasos puede corromper lo que su `currentStep` significa; se recomienda desactivar (`active: false`) antes de editar pasos de una secuencia con inscripciones en curso, sin bloquearlo para mantener esta primera versión simple.
- **UI**: `/whatsapp/secuencias` (nav "Secuencias" en el grupo Automatización, visible admin+user, bloqueada en `EXECUTIVE_BLOCKED`) — `page.tsx` con `EntityList` (mismo patrón que Bots IA: toggle activo/pausado inline + eliminar) y `_form.tsx` (modal estándar, selector de cuenta dual WhatsApp/Telegram igual que `bots/_form.tsx`, selector de trigger condicional, editor dinámico de pasos con agregar/quitar).

### Conversation-level features (distinct from Contact-level)

These mirror equivalent Contact-level concepts but are **separate models** scoped to the `WAChat` itself, not the underlying lead/contact — don't conflate them:

- **`WAChat.status`** (`ChatStatus`: `OPEN`/`PENDING`/`RESOLVED`, default `OPEN`) + `resolvedAt` (set when transitioning to `RESOLVED`, cleared on reopen). `PATCH /api/whatsapp/chats/[chatId]/status`, changed from the chat header. `GET /api/whatsapp/chats` still supports `?status=` (comma-separated), but the inbox no longer renders status tabs — they were removed along with the whole `WAChatNote` internal-notes feature (model, routes, drawer, `@mention` parsing and the `NOTE_MENTION` notification type all deleted for lack of use; `WANote` on Contact remains). Don't re-introduce either without asking.
- **Inbox filters** (`chat-workspace.tsx`): campaign (`?campaignId=`, a relation filter on `WAMessage.campaignId` — not the `Campaña: X` text tag) and lead-reply (`?hasReplied=yes|no`). Each chat row shows a campaign badge (most recent campaign-tagged message) with a hash-derived tone. The `/whatsapp/chat` area renders **full-bleed** — `app-shell.tsx` drops the standard page padding + breadcrumb when `pathname.startsWith("/whatsapp/chat")` (`h-svh`, internal scroll).
- **Per-chat AI cost**: `GET /api/whatsapp/chats/[chatId]/usage` returns the per-interaction list (bot replies + scorer runs — `WABotUsage` + `WALeadScorerUsage` by `waChatId`) with model/tokens/`estimatedCost`; surfaced as a cost badge with breakdown in the chat header. It's per *AI call*, not per message (a humanized reply spans several `WAMessage` chunks from one call).
- **Tags are per account** (since 2026-09-16, audit A3): `Tag.waAccountId` XOR `Tag.channelAccountId`, `@@unique([waAccountId, name])`/`@@unique([channelAccountId, name])` — the catalog used to be global with a unique `name`, so every tenant saw every other tenant's tags (including campaign names via "Campaña: X") and a name used by one company was blocked for all. `lib/tags.ts:resolveTagScope()` resolves the owning account from `waAccountId`/`channelAccountId`/`contactId`/`chatId` with an access check; `GET /api/whatsapp/tags?{waAccountId|channelAccountId|contactId|chatId}=` returns that account's catalog (no params = all accessible accounts), `POST` requires one of those to scope the new tag. Every assignment path checks `tagBelongsTo()` (contact/chat tags, routing rules, sequence triggers) — never accept a bare `tagId` from the client without it. System tags (`Campaña: X`, `Lead Ads: X`) are upserted on `waAccountId_name`. The migration split each existing tag into one copy per account that used it (first account kept the original id) and deleted tags no account used.
- **`ChatTag`** (bridge table, same shape as `ContactTag` but for `WAChat`) uses the same per-account `Tag` catalog. Chat-scoped CRUD at `/api/whatsapp/chats/[chatId]/tags`, UI in `chat-tag-picker.tsx` (popover in the chat header, *not* a drawer).
- **`CannedResponse`** (per-`waAccountId`, `shortcut` + `content`, shared across everyone with access to that account) — managed from the "Respuestas rápidas" section embedded in `/configuracion` (`configuracion/_respuestas-rapidas.tsx` + its `_respuestas-rapidas-form.tsx` modal; the old standalone `/configuracion/respuestas-rapidas` page was folded in during the 2026-07 nav flattening). In the chat composer, typing `/shortcut` filters and shows a dropdown; Tab or click inserts the full `content`.
- **Auto-assignment** (`lib/whatsapp/auto-assign.ts:autoAssignChat()`) — opt-in per account via `WAAccount.autoAssignEnabled` (toggle on the account detail page), off by default so it never silently changes existing manual-assignment behavior. When enabled, an unassigned inbound message is routed to the eligible candidate (`getEligibleAssignees()`) with the fewest `OPEN`/`PENDING` chats, respecting `User.maxOpenChats` (`null` = unlimited; candidates at their cap are skipped). Wired into `ingestInboundMessage()` right before the `CHAT_MESSAGE` notification check.
- **Per-agent metrics**: `WAMessage.senderId` records which human sent a manual outbound reply (set in `chats/[chatId]/send/route.ts`; bot replies leave it `null` — bots are tracked separately via `WABotConversation`). `WAChat.firstResponseAt` is stamped the first time a manual reply is sent on a chat. `lib/estadisticas/get-stats.ts` aggregates these (in JS, not SQL — Prisma can't `AVG()` a date difference) into `agentPerformance` (resolved count, avg minutes to first response, avg minutes to resolution), rendered in `estadisticas/_view.tsx`.

## Design system

All tokens in `app/globals.css` as CSS custom properties. **2026-07 "fresco y cercano" redesign (in progress, step 3)** replaced the previous "Conversación primero" identity: accent is now teal (`#00B88D`), with a violet `--accent-2` (`#6C5CE7`) for secondary accents/icon tones — not a CTA color, don't use it where `--accent` belongs. `success` was moved off teal to green (`#2f8f45`) specifically to stop colliding with the new accent (it used to collide with the old berry-era warning about drifting hues — same rule, new colors). Surfaces are a light, near-white palette (`#fafbfa`/`#ffffff`/`#f2f7f5`). **Single theme for now**: `.light` intentionally duplicates `:root` 1:1 — a dark variant hasn't been designed yet for this palette, so the theme toggle is a no-op until that lands; don't "fix" this into two divergent palettes without checking first.
- **Bubble corner retiring**: `rounded-bubble`/`rounded-bubble-br` (defined as `@utility` in `globals.css`) was the previous redesign's signature corner, whitelisted to `EntityAvatar`, primary `Button`, the active sidebar item, and own chat bubbles. All four have migrated to generous standard corners + soft shadow instead (`EntityAvatar`/`Button` → `rounded-lg`/`rounded-xl`, sidebar active item → `rounded-full` solid pill, chat bubbles → `rounded-2xl` with one corner squared via `rounded-tr-sm`/`rounded-tl-sm`). The utilities stay defined for now — **don't add new usages**; if you find one outside those four call sites it's leftover drift, migrate it the same way.
- **Per-entity hue**: 8 `.hue-0`…`.hue-7` classes set `--entity`/`--entity-bg` (oklch, light/dark aware, hues avoid success-green ~140° and accent-teal ~165-180°), consumed via `bg-entity`/`text-entity`/`bg-entity-bg` utilities. `--entity-bg` mixes against `var(--surface)` (not `transparent`) so the tint stays visible on the new near-white surface. **Only** assign via `HUE_CLASS[hueIndex(id)]`/`hueClassFor(id)` from `app/components/ui/hue.ts` (hash keyed by `accountId` so one WhatsApp number = one color everywhere) — never interpolate `hue-${n}`.

Display/body fonts are Bricolage Grotesque (`--font-display`) / Hanken Grotesk (`--font-body`) — IBM Plex Mono was dropped, there's no separate `--font-data` anymore. `font-mono` is a **temporary bridge** aliased straight to the body font while remaining shared components migrate off it; the actual pattern for figures/phones/dates going forward is the `tabular-nums` utility (for alignment) plus a weight class, not `font-mono` — already done in `KpiStrip`, `dashboard/page.tsx`, `chat-composer.tsx`, `estadisticas/_view.tsx`/`_charts.tsx`, `contactos/page.tsx`. Toast: `const { success, error } = useToast()` → `success("text")`

Three select flavors in `app/components/ui/` — pick by need, don't build a fourth: `select.tsx` (styled native `<select>`, short lists), `multi-select.tsx` (checkbox multi-select), `searchable-select.tsx` (`SearchableSelect`, single-select combobox with a search input that only starts filtering at ≥3 chars — below that the full list stays visible; used for long lists like the template picker in `campanas/nueva`). `pagination.tsx` (`<Pagination currentPage totalPages onPageChange>`) is the shared pager for client-side paginated lists.

## Auth

- `lib/auth.ts` — NextAuth v5 (Credentials + bcrypt, JWT strategy only, **no adapter**)
- Server: `import { auth } from "@/lib/auth"` → `const session = await auth()`
- Client: `useSession()` from `next-auth/react`
- `SystemConfig` (singleton) controls `allowRegistration` toggle for `/register` — **closed by default** since 2026-09-16 (the first admin comes from `/onboarding`, which `app/(auth)/layout.tsx` redirects to when there are no users; everyone else is created by an admin in `/usuarios`). Open registration lets anyone on the internet create a `user`.
- **Session revalidation** (`lib/auth.ts`): the JWT stores `role` + `sessionVersion` at sign-in; every 60s the `jwt` callback re-reads the user (in-memory cache, 60s) — a role change applies to open sessions within a minute, and a user who was deleted, disabled (`User.disabledAt`) or had `sessionVersion` bumped gets `null` → session invalidated. Disabled users can't sign in and are excluded from assignment candidates (`lib/chat-assignees.ts`, Telegram auto-assign). Admins disable/reactivate from `/usuarios` (`PATCH /api/usuarios {userId, disabled}` bumps `sessionVersion` on disable); the first admin can't be disabled or demoted and there must always be at least one **active** admin. Tokens issued before `sessionVersion` existed count as version 0.
- `AUTH_SECRET` = base64 (generated via `openssl rand -base64 32`)

## Gotchas summary

- **`node_modules` belongs to Docker** — `npm install` on the host will fail with `EACCES`. Always install packages inside the container: `docker compose exec app npm install <pkg>`.
- **`npm run build` inside the dev compose fails with `TypeError: Cannot read properties of null (reading 'useContext')` while prerendering** — `docker-compose.override.yml` sets `NODE_ENV=development`, which poisons the production build (dev React mixed into SSR chunks). It is NOT a code bug: run the build check as `docker compose run --rm -e NODE_ENV=production app sh -c "rm -rf .next && npm run build"`, then `docker compose run --rm -u root app sh -c "rm -rf .next"` + `docker compose up -d app` so the dev server doesn't boot on the production `.next`.
- **Campaign visibility is per account, not per creator** — `GET /api/whatsapp/campaigns`, the `[id]` detail/DELETE and `send` all filter by `waAccountId ∈ getUserAccountIds()`; a `WAAccountShare` grantee can create/see/send campaigns on the shared account and the owner sees them too. Don't regress these back to `userId: session.user.id`.
- **Role guards live in the APIs too, not just `proxy.ts`** — all `/api/whatsapp/bots/**` handlers 403 for any non-admin, and `GET /api/whatsapp/contacts` (the list) 403s for role `user` (the `contacts/[id]` detail stays open — the chat's ContactDrawer needs it). `PATCH /api/usuarios` refuses to demote the first-created admin or the last remaining admin.
- **Empty `public/` kills Docker build** — must have `.gitkeep`
- **`tailwindcss` in deps, not devDeps** — production builds need it
- **Shared accounts** — any route resolving a `WAAccount` from user input must check membership via `getUserAccountIds()`, **never** `findFirst({ id, userId: session.user.id })` — the latter 404s ("Cuenta no encontrada") for users who got the account via `WAAccountShare`. This exact bug shipped three times (template sync, template create, campaign create) before being fixed; grep for `userId: session.user.id` next to `wAAccount` when touching account-scoped routes.
- **Knowlege index is async** — use `ragQueue.add()`, never `indexDocument()` directly in HTTP handlers
- **RAG chunk IDs** — use `crypto.randomUUID()`, not `Date.now()`
- **Template creation** — `wabaId` must exist on the account; templates require Meta review
- **Campaign templates** — API must validate `status: "APPROVED"` in addition to existence
- **Embeddings** — dimension is 768, not 1536 (changed from original schema)
- **Rate limiting** — add `rateLimit()` to any new auth-sensitive endpoint
- **Catch blocks** — use `toastError()` not empty `{}` in client code
- **`cn()`** — simple join, no tailwind-merge (avoids Docker dep issues)
- **`login` page** — uses `Suspense` boundary for `useSearchParams("callbackUrl")`
- **Startup script** — `scripts/startup.sh` → `scripts/db-migrate.sh` (`migrate deploy`, see "Migrations"). Schema changes go through `sh scripts/new-migration.sh <nombre>`; never `db push` / `migrate dev`.
- **Dev container needs a restart after a migration** — the running `npm run dev` process keeps the pre-regeneration Prisma Client in memory; `npx prisma generate` writes new files to `node_modules` but the live process won't pick them up without `docker compose restart app` (or a full `down -v && up --build`). Queries against newly-added models/fields will 500 until restarted.
- **Worker code doesn't hot-reload in dev** — `instrumentation.ts` starts the BullMQ workers once per process; HMR swaps route modules but the running workers keep the old closures. After editing anything a worker executes (`lib/workers/**`, `lib/bots/**`, `lib/sequences.ts`, bot workers, ingest-triggered code run inside jobs), restart the app container before testing, or you'll be verifying the previous code.
- **`docker compose restart` does NOT re-read `.env`** — it only restarts the process inside the *existing* container, keeping whatever environment was fixed at the last `up`. Editing `.env` (or a compose file's `environment:`) needs `docker compose up -d <service>` (recreates the container) before the new value takes effect — `restart` alone will silently keep serving the old value indefinitely. Cost real time once: `NEXT_PUBLIC_APP_URL` stayed stale through several `restart`s while debugging the webchat widget (roadmap P3-f) generating URLs with the wrong port.
- **`WABot.status` vs `isActive`** — two separate gates. `ingestInboundMessage()`'s bot lookup requires *both* `isActive: true` and `status: "ACTIVE"`. Any unhandled error in `processBotMessageJob()` sets `status: "ERROR"` (and notifies) — toggling `isActive` back on via `POST /api/whatsapp/bots/[id]/toggle` is what resets `status` back to `"ACTIVE"`; the bot won't recover just by looking "Active" in a stale UI state. The `/test` endpoint bypasses both fields entirely, so it can succeed while the real message pipeline stays silently dead.
- **`WABot.waAccountId` is nullable** — a bot can be created and exercised via its `/test` ("Probar") tab without a WhatsApp account attached; it just never gets picked up by the real inbound pipeline (which filters by account) until one is assigned.
- **`WALeadScore` is keyed by `(chatId, scorerId)`, not just `chatId`** — a chat can carry scores from multiple `WALeadScorerBot`s at once; `findUnique({where:{chatId}})` no longer works, use the composite key.
- **`pdf-parse` must be imported as `pdf-parse/lib/pdf-parse.js`** (the inner module), never the package root — the root `index.js` has a top-level debug block gated on `!module.parent` that misfires under ESM dynamic import and crashes trying to read a bundled test fixture. See `lib/whatsapp/extract-document-text.ts`.
- **`leadRecoveryEnabled` sends real WhatsApp messages unattended** — the `lead-recovery` tick fires every 15 min regardless of app restarts. Never enable it (or shrink its hour thresholds) in a dev DB pointing at real accounts without the user's explicit OK.
- **`MEDIA_RETENTION_DAYS`** (default 90) drives the daily `media-cleanup` queue job that deletes old `WAMessage` media files — set to `0` (or leave unset with a non-positive value) to disable purging.
- **pgvector IVFFlat index** — see "pgvector" under Database; don't re-add the `CREATE INDEX` to `docker/init.sql`, it will silently no-op there.
- **Never put `<Button>` inside `<Link>`** — renders invalid HTML (`<button>` inside `<a>`). Instead: `<Button onClick={() => router.push("/path")}>` or use a plain `<a>` styled as a button.
- **`/api/whatsapp/chats` has two response shapes** — a flat array (legacy, when called with no `page` query param — no in-app consumer left since the overviews became RSC/Prisma-direct, but the shape survives for compatibility) vs. `{items, total, page, pageSize}` (when `page` is present — how `chat-workspace.tsx` calls it). Check which shape a new consumer needs before adding a call.
- **Playwright browser not installed in this environment** — `mcp__plugin_playwright_playwright__*` tools fail with "Chromium distribution 'chrome' is not found" until `npx playwright install chrome` is run; don't assume visual/browser verification is available without checking first. **However**, the plain `mcp__playwright__*` / `mcp__playwright-auth__*` tools (no `plugin_` prefix) work fine and were used successfully this session for real browser verification (login, click-through, file upload, screenshots) — check which namespace is actually available before assuming browser testing is off the table.
