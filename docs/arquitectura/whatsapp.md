# WhatsApp: Cloud API, plantillas, webhook, media, llamadas y coexistencia

> Detalle técnico movido desde `AGENTS.md` (2026-11-01). Las reglas esenciales siguen en [`AGENTS.md`](../../AGENTS.md) y [`CLAUDE.md`](../../CLAUDE.md); aquí está el detalle completo. Mantén este archivo al día en el mismo cambio que el código.

### Creating templates for Meta
`lib/whatsapp/templates.ts` — `createTemplate(wabaId, accessToken, input)` calls `POST /{waba_id}/message_templates`. Constructs the payload from Zod-validated input. API route at `app/api/whatsapp/templates/create/route.ts`.

- **Media headers require the Resumable Upload API, not a URL.** A template with an IMAGE/VIDEO/DOCUMENT header needs `example.header_handle` — a handle string obtained via Meta's separate Resumable Upload API (`POST /{app-id}/uploads` → `POST /{upload-session-id}` with the raw bytes), implemented in `lib/whatsapp/resumable-upload.ts:uploadTemplateHeaderMedia()`. This is a **different** endpoint/credential shape than `lib/whatsapp.ts:uploadMedia()` (the `/{phone-number-id}/media` endpoint used for sending messages and campaign header media by `id` — see below) — a message-media ID is not a valid `header_handle` and vice versa. `POST /api/whatsapp/templates/upload-media` wraps this for the UI; requires `WAAccount.appId` to be set (see "Multiple numbers, each on its own Meta App"), otherwise returns a clear 400 telling the user to set it.
- `whatsapp/plantillas/_form.tsx` uploads the header file directly (`headerExampleHandle` state, not a pasted URL) and renders a live preview via the shared `<TemplatePreview>` component (`app/components/whatsapp/template-preview.tsx`) — the same component used in `campanas/nueva/page.tsx`, so the "what the recipient will see" preview looks identical whether you're creating the template or launching a campaign with it.
- **Template metrics**: `lib/whatsapp/template-analytics.ts` pulls Meta's `template_analytics` (sent/delivered/read/clicked per UTC day) via a field expansion on the WABA node; exposed at `GET /api/whatsapp/templates/[id]/analytics` and rendered by `template-metrics-modal.tsx` from the Plantillas list.

## WhatsApp Business Cloud API

Single channel today — `WAAccount.channel` is an enum (`WAChannel`) kept for future extensibility but only has one value, `META_CLOUD`. The `BAILEYS` channel (unofficial WhatsApp Web protocol, used for dev/testing without a public webhook URL) was removed: `lib/whatsapp-baileys/`, its API routes, and the `WABaileysSession` model are gone. `phoneNumberId`/`accessToken`/`wabaId`/`verifyTokenHash`/`appSecret` stay nullable on `WAAccount` because they're filled in during the account setup wizard, not because of a second channel.

- Outbound sends always go through `lib/whatsapp/send.ts:sendWhatsAppMessage(account, params)` (decrypts the token, delegates to `lib/whatsapp.ts:sendMessage()`) — keep using this wrapper from routes/workers rather than calling `sendMessage()` directly, so token decryption stays in one place.
- Template creation and bulk campaigns require `wabaId` + `accessToken` on the account (checked via `account.channel !== "META_CLOUD" || !account.wabaId || !account.accessToken` in `templates/route.ts`, `templates/create/route.ts`, `campaign-worker.ts` — the channel check is a no-op today but keeps the guard shape if a second channel ever comes back).
- **Nombre para mostrar en revisión** (`name_status` ≠ `APPROVED`, p. ej. `PENDING_REVIEW`): el número queda con `health_status.can_send_message = LIMITED` y Meta es **inconsistente**: el 2026-11-01 entregó respuestas del bot a las 03:43 y por la tarde rechazó textos normales, sin cita, con 131037 ("needs display name approval before message can be sent"). Citar (`context.message_id`) falla siempre. Por eso la bandeja **no bloquea** el compositor (bloquearlo impediría los envíos que Meta sí deja pasar): desactiva citar y reaccionar, muestra un aviso de advertencia (`GET /api/whatsapp/accounts/[id]/display-name`, caché en `lib/whatsapp/display-name.ts`) y, si Meta rechaza, `/send` responde 422 con el texto de `send-errors.ts`. La única solución real es que Meta apruebe el nombre.
- **`WAAccount.appId`** — Meta App ID, distinct from `wabaId`. Only needed for the Resumable Upload API used when creating a template with a media (IMAGE/VIDEO/DOCUMENT) header — see `lib/whatsapp/resumable-upload.ts` and `POST /api/whatsapp/templates/upload-media`. Nullable/optional; accounts that only ever use text-header or headerless templates don't need it.

### Multiple numbers, each on its own Meta App

Every `WAAccount` is fully self-contained — `phoneNumberId`, `wabaId`, `accessToken`, `appSecret`, `verifyTokenHash`, `appId` — and every Graph API call site resolves these from the specific account row, never from a shared/global credential. There's no `META_APP_ID`-style env var and no assumption anywhere that all connected numbers belong to the same Meta App. Practical implications:

- When connecting a second (or Nth) number under a **different** Meta App, use that App's own App ID/App Secret/access token in "Agregar número" — don't reuse another account's values.
- All accounts share the same webhook URL (`/api/whatsapp/webhook`) — the system disambiguates inbound payloads by `phone_number_id` and the GET verification handshake by `verify_token` (both looked up per-account, see "Webhook" above), so multiple Meta Apps can point their WhatsApp product webhook config at the same URL without conflict.
- Manual steps on Meta's side that this system does **not** automate: in the new Meta App, set the WhatsApp product webhook to our URL + that account's generated verify token, and confirm the WABA is subscribed to that App's webhook (`POST /{waba-id}/subscribed_apps` — usually already done when the number was configured in Meta Business Manager, but worth checking first if inbound messages aren't arriving).

### Llamadas de WhatsApp (Calling API, 2026-10-27)

`WAAccount.callingEnabled` (switch on `whatsapp/cuentas/[id]`, `POST /api/whatsapp/accounts/[id]/calling` → `setCallingEnabled()`) shows the phone button in the inbox; the Meta App's webhook must also include the `calls` field (not automated). **Cloud API only**: a coexistence number keeps answering on the phone and `handleCallsWebhook()` ignores its events. Code in `lib/whatsapp/calling/`:

- `meta.ts`: `getCallPermission` / `connectCall` (media `pre_accept`/`accept`/`reject`/`terminate`), `setCallingEnabled`, `CallingError` with `metaCode` (138006 = the customer hasn't authorized calls; the UI offers to send the permission request).
- `access.ts`: per-account authorization (`getUserAccountIds`) plus SDP/digit helpers.
- `events.ts` (pure, unit-tested): maps Meta's `calls` payload to `ParsedCall`/`ParsedStatus`/`ParsedCallArtifact`, and builds the line the call leaves in the thread (`Llamada · 2 min 13 s`, `Llamada perdida`, `No contestaron`…). `formatCallTranscript()` turns Meta's JSON into `Cliente: … / Nosotros: …` lines.
- `ingest.ts`: creates/updates `WACall`, links contact+chat through `jidCandidates()` (Mexican 52/521), and stores the recording (`recordingPath` under `MEDIA_ROOT`) and the transcript (`WACall.transcript`).

UI: `chat-conversation-header.tsx` (phone button) + `call-dock.tsx` — browser WebRTC (Google STUN, 2 s polling on `GET /api/whatsapp/calls`), global incoming ring, microphone permission and rejection when the account hasn't authorized calls. Routes: `GET/POST /api/whatsapp/calls`, `GET /api/whatsapp/calls/[id]`, `POST /api/whatsapp/calls/[id]/signal`, `POST /api/whatsapp/calls/permission`. Outgoing calls are billed by Meta; the recording/transcription notice is shown when answering or dialing.

## Webhook

`POST /api/whatsapp/webhook` handles Meta webhook. Key behaviors:
- Validates `X-Hub-Signature-256` on every payload and **discards it if the HMAC doesn't match — including when the matched account has no `appSecret`** (the signature can never validate without one). That's why `appSecret` is **required** since 2026-09-16 (`waAccountSchema`/`metaAdsAccountSchema`; the update schemas allow replacing it but never clearing it). Before that the form labeled it "(opcional)" while the webhook silently dropped every message and status for such accounts (audit `docs/AUDIT_2026-09-16.md` → A1). Accounts created before the change may still lack it: `GET /api/whatsapp/accounts[/id]` and `GET /api/meta/accounts[/id]` expose a `hasAppSecret` boolean (never the secret), the lists show a "Sin App Secret" badge, and `whatsapp/cuentas/[id]` shows a danger banner plus an "App Secret" row to add/replace it. The webhook now logs a warning (`sin App Secret` / `Firma inválida`) instead of dropping silently.
- Per-message logic (Contact upsert, chat upsert, `WAMessage` create, notification, bot enqueue, media-download enqueue, auto-assignment) lives in `lib/whatsapp/ingest-message.ts:ingestInboundMessage()`. The webhook route itself just parses Meta's payload shape and calls it per message. `ingestInboundMessage()` returns `{messageId, chatId} | null` (null = deduplicated by wamid).
- **Structured content** (2026-11-04): `lib/whatsapp/message-content.ts:structuredContentOf()` turns what doesn't fit `body`/`caption`/media into `WAMessage.content` (location coords, shared contacts without the vCard, order items, `system`, `errors`, media `sha256`/`voice`/`animated`, `context.forwarded`/`frequently_forwarded`/`referred_product`, `context.from`). `getMessageBody()` writes a readable line for location/contacts/order ("📍 …", "👤 …", "🛒 Pedido …") instead of `[type]` — it's what the chat preview, notifications, bots and automations read. Coexistence echoes/history go through the same functions. Real payloads: `docs/META_JSON_CUENTAS_WA_2026-11-04.md` §7.
- **`user_id` / `from_user_id`** (Meta's per-business id for WhatsApp usernames) is stored in `Contact.metaUserId`. If a message arrives **without `from`**, the sender is the contact with that `metaUserId`, else the `user_id` itself becomes the `remoteJid` (the message is kept; before, a missing `from` broke the insert and Meta retried forever).
- Statuses store Meta's `pricing` and its event time (`deliveredAt`/`readAt` on `WAMessage`; `sentAt`/`deliveredAt`/`readAt` on campaign recipients and lead-sheet rows), not the webhook arrival time, and emit `message.status_changed` once per real advance.
- Maps all 4 Meta statuses to `WACampaignRecipient`: `sent → SENT`, `delivered → DELIVERED`, `read → READ`, `failed → FAILED`.
- Detects groups: `remoteJid.includes("@g.us")` → `isGroup = true`.
- For inbound media with a Meta `mediaId` and no local path yet, the webhook enqueues a `media-download` job (see Redis queues).
- **Subscribed webhook fields beyond `messages`**: `phone_number_quality_update`, `account_update`, `user_preferences` (configure these in each Meta App's WhatsApp product webhook alongside `messages`/`message_template_status_update` — `message_template_status_update` itself isn't consumed by the webhook, template status is instead refreshed by polling in `GET /api/whatsapp/templates`, see "Creating templates for Meta"). Any other field arrives at the same URL and is silently ignored (`change.field` doesn't match any handled branch).
  - `phone_number_quality_update` and `account_update` are **not** per-message payloads — they carry no `metadata.phone_number_id`, only a phone number string (`display_phone_number` / `phone_number`) and the WABA id (`entry.id`). The account is resolved via `resolveAccountByWabaAndPhone()`: if exactly one `WAAccount` matches `wabaId`, it's used directly; if several accounts share that WABA, the reported phone number (digit-normalized) disambiguates. If neither is possible, the event is logged and dropped rather than guessed.
  - `phone_number_quality_update` updates `WAAccount.qualityRating`/`messagingTier`/`qualityUpdatedAt` (shown on the account detail page) and fires an `ACCOUNT_STATUS` notification only on a negative signal (rating/event matching `flag|downgrade|red|yellow`) — upgrades don't notify, only the badge updates.
  - `account_update` flips `WAAccount.status` to `ERROR` (with `errorMessage`) when the event or `ban_info` indicates a ban/restriction (`ban|disable|restrict|flag` in the event name); any other event still fires an informational `ACCOUNT_STATUS` notification without touching `status`.
  - `user_preferences` **is** per-number (carries `metadata.phone_number_id` like `messages`) and reports a lead opting out/in of marketing messages via WhatsApp's native mechanism (`category: "marketing_messages"`, `value: "stop"|"resume"`). Sets `Contact.optedOutMarketing`/`optedOutAt`. `campaign-worker.ts` excludes opted-out contacts from every future campaign send (marks the recipient `FAILED` with an explanatory `errorMessage` instead of calling Meta) — this doesn't affect manual/bot replies in an already-open chat, only campaign broadcast sends.

## Media handling

WhatsApp media is **binary-byte persisted locally on disk** (not just Meta URL references), so chat UI and bot vision can stream/read it without depending on Meta's short-lived (≈minutes) download URLs.

- **Storage**: `lib/whatsapp/media-store.ts` — `saveMediaFromMeta(accountId, mediaId, encryptedAccessToken)` (Meta fetch), `saveMediaFromBuffer(accountId, buffer, mimeType)` (persists a buffer already in memory — used for outbound Meta media uploads), `mediaReadStream(relativePath)` (fs stream), `resolveAbsolutePath(relativePath)` (with `..` traversal guard), `mediaEndpointFor(messageId)` (returns the proxy URL the UI must use). The pure helpers (`mediaEndpointFor`, `is*Mime`, `mimeTypeToExtension`) actually live in `lib/whatsapp/media-shared.ts` — a client-safe module with no `fs` imports that `chat-workspace.tsx` imports directly (importing `media-store.ts` from a client component would break the bundle); `media-store.ts` re-exports them for server consumers.
- **Path scheme**: `mediaUrl` stored on `WAMessage` is a path *relative* to `MEDIA_ROOT` (e.g. `<accountId>/<uuid>.<ext>`). All helpers accept/return relative paths; resolve to absolute only at the boundary.
- **Proxied serving**: `GET /api/whatsapp/messages/[messageId]/media` looks up the `WAMessage`, verifies `chat.accountId ∈ getUserAccountIds(session.user.id)`, streams bytes with `Content-Type: mimeType` and `Content-Disposition` (inline for image/audio/video, attachment for documents). Auth check is mandatory — without it any authenticated user could fetch any media by `messageId`.
- **Outbound upload (Meta only)**: `POST /api/whatsapp/media` accepts multipart `file` + `accountId`, validates ownership + that the account is `META_CLOUD`, calls `uploadMedia(phoneNumberId, accessToken, file, name, mime)` (`lib/whatsapp.ts`, `POST /{phone_number_id}/media` Graph endpoint) which returns a Meta `mediaId`, then also persists a local copy for the outbound history. Rate-limited via `rateLimit()`. Returns `{ mediaId, mimeType, filename, localMediaPath, bytesSize }` to be passed to the send route as-is.
- **Chat composer** (`whatsapp/chat/[accountId]/[chatId]/page.tsx`) has a clip 📎 button (`Paperclip` icon, accent-color, left of the text input) that opens a hidden `<input type="file">` accepting `image/*,audio/*,video/*,application/pdf,text/plain`, max 20MB. Caption goes in the text input. The send flow is: upload → `/api/whatsapp/chats/[chatId]/send` with `{type, mediaId, mimeType, filename, localMediaPath, bytesSize, caption}`.
- **UI rendering**: `MessageBubble` switches on `messageType` (`image`/`audio`/`video`/`document`/`sticker`) and renders the appropriate tag pointing at `/api/whatsapp/messages/[id]/media`. While `mediaUrl` is null (async download still queued), shows a placeholder (`[imagen recibida]` etc.) — the 5s polling in the chat page picks up the populated row once the worker finishes.
- **Bot media input**: `lib/workers/bot-worker.ts:buildUserContent()` reads the inbound media's local bytes from disk → base64 data-URI part. Images → `image_url` (both providers); audio → `audio_url` (**Gemini-only** — on OpenCode the bot falls back to a text label); documents → text extracted via `extract-document-text.ts` (PDF/`text/*`, provider-agnostic; other MIME types fall back to a label with the filename). Media in history turns is NOT forwarded (text-only) to bound token cost. `bot-worker` re-checks Prisma for `mediaUrl` if the enqueue payload's `localMediaPath` is empty (situation: bot job fired before `media-download` worker finished).

## WhatsApp: Embedded Signup and coexistence (since 2026-10-03)

Two ways to connect a number, both ending in a `WAAccount`:

- **`connectionType = MANUAL`** (the old way, now "Conexión manual"): the customer pastes credentials of **their own** Meta app (`appSecret` per account).
- **`connectionType = EMBEDDED_SIGNUP`**: one-click "Conectar WhatsApp" on the **platform's** Meta app (Colibly, Tech Provider). No customer secrets: `PlatformSettings.metaAppId/metaAppSecret/metaEmbeddedSignupConfigId/metaWebhookVerifyToken` (edited in `/plataforma` → Configuración; `lib/meta/platform-app.ts`). `WAAccount.appSecret` stays null; the UI shows "La gestiona Colibly" and `hasAppSecret` is derived (`connectionType === EMBEDDED_SIGNUP || !!appSecret`) — never treat a null `appSecret` as "missing" for these accounts.

**Webhook** (`/api/whatsapp/webhook`, one URL for all): `validateWhatsAppWebhookSignature()` picks the secret by `connectionType` (platform secret vs. the account's). The GET handshake accepts the platform verify token first, then the per-account hashes. Never validate a payload for an `EMBEDDED_SIGNUP` account with an account secret or vice versa (tested).

**Signup flow**: `_conectar-whatsapp.tsx` (FB SDK + `FB.login` with `config_id`, `featureType: "whatsapp_business_app_onboarding"` for coexistence, `sessionInfoVersion: "3"`; `postMessage` events parsed by `lib/whatsapp/embedded-signup/session.ts` — only from `https://*.facebook.com`) → `POST /api/whatsapp/embedded-signup/complete` → `completeEmbeddedSignup()` (code→token, **verify the phone belongs to the WABA with the customer's token**, subscribe the app to the WABA, register the number with a random 6-digit PIN **only when not coexistence**, create the account). Meta, not the browser, decides if it is coexistence (`is_on_biz_app`). The coexistence event carries only `waba_id`; the number is resolved server-side. Gates identical to the manual create (verified email, channel plan limit, rate limit, role ≠ ejecutivo, organization scope) plus the per-organization flag `Organization.whatsappCoexistenceEnabled` (**on by default since 2026-10-19** — schema default + `createOrganizationWithOwner()`; migration `*_coexistence_default_on` changed only the default, older orgs keep their value; the operator can turn it off per org in `/plataforma` → organization detail). The dialog needs `frame-src` for facebook.com in the CSP (`next.config.ts`).

**Coexistence data** (`lib/whatsapp/coexistence/`): `smb_message_echoes`, `history` and `smb_app_state_sync` are handled by `webhook.ts`; payloads are normalized by pure functions (`normalize.ts`), history/contacts batches are queued (a single webhook can hold thousands of messages — never process them inside the request), and ingestion is **silent** (`ingest.ts`): no notifications, bot, automations, domain events, auto-assign or unread counts. Messages carry `WAMessage.origin` (`API` | `BUSINESS_APP_ECHO` | `HISTORY`). **An echo counts as human takeover for the bot** (`lib/bots/guards.ts`); imported history does not. Mexican numbers appear as `52…` or `521…`: always look chats/contacts up with `jidCandidates()`. Meta allows each `smb_app_data` request (contacts, history) **once per connection** and only within **24 h** of onboarding: `runCoexistenceSync()` saves each step right after it is accepted and must stay idempotent; `WAAccount.syncStatus/syncProgress/syncDeadlineAt` track it and `processCoexistenceTick()` expires or retries. Contact removals from the phone never delete CRM contacts. Imported contacts are not blocked by the plan's contact limit (the billing tick already warns).

**Stickers and edits (2026-11-02)**: an inbound `sticker` keeps `sticker.id`/`mime_type` through `getMediaInfo()` so the media worker downloads it and the inbox draws it (before, it had no `mediaId`, `hasMedia` was false and the bubble showed the literal `[sticker]`; stickers received before this change stay that way — Meta's media id was never stored). Meta sends an edit as a separate `type: "edit"` message (coexistence only, within 15 min): `parseMessageEdit()` reads `edit.original_message_id` plus the new body/caption, and both the `messages` webhook and `ingestBusinessAppMessages()` (echoes, `NormalizedBusinessMessage.editOf`) update the original `WAMessage` instead of storing a `[edit]` message. There is no "edited" marker yet (no schema field).

**Lifecycle**: `account_update` `PARTNER_REMOVED` → `DISCONNECTED` (+`disconnectedReason`), `ACCOUNT_OFFBOARDED` → `ERROR`, `ACCOUNT_RECONNECTED` → `CONNECTED` (`lifecycle.ts`). The business token may expire (`tokenExpiresAt`, Meta's docs do not specify renewal): the tick warns 10 days ahead and puts the account in `ERROR` on expiry; the remedy is reconnecting.

**Meta callbacks** (public, authenticated only by `signed_request` HMAC with the platform App Secret, `lib/meta/signed-request.ts`): `POST /api/meta/deauthorize` disconnects the user's accounts; `POST /api/meta/data-deletion` deletes the user's `EMBEDDED_SIGNUP` accounts (cascade + media) and records a `MetaDataDeletionRequest` shown at the public `/eliminacion-de-datos/[code]`. If the `user_id` matches accounts in **more than one organization** nothing is deleted and the request stays `MANUAL_REVIEW`. The mapping relies on `WAAccount.metaUserId` (from `debug_token` at signup) — verify on the first real connection that it equals the `user_id` Meta later sends.

**Graph versions**: new code uses `lib/meta/graph.ts` (`GRAPH_API_VERSION`); older clients are still pinned to `v21.0` on purpose. In development `META_GRAPH_ORIGIN` points the new code at a simulated Meta (ignored in production). Dev stack and end-to-end scripts: `dev/coexistencia/README.md` (run migrations for this feature only in that isolated stack).
