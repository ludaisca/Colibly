# Bandeja: funciones por conversación, operación, timeline, reportes, CSAT y macros

> Detalle técnico movido desde `AGENTS.md` (2026-11-01). Las reglas esenciales siguen en [`AGENTS.md`](../../AGENTS.md) y [`CLAUDE.md`](../../CLAUDE.md); aquí está el detalle completo. Mantén este archivo al día en el mismo cambio que el código.

### Conversation-level features (distinct from Contact-level)

These mirror equivalent Contact-level concepts but are **separate models** scoped to the `WAChat` itself, not the underlying lead/contact — don't conflate them:

- **`WAChat.status`** (`ChatStatus`: `OPEN`/`PENDING`/`RESOLVED`, default `OPEN`) + `resolvedAt` (set when transitioning to `RESOLVED`, cleared on reopen). `PATCH /api/whatsapp/chats/[chatId]/status`, changed from the chat header. `GET /api/whatsapp/chats` still supports `?status=` (comma-separated), but the inbox no longer renders status tabs — they were removed along with the whole `WAChatNote` internal-notes feature (model, routes, drawer, `@mention` parsing and the `NOTE_MENTION` notification type all deleted for lack of use; `WANote` on Contact remains). Don't re-introduce either without asking.
- **Inbox filters** (`chat-workspace.tsx`): campaign (`?campaignId=`, a relation filter on `WAMessage.campaignId` — not the `Campaña: X` text tag) and lead-reply (`?hasReplied=yes|no`). Each chat row shows a campaign badge (most recent campaign-tagged message) with a hash-derived tone. The `/whatsapp/chat` area renders **full-bleed** — `app-shell.tsx` drops the standard page padding + breadcrumb when `pathname.startsWith("/whatsapp/chat")` (`h-svh`, internal scroll).
- **Per-chat AI cost**: `GET /api/whatsapp/chats/[chatId]/usage` returns the per-interaction list (bot replies + scorer runs — `WABotUsage` + `WALeadScorerUsage` by `waChatId`) with model/tokens/`estimatedCost`; surfaced as a cost badge with breakdown in the chat header. It's per *AI call*, not per message (a humanized reply spans several `WAMessage` chunks from one call).
- **Tags are per account** (since 2026-09-16, audit A3): `Tag.waAccountId` XOR `Tag.channelAccountId`, `@@unique([waAccountId, name])`/`@@unique([channelAccountId, name])` — the catalog used to be global with a unique `name`, so every tenant saw every other tenant's tags (including campaign names via "Campaña: X") and a name used by one company was blocked for all. `lib/tags.ts:resolveTagScope()` resolves the owning account from `waAccountId`/`channelAccountId`/`contactId`/`chatId` with an access check; `GET /api/whatsapp/tags?{waAccountId|channelAccountId|contactId|chatId}=` returns that account's catalog (no params = all accessible accounts), `POST` requires one of those to scope the new tag. Every assignment path checks `tagBelongsTo()` (contact/chat tags, routing rules, sequence triggers) — never accept a bare `tagId` from the client without it. System tags (`Campaña: X`, `Lead Ads: X`) are upserted on `waAccountId_name`. The migration split each existing tag into one copy per account that used it (first account kept the original id) and deleted tags no account used.
- **`ChatTag`** (bridge table, same shape as `ContactTag` but for `WAChat`) uses the same per-account `Tag` catalog. Chat-scoped CRUD at `/api/whatsapp/chats/[chatId]/tags`, UI in `chat-tag-picker.tsx` (popover in the chat header, *not* a drawer).
- **`CannedResponse`** (per-`waAccountId`, `shortcut` + `content`, shared across everyone with access to that account) — managed from the "Respuestas rápidas" section embedded in `/configuracion` (`configuracion/_respuestas-rapidas.tsx` + its `_respuestas-rapidas-form.tsx` modal; the old standalone `/configuracion/respuestas-rapidas` page was folded in during the 2026-07 nav flattening). In the chat composer, typing `/shortcut` filters and shows a dropdown; Tab or click inserts the full `content`.
- **Auto-assignment** (`lib/whatsapp/auto-assign.ts:autoAssignChat()`) — opt-in per account via `WAAccount.autoAssignEnabled` (toggle on the account detail page), off by default so it never silently changes existing manual-assignment behavior. When enabled, an unassigned inbound message is routed to the eligible candidate (`getEligibleAssignees()`) with the fewest `OPEN`/`PENDING` chats, respecting `User.maxOpenChats` (`null` = unlimited; candidates at their cap are skipped). Wired into `ingestInboundMessage()` right before the `CHAT_MESSAGE` notification check.
- **Per-agent metrics**: `WAMessage.senderId` records which human sent a manual outbound reply (set in `chats/[chatId]/send/route.ts`; bot replies leave it `null` — bots are tracked separately via `WABotConversation`). `WAChat.firstResponseAt` is stamped the first time a manual reply is sent on a chat. `lib/estadisticas/get-stats.ts` aggregates these (in JS, not SQL — Prisma can't `AVG()` a date difference) into `agentPerformance` (resolved count, avg minutes to first response, avg minutes to resolution), rendered in `estadisticas/_view.tsx`.

### Inbox operations: snooze, priority, bulk, typing and drafts (2026-10-30)

- **Priority and snooze live on both `WAChat` and `Conversation`**: `priority` (`ChatPriority`: LOW/NORMAL/HIGH/URGENT, default NORMAL) and `snoozedUntil` (DateTime?). Snooze is deliberately **not** a `ChatStatus`: the chat keeps OPEN/PENDING, a future `snoozedUntil` hides it from the active list, and the ingest clears the field on any inbound (also reopening RESOLVED). `PATCH /api/whatsapp/chats/[chatId]/snooze` `{ until: ISO | null }` (future, max 30 days) and `PATCH /api/whatsapp/chats/[chatId]/priority` `{ priority }`.
- **List filters**: `GET /api/whatsapp/chats` (and `lib/channel-chats.ts` for every generic channel) accept `assigned=me|unassigned`, `priority=LOW|NORMAL|HIGH|URGENT` and `snoozed=only|all` (omitted = active only). The chat workspace mirrors them in the URL (`assigned`, `priority`, `snoozed`), and `chat-filters-panel.tsx` exposes them.
- **Bulk actions**: `POST /api/whatsapp/chats/bulk` `{ chatIds, action }` — max 100 ids, scoped via `getUserAccountIds` + `getUserChannelAccountIds`, actions `assign` (`{self:true}` or `assignedToId`), `status` OPEN/RESOLVED, `priority`, and `snooze`. Emits `conversation.assigned`/`conversation.resolved` per changed chat and sends one summary `CHAT_ASSIGNED` notification when assigning someone else. The list has an explicit selection mode (checkbox + bulk bar), not permanent checkboxes.
- **Claim**: `PATCH /api/whatsapp/chats/[chatId]/assign` accepts `{ self: true }`; `CHAT_ASSIGNED` notifies the target only when someone else assigns, never on self-claim. The composer shows an "Asignarme" banner for unassigned, non-resolved chats.
- **Typing**: `lib/typing.ts` keeps a Redis sorted set `typing:<chatId>` (6 s window, 10 s TTL); `GET/POST /api/whatsapp/chats/[chatId]/typing`. The workspace polls every 5 s and shows "X está escribiendo…" in the header. No websockets.
- **Drafts**: text drafts persist in `localStorage` under `colibly_chat_draft:<userId>:<chatId>` (plus the in-memory map for instant switching), flushed on chat switch/close and removed on send.
- **Saved views**: `chat-views-menu.tsx` stores `{id,name,query}` in `localStorage` (`colibly:chat-views`); applying one replays the URL filter params. They are per browser, not shared — if shared views are needed later, migrate to a `SavedView` model instead of adding permissions to localStorage.

### Contact timeline, reports and command actions (2026-10-31)

- **`ContactActivity`** is the append-only contact timeline (`type`, `title`, `body`, `actorId`, `metadata`, `dedupeKey`). The `domain-events` worker records it for existing events (`contact.created`, lead status, tags, assignment, resolution, appointments, scoring, ad capture); notes, tasks and custom-field routes write directly with their own dedupe keys. `GET /api/whatsapp/contacts/[id]/activities` is scoped like the rest of the contact routes and the drawer renders it with a manual refresh. The worker call is wrapped so a timeline failure never blocks webhook fan-out or automations.
- **Reports**: `/estadisticas/reportes` (`lib/estadisticas/reports.ts`) accepts `?from=YYYY-MM-DD&to=YYYY-MM-DD`, defaults to 30 days, caps at 90, reports new/resolved chats, messages, FRT/resolution, agent drilldown and a per-channel table, and exports both tables to CSV. Days are cut in the organization's time zone (`Organization.timezone` through `lib/dates/zoned.ts`; until 2026-11-01 it was a fixed `-06:00`). It is a separate page because the original `/estadisticas` cache is keyed by user only and aggregates all-time; don't bolt arbitrary ranges onto that cache without changing its key.
- **Command palette**: `command-palette.tsx` now has contextual chat actions (self-assign, resolve, snooze 1 h, high priority), create/navigation actions, and a `Recientes` group stored in `localStorage` (`colibly:command-recent`). Actions call the same APIs as the inbox; no second mutation path.
- **Contact drawer deep link**: `?contacto=<id>` opens the drawer independently of the selected chat; `chat-workspace` syncs the URL with `history.replaceState` and **preserves** `contacto` while rebuilding the filter query string. The drawer has “Copiar enlace”.
- **Shared chat filters**: `lib/chats/query.ts` centralizes `parseChatListFilters`, the Prisma `where` builders for both chat tables and the row mappers/selects used by `/api/whatsapp/chats` and `lib/channel-chats.ts`. There is deliberately no single `/api/chats` endpoint yet: each table paginates over its own total, and a merged endpoint would overfetch both. Use this module for any new chat list filter instead of duplicating it in a route.

### Contact import, CSAT, campaign analytics and calendar (2026-10-31)

- **CSV contact import**: `POST /api/whatsapp/contacts/import` (`{accountId, csv}`) uses the shared `parseCsv`, normalizes/dedupes phones, checks the contacts plan limit with `evaluatePlanLimit`, and inserts with `createManyAndReturn({skipDuplicates:true})`. Blocked for role `user` (`forbidRoles`, same as the Contactos list), 10 imports/h per user, and every created contact emits `contact.created` with `source: "import"` (low priority, spaced 200 ms — same as the coexistence history import; `contact.created` doesn't trigger automations, so nothing is sent). It works for WhatsApp and generic channel accounts; imported contacts have no chat until they write. UI: “Importar CSV” on `/whatsapp/contactos`.
- **CSAT**: `WAAccount.csatEnabled` (off by default) + `CsatResponse` (one per `WAChat`, unique token). Resolving a WhatsApp chat calls `maybeSendCsat()` after the status update: it only sends inside the 24h window, stores the outbound `WAMessage`, and records `sentAt`; failures delete the survey row and never fail the resolve. The public page is `/csat/[token]` + `POST /api/csat/[token]` (rating 1–5, optional comment, rate-limited, one response — enforced by a conditional `updateMany` on `respondedAt: null`, so concurrent submits get 409). Bulk resolve (`chats/bulk`) does **not** send CSAT; single resolve and macros do. Reports include sent/responses/average.
- **Campaign detail**: recipient list accepts `?status=`, the page shows delivery/read rates and lets you export the filtered recipients to CSV. The existing campaign counters remain the source of truth; don't recompute them from recipients.
- **Citas calendar**: `/whatsapp/citas` has a Lista/Calendario toggle. The calendar is a client-side month grid over the already-loaded appointments (respects the active filters); clicking an appointment opens the same `AppointmentFormModal`.
- **Macros**: `Macro` is organization-scoped (`name`, `description`, `actions Json`). CRUD is `/api/whatsapp/macros` (GET/POST) and `/macros/[id]` (PATCH/DELETE); execution is `POST /macros/[id]/run {chatId}`. `lib/macros/execute.ts` applies **assign_self / status / priority / snooze / send_message** using the same effects as the inbox (`sendOutbound`, `emitDomainEvent`, `maybeSendCsat`), never a second automation engine. Any role with chat access can run; `ejecutivo` cannot manage. UI: `/configuracion/macros` + “Aplicar macro” in the chat menu.
- **Conversation attributes**: `ChatCustomFieldDefinition` is account-scoped (`waAccountId` XOR `channelAccountId`, key/label/type/options/required/order); values live in `WAChat.customFields` / `Conversation.customFields` as `{ [key]: string }` (no values table). APIs: `/api/whatsapp/chat-custom-fields` (GET/POST) + `/[id]` (PATCH/DELETE), and `/api/whatsapp/chats/[chatId]/custom-fields` (GET/PUT). UI: section in `/configuracion` and “Atributos de la conversación” in the chat details. Definitions can be deleted; orphan JSON keys are harmless and are filtered at read time. `ejecutivo` cannot manage definitions.
- **Still pending from Fase 3/4**: SLA, teams, FAQ suggestions with AI, duplicate merge. These need schema/UI work; don't assume they exist.

### Esperando respuesta (`waitingSince`, 2026-11-01)

- `WAChat.waitingSince` / `Conversation.waitingSince`: desde cuándo el cliente espera. Los dos ingests llaman `markWaiting()` después de guardar el mensaje (conserva la marca más antigua). La importación del historial de coexistencia **no** marca.
- Se limpia con una respuesta real: envío manual (`chats/[chatId]/send`, las 4 ramas), `sendOutbound()` (API v1, macros, pasos de automatización, plantillas desde el chat), los 4 bot workers (respuesta directa y cada fragmento humanizado) y el eco de la app del negocio en coexistencia. También al resolver (ruta `status`, `bulk`, macros).
- **No** lo limpian: el aviso cuando el bot falla (`FALLBACK_REPLY`), campañas, secuencias, recuperación, CSAT, ni los avisos automáticos que pasan `countsAsReply: false` a `sendOutbound()`.
- Backfill (`20261101072500_chat_waiting_since_backfill`): solo chats no resueltos cuyo último mensaje es entrante y de los últimos 30 días, ignorando el historial importado.
- Filtro `awaiting=1` en `lib/chats/query.ts` (siempre en `AND`), en el panel de filtros ("Respuesta → Esperando respuesta"), en la URL y en las vistas guardadas. La fila muestra `WaitingBadge` ("espera 25 min"): ámbar desde 15 min, rojo desde 60 (`lib/chats/waiting-shared.ts`, importable desde el cliente).
- Los builders de `lib/chats/query.ts` ya no confían en `accountId`: uno ajeno a la lista del usuario da `{ in: [] }`.

### Resolver solos los chats inactivos (auto-resolver, 2026-11-01)

- Configuración por organización en `/configuracion/ia` (tarjeta "Bandeja", solo admin; `PATCH /api/configuracion/ia`): `autoResolveAfterHours` (1–720, `null` = apagado), `autoResolveMessage`, `autoResolveTagName`, `autoResolveSkipWaiting` (default `true`).
- `lib/inbox/auto-resolve.ts:processAutoResolveTick()` corre en la cola `inbox` cada 15 min. Por cada organización activa y **escribible** (`isOrgWritable`) toma hasta 200 chats `OPEN/PENDING` con `lastMessageAt` anterior al corte, sin posposición vigente y —con `skipWaiting`— sin cliente esperando. Las reglas puras viven en `auto-resolve-rules.ts` (con tests).
- Claim atómico: `updateMany` condicionado al mismo `lastMessageAt` leído; si entró un mensaje en medio no se toca.
- Después: `conversation.resolved`, etiqueta opcional **solo en WhatsApp** (los canales genéricos no tienen etiquetas de chat) y mensaje opcional por `sendOutbound(..., { countsAsReply: false })`. Si la ventana de 24 h está cerrada (`OutboundError`) no se manda nada. **No envía CSAT**: nadie atendió el chat.

### Mensaje fuera de horario y días hábiles (2026-11-01)

- `Organization.businessDays Int[]` (0 = domingo … 6 = sábado, default todos). `getOrgBusinessHours()` devuelve `days` y `isWithinBusinessHours()` —ahora puro en `lib/dates/business-hours.ts`, re-exportado desde `lib/whatsapp/lead-recovery.ts`— los respeta, calculando el día en la zona de la organización. Con el default nada cambia; al configurar días, la recuperación de leads, las hojas y la condición "en horario" de las automatizaciones también los respetan.
- `Organization.awayMessageEnabled` (default `false`) + `awayMessageText`; `WAChat/Conversation.awayMessageSentAt`. Se configura en `/configuracion/ia` → Bandeja (la API rechaza activarlo sin texto).
- Los dos ingests llaman `queueAwayMessage()` **solo** si no hubo `suppressBot` ni bot activo (decisión del usuario: el bot gana). Encola `inbox/away-message` con 4 s de retraso y `jobId` por chat y ventana, así una ráfaga produce un solo job. Nunca para grupos ni comentarios de Facebook.
- `processAwayMessageJob()` vuelve a comprobar todo (`away-message-rules.ts`, puro con tests): que siga activo, que haya texto, que no haya bot ni flujo conversacional vivo, que esté fuera de horario, el cooldown de 12 h, que alguien no haya contestado en esos segundos (`waitingSince`) y que la organización sea escribible. Hace un claim atómico de `awayMessageSentAt` y manda con `sendOutbound(..., { countsAsReply: false })`: el chat sigue en "Esperando respuesta". Si el envío falla, el claim se queda (preferimos no duplicar el aviso).

### Contadores de vistas (U4, 2026-11-01)

- `GET /api/whatsapp/chats/counts` → `{ awaiting, mine, unassigned, all }` de chats activos (OPEN/PENDING, sin posponer) en todas las cuentas del usuario, WhatsApp + canales genéricos. Usa los mismos builders que la lista; `buildChannelChatWhere()` acepta `channel` opcional para contar todos los canales genéricos en una sola consulta. Rate limit 60/min.
- `chat-views-menu.tsx`: sección "Vistas rápidas" (Esperando respuesta, Míos, Sin asignar, Todos los activos) con su número, refrescada cada 30 s solo con la pestaña visible. El botón del menú muestra cuántos esperan respuesta. **No** hay pestañas en la cabecera (se quitaron a propósito).

### Atajos de teclado (2026-11-01)

- Mapa y reglas puras en `lib/inbox/shortcuts.ts` (con tests): Alt+J / Alt+K siguiente/anterior chat (orden visual de la lista, agrupada por cuenta), Alt+E resolver, Alt+A asignarme, Alt+S posponer 1 h, `/` buscar, `?` ayuda. Se compara `event.code` (en macOS Alt cambia `event.key`); Ctrl/Cmd nunca se interceptan; los de Alt funcionan escribiendo, `/` y `?` no; con un diálogo abierto, ninguno.
- Las acciones viven en `lib/inbox/actions.ts` (solo `fetch` a las rutas de siempre) y las comparten el palette (que muestra el atajo a la derecha) y `chat-workspace.tsx`. `shortcuts-modal.tsx` lista los atajos desde el mismo mapa.

### Transcripción de notas de voz (2026-11-01)

Bajo cada burbuja de audio (`app/components/whatsapp/audio-transcript.tsx`): botón "Transcribir" (1 crédito) o la transcripción plegable si ya existe. Se muestra también cuando el canal no tiene reproductor (sin proxy de medios). La lógica y las reglas de crédito están en `ia.md` → "Transcripción de notas de voz"; el mensaje lleva `transcript` en `GET /api/whatsapp/chats/[chatId]/messages`.

### Buscar dentro de los mensajes (2026-11-01)

`GET /api/whatsapp/search/messages?q=` (3–100 caracteres, 30/min por usuario) busca en `body`, `caption` y `transcript` de las dos tablas con `$queryRaw` parametrizado (`lib/search/messages.ts`), escapando `%`, `_` y `\` (`escapeLikePattern`, Prisma `contains` no lo hace) y con el alcance de `getUserAccountIds()`/`getUserChannelAccountIds()` en el `WHERE`. Usa los índices trigram de `prisma/sql/ensure-search-indexes.sql` (runbook de producción en `desarrollo.md`). En la bandeja aparece como sección "En mensajes" bajo la lista de chats (`message-search-results.tsx`) y como grupo en el palette.

Saltar al mensaje: `GET …/chats/[chatId]/messages?around=<messageId>` devuelve los 25 anteriores y **todos** los posteriores (hasta 500; si hay más, 422 `too_far` y el chat se abre normal). Así el poll de 5 s, que trae los últimos 50, nunca deja un hueco. El workspace guarda el salto en `jumpRef` y en la URL (`?mensaje=`, que la sincronización de filtros conserva igual que `contacto`), y el hilo centra e ilumina el mensaje (`focusMessageId`).

### Ficha del contacto con pestañas (U1, 2026-11-01)

`contact-drawer.tsx` se divide en **Resumen** (estado, trato, etiquetas, próxima cita), **Actividad** (notas y línea de tiempo), **Tareas y citas** y **Campos** (`HeroTabs`). La pestaña va en la URL como `ficha=` (se omite para Resumen) para que "Copiar enlace" abra la misma; la sincronización de filtros de la bandeja la conserva igual que `contacto` y `mensaje`, y cerrar la ficha borra `ficha` y `contacto`. Pie fijo con "Agendar cita" y, fuera de la bandeja, "Abrir chat" (solo WhatsApp: el GET del contacto trae `chat`).

### Disponibilidad del equipo (2026-11-01)

`User.availability` (`ONLINE`/`BUSY`/`OFFLINE`, la que elige el usuario en el menú de perfil vía `GET/PATCH /api/usuarios/me/disponibilidad`, cualquier rol; bajo `/api/usuarios` para heredar la allowlist de solo lectura) y `User.lastSeenAt`. Latido sin websockets: `GET /api/whatsapp/notifications` llama `touchLastSeen()` (como mucho una escritura por minuto); la campana lo consulta cada 25 s con la pestaña visible y cada ~100 s con la pestaña oculta, para que quien trabaja en otra pestaña no aparezca desconectado. `lib/users/availability-rules.ts:effectiveAvailability()` (pura, con tests): OFFLINE si lo eligió o si no hay latido en 5 min; BUSY se respeta mientras siga conectado. Auto-asignación: `autoAssignOnlineOnly` en `WAAccount` y `ChannelAccount` (apagado por defecto) → `assignableCandidateIds()` filtra a los ONLINE efectivos **antes** de las reglas de enrutamiento; si no queda nadie, el chat queda sin asignar. Apagado, la lista no se toca (comportamiento anterior). El interruptor está en el detalle de la cuenta de WhatsApp; los canales genéricos todavía no tienen UI para `autoAssignEnabled`, así que su campo existe pero no se edita.

### Panel en vivo y mapa de calor (2026-11-01)

`/estadisticas/reportes` arranca con "Ahora" (`_live.tsx`): `GET /api/estadisticas/en-vivo` (`lib/estadisticas/live.ts`; 403 para ejecutivo, 30/min) cada 30 s con la pestaña visible — abiertos, pendientes, sin asignar, esperando respuesta (con el más antiguo), equipo en línea y carga por agente. Al final, "Por día y hora" (`_heatmap.tsx`, `lib/estadisticas/heatmap.ts`): mensajes entrantes o chats resueltos en una cuadrícula 7×24 en la zona de la organización. Las columnas son `timestamp` sin zona guardadas en UTC: se convierten con `(col AT TIME ZONE 'UTC') AT TIME ZONE tz`; un solo `AT TIME ZONE tz` daría 6 h de desfase. El color mezcla `--accent-strong` sobre `--surface` con raíz cuadrada (`heatIntensity`), y cada celda lleva el número en `title`/`aria-label`.

### Notificaciones push del navegador (2026-11-01)

Acompañan a algunas `Notification` de la campana, nunca la reemplazan: mensaje entrante en un chat asignado (los dos ingests, `tag: chat:<id>` para que el navegador reemplace el aviso anterior del mismo chat), chat asignado (`assign` y `bulk`) y llamada entrante (`calling/ingest.ts`). `lib/notifications/push.ts:queuePush()` (nunca lanza) encola `inbox/push` solo si hay llaves VAPID (`plataforma.md`) y el usuario tiene al menos una `PushSubscription`; el worker manda con `web-push` (TTL 5 min, urgencia alta, 10 s de timeout) y borra la suscripción si el servicio responde 404/410. El link siempre es una ruta interna (`safePushLink`). Navegador: `public/sw.js` (solo `push` y `notificationclick`; no cachea ni intercepta peticiones; `worker-src` cae en `script-src 'self'` y `proxy.ts` no redirige `/sw.js`), `lib/notifications/push-client.ts` y el interruptor "Avisos en este navegador" del menú de usuario (`/api/usuarios/me/push`, cualquier rol, bajo la allowlist de solo lectura). Al cargar la app se re-sincroniza la suscripción del navegador con el usuario actual; **cerrar sesión la borra** (`disablePush()` en los tres botones de cerrar sesión) para que el navegador no siga recibiendo avisos de la cuenta anterior. En iPhone solo funciona con la app agregada a la pantalla de inicio (el menú lo explica). Playwright no puede suscribirse (su Chromium no trae servicio push): la prueba real es en Chrome.

### Rendimiento del bot en reportes (F1, 2026-11-01)

`lib/estadisticas/bot-performance.ts`: una fila por chat con respuestas del bot (`WABotUsage` con `waChatId`/`conversationId`) en el periodo y las cuentas del usuario. Traspaso = existe un OUTBOUND con `senderId` (una persona) después de la primera respuesta del bot del periodo; resuelto por el bot = `RESOLVED` sin traspaso; el resto, abierto. CSAT separado por grupo (solo WhatsApp tiene CSAT). Clasificación y totales puros con tests (`bot-performance-rules.ts`). La sección "Bot de IA" de `/estadisticas/reportes` solo aparece si hubo chats con bot. Nota: `suggest-reply` también escribe `WABotUsage`; como el humano manda después la sugerencia, esos chats cuentan como traspaso, que es correcto.

### Variables en respuestas rápidas (F5, 2026-11-01)

`{{nombre}}` (si el nombre del chat es solo el número, queda vacío), `{{agente}}` (nombre del usuario en sesión) y `{{negocio}}` (`Organization.name`, vía `BusinessNameProvider` en `dashboard-shell.tsx` → `useBusinessName()`). `lib/inbox/canned-variables.ts:renderCannedResponse()` (pura, con tests) se aplica al insertar en el compositor; a diferencia de `renderText()` de las automatizaciones, una variable desconocida **se deja tal cual** para que el agente la vea antes de enviar.

### Firma personal (F6, 2026-11-01)

`User.messageSignature` (máx. 100) + `User.signatureEnabled`, editables en Configuración → "Firma en los mensajes" (`GET/PATCH /api/auth/profile`). La ruta de envío manual (`chats/[chatId]/send`, las cuatro ramas: WhatsApp, Telegram, Messenger/Instagram y web) la agrega con `lib/inbox/signature.ts:appendSignature()` **solo a mensajes `type: "text"`**: nunca a botones, plantillas, media, notas automáticas ni a lo que mandan bots, macros o la API. No se duplica si el texto ya termina con ella y se omite si el texto con firma pasaría el límite del canal (4096 WhatsApp/Telegram, 2000 Messenger/Instagram/web). El compositor muestra "Se agregará tu firma" mientras se escribe.

### Importación de contactos con mapeo de columnas (F3, 2026-11-01)

El modal (`contact-import-modal.tsx`) tiene dos pasos: archivo → "Importar como" por columna (teléfono, nombre, etiqueta(s) separadas por `;` o `|`, un campo personalizado de la cuenta destino, o no importar) con vista previa de contactos listos, repetidos en el archivo y avisos por fila. La vista previa y la ruta usan la misma lógica pura (`lib/contacts/import-mapping.ts`: `guessMapping`, `mappingError`, `normalizeFieldValue` por tipo —número, fecha AAAA-MM-DD o DD/MM/AAAA, sí/no, opción de la lista— y `buildImportPlan`), con tests. `POST /api/whatsapp/contacts/import` acepta `mapping` (debe tener una entrada por columna y sus `definitionId` deben ser de ESA cuenta; si no, 400) y sin `mapping` propone uno por los nombres de cabecera (compatibilidad). Una fila con teléfono inválido se descarta; un campo inválido solo se omite. Etiquetas (`findOrCreateTag` en la cuenta destino, máx. 50 distintas) y campos se aplican **solo a los contactos nuevos**; los existentes se omiten como antes. `tag.added`/secuencias por etiqueta corren en `after()` (pueden ser miles). Se conservan el límite del plan, `contact.created`, el rate limit y el 403 para el rol user. `parseCsvTable()` (en `parse-csv.ts`, quita el BOM) da la tabla cruda; `parseCsv()` de campañas no cambió.

### Atributos obligatorios al resolver (F4, 2026-11-01)

Un `ChatCustomFieldDefinition` con `required: true` bloquea resolver mientras su valor esté vacío (`lib/chats/required-fields.ts`; regla pura `missingRequiredFields` con tests: espacios cuentan como vacío, `"false"` es un valor). Dónde se aplica: `PATCH …/status` responde **422 `required_fields`** con la lista `fields`; `POST /chats/bulk` (resolver) salta esos chats y devuelve `skipped`; una macro que resuelve se rechaza **antes** de aplicar cualquier acción (`MacroBlockedError` → 422, nunca queda a medias); el auto-resolver los salta (`result.skippedRequired`; si hubiera más de 200 bloqueados en una organización ocuparían el lote del tick). En la bandeja, `handleStatusChange` (selector de estado y Alt+E) abre `required-fields-modal.tsx`, que pide solo los que faltan, guarda con `PUT …/custom-fields` y reintenta.
