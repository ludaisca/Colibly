# Autenticación, correos de cuenta y sesiones

> Detalle técnico movido desde `AGENTS.md` (2026-11-01). Las reglas esenciales siguen en [`AGENTS.md`](../../AGENTS.md) y [`CLAUDE.md`](../../CLAUDE.md); aquí está el detalle completo. Mantén este archivo al día en el mismo cambio que el código.

## Auth

- `lib/auth.ts` — NextAuth v5 (Credentials + bcrypt, JWT strategy only, **no adapter**)
- Server: `import { auth } from "@/lib/auth"` → `const session = await auth()`
- Client: `useSession()` from `next-auth/react`
- **Account emails** (since 2026-09-25): `lib/email/mailer.ts` sends over SMTP, configured from `/plataforma` (`PlatformSettings.smtpHost`/`smtpPort`/`smtpSecure`/`smtpUser`/`smtpPass`/`emailFrom` — never env vars since S5, 2026-09-28); required in production, logged to the console in dev without it — point it at **Mailpit** from `/plataforma` (host `mailpit`, port `1025`), UI at `http://localhost:18025`. One-time links live in `AuthToken` (`EMAIL_VERIFY` 48h, `PASSWORD_RESET` 1h, `INVITE` 7d; only the sha256 is stored, issuing a new one deletes the pending ones, consumption is an atomic `updateMany`) — `lib/auth-tokens.ts`, flows in `lib/auth-emails.ts`, templates in `lib/email/templates.ts` (inline styles, client data HTML-escaped). Sends run inside Next's `after()` so they never delay or fail the response.
  - **Verification**: signup emails a link (`/verificar-correo`); `User.emailVerifiedAt` null shows a banner with "Reenviar enlace" (`AppShell` `topBanner` slot) and `requireVerifiedEmail()` answers 403 `code: "email_unverified"` on every channel-account create (WhatsApp, Telegram, Messenger, Instagram, Web, Meta Ads). Users that existed before this shipped were marked verified by a data migration. **Since 2026-10-30 an unverified email cannot sign in**: `authorize` throws `CredentialsSignin` with `code: "email_not_verified"` and the 60 s JWT revalidation drops already-open sessions (`lib/auth-policy.ts:emailAllowsSignIn()`). The **SaaS owner** in `PLATFORM_ADMIN_EMAILS` is exempt; the owner of each organization is **not** (every signup creates one and would bypass the anti-bot block). Registration no longer signs in automatically: it shows a "confirma tu correo" screen with resend; `POST /api/auth/verify-email/resend` also accepts an unauthenticated `{ email }` and always answers generically (3/10 min per email, 10/h per IP). The login page detects `email_not_verified` and offers "Reenviar enlace". `lib/platform-admin-emails.ts` is the pure parser shared by the policy and the panel.
  - **Password reset**: `/recuperar` → `POST /api/auth/forgot-password` (same answer and timing whether the email exists; limited per IP and per email) → `/restablecer` → `POST /api/auth/reset-password`, which bumps `sessionVersion` (closes other sessions) and marks the email verified.
  - **Invitations**: admins invite from `/usuarios` (`/api/usuarios/invitaciones`, list/POST/DELETE, org-scoped); `/invitacion` shows the org and role and `POST /api/auth/invitacion` creates the user in that organization, verified. Re-inviting invalidates the previous link; an email that already has an account (any organization) can't be invited, since a user belongs to one organization. Creating a member with a typed password stays available to admins.
- Registration is open to anyone and always creates a **new organization** (never joins an existing one); members of an existing organization are created by its admins in `/usuarios` (scoped to the org). Signing in to an organization with status `SUSPENDED` is refused, and the 60s revalidation drops open sessions of such organizations.
- **Session revalidation** (`lib/auth.ts`): the JWT stores `role` + `sessionVersion` at sign-in; every 60s the `jwt` callback re-reads the user (in-memory cache, 60s) — a role change applies to open sessions within a minute, and a user who was deleted, disabled (`User.disabledAt`) or had `sessionVersion` bumped gets `null` → session invalidated. Disabled users can't sign in and are excluded from assignment candidates (`lib/chat-assignees.ts`, Telegram auto-assign). Admins disable/reactivate from `/usuarios` (`PATCH /api/usuarios {userId, disabled}` bumps `sessionVersion` on disable); the organization owner can't be disabled or demoted and each organization must keep at least one **active** admin. Tokens issued before `sessionVersion` existed count as version 0.
- `AUTH_SECRET` = base64 (generated via `openssl rand -base64 32`)
