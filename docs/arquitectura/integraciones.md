## Eventos de dominio, API pública y webhooks (2026-09-25)

Three pieces sharing one scope model. **Admin-only in 3 layers** (card on `/configuracion` only for admin, `/configuracion/api` in both blocked lists, every `/api/configuracion/{api-keys,webhooks,integration-accounts}` handler 403s via `lib/integrations/admin-session.ts:requireAdmin()`).
- **Rotate an API key** (2026-11-05): "Rotar" in `/configuracion/api` → `POST /api/configuracion/api-keys/[id]/rotate {graceHours: 0|24}`. Creates a new key with the same name, scopes, accounts and expiry, owned by the admin who rotates (doesn't count against the key cap); the old one is revoked now or expires in 24 h (`lib/api/key-rotation.ts:rotationExpiry()`, never later than its original expiry) and its auth cache is invalidated. A leaked key should be rotated without grace.

- **Event bus** (`lib/events/`): `emitDomainEvent(input)` only enqueues on `domain-events` and **never throws** (the fact already happened). Types in `lib/events/types.ts` (`DOMAIN_EVENT_CATALOG` is the public list). Each event carries `account` (`{kind:"whatsapp"}` or `{kind:"channel", channel}`), `contactId`, `chat` and typed `data`. Emitted from: both ingests (`message.received`, `contact.created`, `lead.ad_captured` for CTWA, auto `conversation.assigned`), `chats/[chatId]/{send,assign,status,tags}`, contacts PATCH/tags (through `lib/contacts/side-effects.ts`), appointments POST/PATCH and the bot's AI appointments, `scoreChatWithScorer` (`lead.scored` with `previousLabel`), the leadgen webhook. **New code that changes one of these facts must emit the event** — and for lead status / contact tags call `afterLeadStatusChanged()` / `afterContactTagAdded()` instead of repeating Meta CAPI + sequences + event inline.
- **Integration scope** (`lib/integrations/account-scope.ts`): an `ApiKey`/`WebhookEndpoint` sees what its owner sees **today** (`getUserAccountIds` + `getUserChannelAccountIds`, recomputed each use) intersected with its own `accountIds`/`channelAccountIds` (both empty = no restriction). Because of that, `webhookUpdateSchema` (`lib/webhooks/crud.ts`) has **no `.default()`**: Zod 4's `.partial()` keeps defaults, and a PATCH that left out `accountIds` used to save `[]` and silently widen the webhook to every account (fixed 2026-11-13, guarded by `lib/webhooks/__tests__/schema.test.ts`). Any future update schema for a scoped resource must follow the same rule. Keys stop working immediately if the owner stops being admin or is disabled.
- **Public API** (`/api/v1/*`, outside NextAuth — no session, so `proxy.ts`'s role lists and read-only gate don't apply; the API enforces its own GET-only rule for read-only orgs): `Authorization: Bearer sk_live_…`, only the sha256 is stored (`ApiKey.keyHash`), secret shown once. Every handler: `withApiErrors(async (req) => { const ctx = await authenticateApiKey(req, "<scope>"); … })` (lib/api). Errors are `{error:{code,message}}` (`ApiError`); ids outside the scope answer **404, never 403**. Resource lookups go through `lib/api/resources.ts` (`findScopedContact`, `findScopedConversation`). Cursor pagination is keyset `(date, id)`; `/conversations` merges `WAChat`+`Conversation` with the same cursor. 120 req/min per key. `lib/api/openapi.ts` is hand-written — **update it in the same change as any `/api/v1` route**.
- **Outbound sends** (`lib/messaging/outbound.ts:sendOutbound()`): text/buttons/template for any channel, enforces the WhatsApp 24h window (templates exempt), persists the message, emits `message.sent`. Used by the API (and phase 2 automations); the inbox composer keeps its own route because of uploaded media.
- **Webhooks**: fan-out in `lib/webhooks/fanout.ts` (one `WebhookDelivery` per matching endpoint, `@@unique([endpointId,eventId])` makes retries idempotent), delivery in `lib/webhooks/deliver.ts` signed `X-Colibly-Signature: t=<unix>,v1=hex(hmac_sha256(secret, "t.body"))`. 20 consecutive final failures ⇒ endpoint disabled + `INTEGRATION_ERROR` notification. Deliveries are purged after 30 days by the daily `media-cleanup` job.
- **Public message shape** (2026-11-04, `docs/META_JSON_CUENTAS_WA_2026-11-04.md` §8): `lib/messages/serialize.ts:serializeMessage()` is the **only** serializer of a message — `GET /api/v1/conversations/{id}/messages` and the `message` field of every `message.*` webhook use it (`lib/webhooks/payload.ts:loadPublicMessage()`, read at delivery time). Additive contract: the v1 fields stay; added `externalId`, `content` (location, shared contacts, order, system, errors, media sha256/voice/animated, forwarded, referredProduct, replyToFrom), `media` (`url` = `GET /api/v1/messages/{id}/media` with the API key, `ready`, `size`, `sha256` — never Meta's URL), `replyTo {externalId, messageId, from}`, `reaction`, `transcript`, `error`, `deliveredAt`/`readAt` (Meta's time) and `pricing`. `text` is `null` instead of a `[type]` marker (`publicText()`, also applied to `data.text` of `message.received`). A new message field goes in the serializer + its `MESSAGE_SERIALIZE_SELECT_*` + the OpenAPI `Message` schema, never in one place only. **`message.status_changed`** (WhatsApp only) is emitted by the Meta webhook when a status actually advances (the rank-guarded `updateMany` returned a row), with `previousStatus` (read just before the update), `error` (`message` in Spanish + Meta's `title`/`details`/`href`, stored in `WAMessage.errorDetail`) and `pricing`. A `read` without a previous `delivered` also sets `deliveredAt = readAt`.
- **Contract v1.1 (2026-11-04, `docs/API_WEBHOOKS_AUDITORIA_2026-11-04.md`):**
  - **`message.sent` has one emitter, `lib/events/message-sent.ts:emitMessageSent(kind, messageId, origin)`**, called right after the outbound row is saved by every sender: inbox send route (`agent`), `sendOutbound()` (`api`/`automation`/`system` via `outboundOriginOf()`, or an explicit `opts.origin`), bot workers and `bot-send-worker` (`bot`), `campaign-worker` (`campaign`, low priority), `sequences.ts` (`sequence`), the three `lead-recovery.ts` (`recovery`), CSAT (`system`), Google lead sheets (`automation`), call permission (`agent`) and Coexistence echoes (`business_app`; history imports emit nothing). It reads the saved row, so `data` (`origin`, `sentBy`, `senderName`, legacy `source`, `publicText` text) matches what the API returns. **A new way to send must set `sentVia` on the row and call it.**
  - `sentVia` (`WAMessage`/`ChannelMessage`) stores the origin; `lib/messages/origin.ts:messageOrigin()` derives it for older rows (`origin` BUSINESS_APP_ECHO/HISTORY, `campaignId`, `recoveryAttempt`, `leadSheetSourceId`, `senderId`) and returns `null` when nothing tells. The serializer exposes `origin`, `sentBy`, `senderName`.
  - Phones: `lib/phone/e164.ts:toE164()` (Mexico `521…` → `+52…`) feeds `contact.phoneE164`, `account.phoneNumber`/`phoneE164` in the event envelope and `phoneE164` in `/accounts` and `/contacts`; `phone` keeps Meta's raw `wa_id`. `POST /contacts` dedupes with `jidCandidates()`.
  - Every `/api/v1` response (`withApiErrors` → `withSchemaVersion`) and every delivery carries `X-Colibly-Schema-Version` (`API_SCHEMA_VERSION` in `lib/api/constants.ts`). A contract change bumps it, `API_VERSION` and `API_CHANGELOG` (`x-colibly-changelog`) in `openapi.ts`. `lib/api/__tests__/openapi.test.ts` fails if the `Message` schema, the event `data` examples or the envelope drift from the code.
  - `app/api/v1/[...path]` answers JSON 404 for unknown routes; `readPageParams()` answers 400 to a non-integer `limit` and still clamps to 100. `openapi.json` is built once per base URL.
  - Part 2 (same v1.1, not yet released): `Message.referral` (Meta's CTWA `referral` in camelCase, without the CDN image/video URLs) and `Message.createdAt` (when Colibly stored it — the checkpoint for `since`); `content.placeholder = { reason: "history_media" }` is added by the serializer for `media_placeholder` rows (not stored); `Contact.adId`/`ctwaClid`; `Conversation.updatedAt`; `contact.tags` in the event envelope.
  - Incremental sync: `GET /conversations?updatedSince=` (`updatedAt ≥`), `GET /conversations/{id}/messages?since=` (switches to `createdAt` ascending, cursor on `createdAt`), `GET /messages?since=` (`lib/api/messages-feed.ts:messagesFeed()`, both tables merged by `(createdAt, id)` like `/conversations`, own 60/min limit, `since` required) and `GET /messages/{id}` (`findScopedMessage()`). Indexes `wa_messages(created_at)` and `channel_messages(created_at)`. Status changes don't move `createdAt`: integrators get them from `message.status_changed` or by re-reading the message.
  - Part 3 (same v1.1): `media.sha256Hex` = `WAMessage/ChannelMessage.mediaSha256`, the hex sha256 of the stored file — set by `media-worker` (all inbound downloads, from `persistBuffer()`), the inbox send route (`mediaSha256Of()` on the uploaded file), and campaign/lead-sheet header media. `media.sha256` stays Meta's base64 value. A new path that stores a media file must set `mediaSha256` too.
  - Deliveries over the API: `GET /webhooks/{id}/deliveries` (status/eventType/since filters, no body), `GET …/deliveries/{deliveryId}` (with `payload`) and `POST …/replay`. Replay lives in `lib/webhooks/replay.ts:replayDelivery()` (atomic claim of the current status → PENDING, attempts 0, new jobId; same body and eventId), shared with the settings "Reintentar" button (FAILED only); the API also allows SENT, refuses PENDING or an inactive endpoint with 409, and has its own 30/min per org limit (`API_RATE_LIMIT_WEBHOOK_REPLAYS_PER_ORG`).
  - Part 4 (same v1.1): **`message.updated`** `{ messageId, reason: "media_ready" | "history_media" }` via `lib/events/message-sent.ts:emitMessageUpdated()` — `media-worker` after any download (all channels) and Coexistence ingest when a `media_placeholder` gets its content; history rows go out with background priority. `Contact.dealValueCents` (cents, `dealCurrency: "MXN"`) and `expectedCloseAt`, readable and writable through `PATCH /contacts/{id}` (same 20,000,000 MXN cap as the UI).
  - Data fix `20261104210200_message_status_backfill`: campaign messages got `deliveredAt`/`readAt` from `WACampaignRecipient`; `read` rows without `deliveredAt` got `deliveredAt = readAt`. Other messages before 2026-11-04 19:47 UTC have no times (Meta has no API to fetch past statuses).
- **Contract v1.2 (2026-11-05, schema `2026-11-05`) — integrator experience:**
  - Errors: `lib/api/respond.ts:readJsonBody(req, schema)` is the only way a `/api/v1` handler reads a body — empty body / malformed JSON get their own message, zod issues come out in Spanish (`z.locales.es()` per parse; a schema's own messages win) as `error.details[] = { path, message }` (`template.id`, `buttons.0.title`) with the first one in `message`. `ApiError` carries `details`.
  - Request id: `withApiErrors` (and `withIdempotency` via `withRequestScope`) run the handler inside an `AsyncLocalStorage` with a `req_…` id; `apiError()` adds `error.requestId` and every response gets `X-Request-Id`. 500s log `[api] <requestId> METHOD path`.
  - 405: every `app/api/v1/**/route.ts` exports all of GET/POST/PUT/PATCH/DELETE; the ones it doesn't serve are `methodNotAllowed(...served)` (JSON `method_not_allowed` + `Allow`). `openapi.test.ts` checks that each route exports the five and serves exactly the documented ones — a new route must follow it.
  - Catalogs (`lib/api/catalog.ts`, full lists, no cursor): `GET /templates` (`messages:send`; `params` from `getTemplateVariables()` = what POST /messages needs; `statusReason`; refreshes pending templates in the background) and `POST /templates/sync` (v1.4.0, 2026-11-06: asks Meta now, 6/min/org, 502 `upstream_error` with per-account `details` when Meta fails), `GET /tags` (`contacts:read`), `GET /users` (`conversations:read`, the whole org incl. disabled), `GET /teams` (`conversations:read`, v1.3: `memberIds` = active members; `Conversation.teamId`, `?teamId=` on the list and `teamId` in PATCH, which goes through `setChatTeam()` first so an explicit `assignedToId` wins), `GET /automations` (`automations:run`, `runnable` = ACTIVE + manual).
  - `PATCH /conversations/{id}` (new scope `conversations:write`): status and/or `assignedToId`, through `lib/chats/actions.ts:setChatStatus()` / `assignChat()` — the same functions the inbox routes `/api/whatsapp/chats/[chatId]/{status,assign}` use (required attributes → 422 `required_fields`, `waitingSince` cleared on resolve, CSAT, `conversation.*` events, assignee notification + push). Don't reimplement status/assignment elsewhere.
  - Webhooks: `POST /webhooks/{id}/test` (`lib/webhooks/test-event.ts:sendWebhookTestEvent()`, shared with the settings "Probar" button; 10/min per org) and `POST /webhooks/{id}/rotate-secret` (`rotateWebhookSecret(owner, id, graceHours)`).
  - **Rotation grace period**: `WebhookEndpoint.previousSecret` (encrypted) + `previousSecretExpiresAt`. With `graceHours` 1–72 (API body, or the settings modal's "Rotar con 24 h de gracia") the old secret keeps signing: `lib/webhooks/signature.ts:signingSecrets()` feeds `signWebhookBody([new, old])` → `t=…,v1=<new>,v1=<old>`. Without it (default) the header keeps its single-v1 form. Only the immediately previous secret is kept. The published verification recipes (`_snippets.ts`) accept any matching v1 and `docs-snippets.test.ts` executes the Node one against both forms — keep them that way.
  - **Media over the API**: `POST /messages` with `type` image/document/audio/video + `media.url` (https) [+ `filename`, `mimeType`, `caption`]. `lib/messaging/outbound-media.ts:fetchOutboundMedia()` downloads through `safeFetch` (`binary: true`, 30 s, size cap per type) and validates the MIME against `OUTBOUND_MEDIA_RULES` (WhatsApp's lists, the strictest, for every channel; octet-stream → by extension). `sendOutbound()` takes `{ type: "media", file }`: WhatsApp uploads (`uploadMedia`) + sends by media id, Telegram `sendTelegramMedia`, Messenger/Instagram `sendMetaChannelMedia` (no caption); the file is stored with `saveMediaFromBuffer()` (sets `mediaSha256`). `assertMediaSupported()` runs before the download (webchat has no media yet; Meta no caption).
  - Docs: `/docs/api` adds the Python verification snippet (`_snippets.ts:PYTHON_VERIFY`), `details`/`X-Request-Id` and the catalogs note.

- **SSRF**: any HTTP to a user-supplied URL goes through `lib/net/safe-fetch.ts` — the IP is checked in the socket `lookup` (no DNS-rebinding window), no redirects, blocks private/loopback/link-local/CGNAT/reserved and IPv4-mapped IPv6. `NODE_ENV=development` additionally allows loopback + RFC1918 (for local receivers), never 169.254/metadata.

- **Pendiente:** `LeadOutcomeEvent.valueCents` (historial de ganados/perdidos con su monto) aún no está en `/api/v1`. `dealValueCents`/`expectedCloseAt` del contacto ya se exponen (2026-11-04). El chat web aún no recibe archivos (ni desde la bandeja ni por API).

## Automatizaciones (motor único, 2026-09-25)

One engine for button chatbots ("flows"), event→action rules and drip follow-ups, in every channel. `/whatsapp/automatizaciones` (nav "Automatizaciones", admin + user; `ejecutivo` blocked in 3 layers — nav, `EXECUTIVE_BLOCKED`, `lib/automations/access.ts:requireAutomationSession()` 403). Chat-level actions (the inbox chip, manual start) are authorized **by chat access** (`lib/automations/chat-access.ts`), so ejecutivos can pause/resume/start from the chat.

- **Graph = tree** (`lib/automations/types.ts`): a step with branches (buttons, list, wait-for-reply, condition, AI classify) must be the **last** of its column and branches never rejoin — so a run's position is just a `nodeId` and "next" is the next sibling. `validate.ts` (pure, used by the editor in the browser too) enforces structure, Meta limits (3 buttons × 20 chars, 10 list rows) and warns when a free-form WhatsApp message would land >24 h after the customer's last message. `publish.ts:validateForPublish()` adds the DB checks (template of THIS account and approved, assignee has access, custom field and scorer exist, `safe-fetch` URL).
- **Versions**: editing touches `Automation.draftGraph`; publishing creates an immutable `AutomationVersion` and runs are pinned to theirs — editing never breaks a run in flight (the old sequences only warned about it).
- **Executor is pure** (`executor.ts`): all effects go through `ExecutorAdapters`. Real runs use `adapters.ts` (Prisma + existing modules: `sendOutbound`, `afterLeadStatusChanged`/`afterContactTagAdded`, auto-assign, `scoreChatWithScorer`, `safe-fetch`); "Probar" uses `simulate.ts` (nothing sent, CRM untouched, AI real); tests use fakes (`__tests__/helpers.ts`). **Add a step type = types.ts + validate.ts + executor.ts + labels.ts + editor form + tests** (plus `simulate.ts`, `_graph-edit.ts` defaults and, if it references something of the org, a check in `publish.ts`). `assign_team` (2026-11-05) moves the chat to a team through `setChatTeam()` (same effects as the inbox selector); `publish.ts` rejects a team that isn't in the organization.
- **Runner** (`runner.ts`): `startRun()` guards inside a Serializable transaction — one live run per (automation, contact), `allowReentry`, **one conversational run per chat**, and max 20 run starts per contact per hour (stops automations that trigger each other). `advanceRun()` takes a row lock (`lockedAt`), executes, persists; a reply that arrives mid-advance bumps `inputSeq` and is processed right after. Send failures: `window_closed` → EXPIRED (or the step's fallback template), upstream → backoff 15/30/60/120 min then FAILED.
- **Entry points**: `dispatch.ts:dispatchInboundMessage()` is called by **both ingests before enqueuing the bot** — a waiting run takes the reply, else keyword > first_message > message_received; if it returns `suppressBot`, the bot doesn't answer. Event triggers (tag added, lead status, appointment completed, score label change, ad lead) come through the `domain-events` worker (`handleDomainEvent`). An agent's manual reply pauses conversational runs in that chat (`PAUSED_BY_AGENT`); `lib/bots/guards.ts` keeps the bot quiet while a conversational run holds the chat and for 24 h after a "Pasar a humano" step.
- **Interactive messages in every channel** (`lib/messaging/outbound.ts`): WhatsApp buttons/list, Telegram inline keyboard (`callback_query` ingested as text + `interactiveReplyId`, `answerCallbackQuery`), Messenger/Instagram quick replies (`quick_reply.payload`), web widget buttons (`interactivePayload` rendered by `widget.js`, tap sends `replyId`). Replies match by id → option text (accent/case-insensitive) → number ("2") → optional AI.
- **AI steps** use the recommended model of the first enabled platform provider (`DEFAULT_AI_MODEL`), reserve an organization credit per call (`AiCallContext.organizationId`) and log `AutomationAiUsage` — summed by `getOrgAiCost()` and shown in the chat cost badge.
- **Public API**: `POST /api/v1/automations/{id}/runs` (scope `automations:run`) starts a `manual` automation for a contact, with `vars`.
- **Sequences** (`WASequence`) still run side by side until they are converted (phase 3); don't add features to them.

## Meta Ads (feedback loop de calificación de leads)

Closes the loop between CRM lead scoring and ad optimization: when an ads-originated lead changes `leadStatus`, the system reports the change to Meta's **Conversions API** so the algorithm can optimize for quality.

- **`MetaAdsAccount`** (`/meta-ads`, admin-only — credentials are sensitive business config with no `ChannelAccountShare`/`WAAccountShare` equivalent): a Facebook Page + Business config, deliberately separate from `WAAccount` (a Lead Ads page isn't a WhatsApp number — it can feed leads to an existing number via `waAccountId` without being one). Fields: `pageId`, `pageAccessToken`, `appSecret`, `verifyTokenHash`, `datasetId` (Pixel/Dataset id), `capiAccessToken`, `status` (`WaAccountStatus`), `mode` (`TEST`/`LIVE`), `testEventCode`. **Safety**: `lib/meta/conversions.ts` rejects sending an event unless `testEventCode` (TEST mode) or `mode: LIVE` is explicitly confirmed — a bug can't emit events "into the air" that would pollute the ad account.
- **`Contact.leadOrigin`** (`ORGANIC`/`INSTANT_FORM`/`CTWA`, default `ORGANIC`) + `metaLeadId` (Instant Forms) + `ctwaClid`/`adId` (click-to-WhatsApp referral captured in `lib/whatsapp/ingest-message.ts`). `LeadOrigin` decides which payload builder runs (`buildInstantFormPayload` with `action_source: "system_generated"` + `lead_id` vs `buildCtwaPayload` with `action_source: "business_messaging"` + `ctwa_clid`).
- **Webhooks**: `/api/meta/webhook/leadgen` (Instant Forms — creates the `Contact` on the `waAccountId` configured on the `MetaAdsAccount`, first-touch attribution) and `/api/meta/webhook/messaging` (Messenger/Instagram messages). Both validate `X-Hub-Signature-256` via `lib/meta/webhook-signature.ts`.
- **Trigger**: `PATCH /api/whatsapp/contacts/[id]` (the pipeline Kanban drop + contact edit) enqueues `meta-conversions` when `leadStatus` changes on a non-`ORGANIC` contact. `lib/meta/send-conversion.ts:sendLeadConversionEvent(contactId, leadStatus)` is the single business entry point (shared by the automatic trigger and any future manual resend — same pattern as `scoreChatWithScorer()`); `lib/meta/lead-status-mapping.ts:mapLeadStatusToMetaEvent()` decides which statuses get reported and with what `event_name`/`value` (business decision, 2026-08-05: `NEW` isn't reported — it adds no new quality signal over the initial click/form; `CONTACTED`/`QUALIFIED`/`CUSTOMER`/`LOST` are, as `Contact`/`Lead`/`Purchase`/`LeadLost` respectively, no `value`/`currency` yet — occurrence-only). If a Meta Events Manager funnel mapping is configured later with different event names, update the strings in that file to match.
- **`MetaConversionEvent`** logs every send attempt (`@@unique([contactId, leadStatus])`, upsert so a contact passing through the same status twice re-sends; `status`: PENDING/SENT/FAILED + `errorMessage` + `metaEventId` for Meta-side dedup). Queue: `meta-conversions` (concurrency 1).

## Nodo de n8n (`integrations/n8n`, 2026-11-10)

Paquete npm aparte, `n8n-nodes-colibly`, que consume la API pública tal como está (no hay rutas propias de n8n). Vive en `integrations/n8n/` con su propio `package.json` y `node_modules`; está excluido del `tsconfig`, del ESLint y del `.dockerignore` de la app.

- **Credencial** `coliblyApi`: API key + URL base; el test llama `GET /api/v1/me`.
- **Nodo Colibly**: contactos, etiquetas, conversaciones, mensajes, automatizaciones y catálogos. Paginación por cursor (`limit`/`cursor`), `Idempotency-Key` en `POST /messages` y `POST /automations/{id}/runs`, y los errores de la API se muestran con su mensaje y `requestId` (se lee la respuesta con `ignoreHttpStatusErrors`).
- **Colibly Trigger**: `webhookMethods` crea el webhook (`POST /webhooks`) al activar el flujo, guarda el `whsec_…` en el static data del nodo y lo borra al desactivar; `webhook()` verifica `X-Colibly-Signature` igual que `lib/webhooks/signature.ts` (varias `v1` en una rotación, 5 min de tolerancia). **Si cambia el esquema de firma o la lista de eventos (`DOMAIN_EVENT_CATALOG`), actualizar el nodo y subir su versión.**
- Comandos dentro de un contenedor Node desechable: `npm ci && npm run lint && npm run build && npm test`. Publicar: `npm publish --access public` desde `integrations/n8n/` con la cuenta de npm de Colibly.
