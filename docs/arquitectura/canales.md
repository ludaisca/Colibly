# Canales genéricos (Telegram, Messenger, Instagram, widget web, WhatsApp por QR)

> Detalle técnico movido desde `AGENTS.md` (2026-11-01). Las reglas esenciales siguen en [`AGENTS.md`](../../AGENTS.md) y [`CLAUDE.md`](../../CLAUDE.md); aquí está el detalle completo. Mantén este archivo al día en el mismo cambio que el código.

## Canal genérico (Telegram, Messenger, Instagram)

Parallel stack to the WhatsApp one, added as an adapter layer rather than a schema migration (the `WA*` tables hold production data and were deliberately left untouched). Tables: `ChannelAccount` (`channel` enum — **Telegram/Messenger/Instagram**), `Conversation` (the `WAChat` analogue), `ChannelMessage` (the `WAMessage` analogue), `ChannelAccountShare` (the `WAAccountShare` analogue).

**Enabled from signup (2026-10-27)**: `Organization.channelTelegramEnabled` / `channelMessengerEnabled` / `channelInstagramEnabled` / `channelWebchatEnabled` default to `true` (schema default + explicit set in `createOrganizationWithOwner()`, migration `*_channels_default_on_existing` for older orgs). `lib/channel-flags.ts:assertChannelEnabled()` runs in each `POST /api/{telegram,messenger,instagram,webchat}/accounts` and answers 403 `channel_disabled`; the operator can turn a channel off per organization from `/plataforma` as an exception. Turning it off does **not** stop existing accounts — they keep sending and receiving; it only blocks creating new ones.

- **Per-channel plumbing**: `lib/telegram.ts` (Telegram API client), `lib/meta-messaging.ts` (shared Messenger+Instagram client — both use the same Page Access Token and `graph.facebook.com` under the page-linked model, not standalone Instagram Login), `lib/meta-messaging/{send,account-crud,routes}.ts` (`routes.ts`: create/delete handlers of `/api/messenger/*` and `/api/instagram/*`, generated per channel), `lib/channels/routes.ts` (the handlers every generic channel shares: account list, chats, outbound media upload and the media proxy — Telegram, Messenger, Instagram, web chat and WhatsApp por QR export them from their `route.ts`; only creating/deleting an account, which registers or drops each provider's webhook, stays per channel). Deleting a Messenger/Instagram account is scoped with `accountManageWhere()` like Telegram (any admin of the org or the owner; until 2026-11-18 only the creator), `lib/channel-media.ts`, `lib/channel-chats.ts`. The account lists `/telegram/cuentas`, `/messenger/cuentas`, `/instagram/cuentas` are one client component, `app/components/channel-accounts/accounts-page.tsx` (`ChannelAccountsPage` + a per-channel config of texts, icon and form); web chat and WhatsApp por QR keep their own page (snippet, QR).
- **Scoping**: `lib/shared-accounts.ts` exports `getUserChannelAccountIds(userId)` (own + `ChannelAccountShare`) — the channel counterpart of `getUserAccountIds()`. Use it in any new channel-scoped route; **never filter channel data by `channelAccount: { userId }`** (owner-only). Until 2026-09-16 there was no way to create a share and half the routes filtered by owner, so Telegram/Messenger/Instagram/Web chats could only be worked by the account owner (audit M11). Sharing: `GET/POST/DELETE /api/channel-accounts/[id]/share` (admin + account owner, mirrors the WhatsApp share route), UI = "Compartir" row action in the 4 channel account lists (`app/components/channel-accounts/share-modal.tsx`). Grantees see and work chats/contacts, appear as assignees (`getEligibleChannelAssignees()`, also used by channel auto-assign), but editing/deleting the account stays owner-only. `lib/chat-resolver.ts:resolveChatChannel()` lets the WhatsApp chat routes (`/api/whatsapp/chats/[chatId]/...`) serve both channels: a `chatId` may be a `WAChat.id` *or* a `Conversation.id` — new per-chat routes should follow this shape instead of being duplicated under `/api/telegram/`.
- **Webhooks**: `/api/telegram/webhook/[accountId]` (URL identifies the account; `X-Telegram-Bot-Api-Secret-Token` header authenticates, rate-limited) and `/api/meta/webhook/messaging` (Messenger/Instagram — validates `X-Hub-Signature-256` against the account's `appSecret`, same mechanism as the WhatsApp webhook).
- **Bots**: `WABot.waAccountId` XOR `WABot.channelAccountId` (mutually exclusive at the application level — a bot serves exactly one account). The `bot-messages` queue carries both kinds of jobs; `lib/workers/index.ts` routes on payload shape (`conversationId` present ⇒ channel) rather than a flag. Every generic channel (Telegram, Messenger, Instagram, WEBCHAT, WHATSAPP_WEB) uses **one** bot worker, `lib/channels/bot-worker.ts:processChannelBotMessageJob()` — it mirrors the WhatsApp one but lacks campaign context and outbound media. The only per-channel difference is sending, in `lib/channel-send.ts:sendChannelReplyText()` (also used by `bot-send-worker.ts` for humanized chunks). Until 2026-11-17 Messenger/Instagram had a near-identical copy (`lib/meta-messaging/bot-worker.ts`); don't fork it again — add a `case` to `sendChannelReplyText()`.
- **Media**: `ChannelMessage.mediaUrl` uses the same local-disk scheme under `MEDIA_ROOT`; proxied via `/api/telegram/messages/[messageId]/media` and `/api/instagram/...`-style endpoints with the same auth checks. Messenger/Instagram outbound media is a two-step (upload → `attachment_id` reference, `uploadMetaAttachment()` in `lib/meta-messaging.ts`) — Meta's URL-alternative doesn't apply since our media isn't publicly fetchable.
- **Lead recovery**: `lib/channels/lead-recovery.ts:sendChannelRecoveryMessage()` — Telegram, Messenger and Instagram (`RECOVERY_CHANNELS`) re-engage silent leads with the account's active bot (no 24h window restriction like WhatsApp's); it refuses any other channel before spending AI and sends through `sendChannelReplyText()`.
- **Telegram deliberately lacks** (guarded in the UI, not merely absent): campaigns/templates (Meta-specific concepts), lead scoring, chat tags, outbound media, multimodal AI input. Messenger/Instagram share the same limitations plus no campaigns/lead scoring/tags.
- **Comment-to-inbox (Facebook e Instagram: publicaciones, reels y anuncios; reescrito 2026-11-18)**: `/api/meta/webhook/messaging` also handles `entry[].changes` with `field: "feed"` (`value.item === "comment"`, `value.verb === "add"`) — a comment on a Page post **or ad** (Meta sends ad-post comments through the same field) becomes a normal `Conversation`/`ChannelMessage` keyed by the commenter's id (`value.from.id`), with `isFromComment: true` and `commentPostId` (the post, linked from the bubble as «Ver publicación»). Comments written by the Page itself are dropped. `subscribePageToApp()` subscribes `messages,feed` for **both** Messenger and Instagram accounts (`subscribed_fields` replaces the Page's list, so the two channels of one Page must ask for the same) — **Messenger accounts created before 2026-08-06 must be reconnected once**.
  - **Instagram comments (2026-11-18):** the same webhook handles `object: "instagram"` + `changes[].field === "comments"` (posts, reels and ads; Meta sends no date, the entry's `time` is used). Keyed by the commenter's IGSID (`from.id`, name `@username`), own-account comments dropped, `commentPostId` = the post's permalink fetched once (`fetchInstagramPermalink()`; only `https://www.instagram.com/…` is stored). Same rules and code as Facebook (`isCommentChannel()`): private reply through the Page's Send API with `recipient.comment_id`, public reply with `POST /{ig-comment-id}/replies` (`instagram_manage_comments`). The app must have the Instagram webhook field `comments` subscribed (platform app: once by the operator; manual accounts: in the customer's app).
  - **One place decides how a Messenger message goes out: `lib/meta-messaging/comment-reply.ts`** (pure rules in `comment-rules.ts`, shared with the inbox). Used by the chat (`chats/[chatId]/send`) and `sendOutbound` (API, automations, macros) — a new way to send on Messenger must go through `sendMetaDirectText()` / `assertMetaMediaAllowed()`. Meta's rules: if the person's latest inbound is a comment not yet answered privately and ≤ 7 days old → **private reply** (`POST /{page-id}/messages` with `recipient.comment_id`; the old `/{comment-id}/private_replies` edge is gone from Meta's docs), text only, one per comment. After that, Messenger only opens when the person answers (24 h from their last DM); otherwise the send is refused with `CommentReplyBlockedError` (`awaiting_reply` / `comment_expired`; chat 409, API 422 `window_closed`). A new comment allows another private reply.
  - **Same thread after the private reply:** Meta returns the person's Messenger id (PSID) in `recipient_id`, which can differ from the commenter id. It is stored in `Conversation.aliasExternalId` (unique per account); the webhook resolves an incoming DM from that PSID to the comment's conversation (`resolveInboundExternalId()`), and every Messenger send resolves its recipient through it (`lib/meta-messaging/send.ts:resolveRecipient()`, so the bot and lead recovery too). If another conversation already uses that PSID (the person had DM'd before commenting) nothing is merged.
  - **Public reply:** `commentReply: "public"` on the chat send replies under the person's latest comment (`POST /{comment-id}/comments`, needs `pages_manage_engagement`; no time window). Outbound rows carry `commentReplyKind` (`private`/`public`) and the answered comment in `replyToExternalId`, so the bubble quotes it.
  - **Inbox UI:** `CommentReplyBar` (`app/components/whatsapp/comment-reply-bar.tsx`) above the composer on Messenger chats that have comments: «Mensaje privado | En la publicación» plus the rule that applies now; the default is public when Meta blocks the private route. Bubbles show «Desde un comentario · Ver publicación» and «Respuesta privada al comentario» / «Respuesta en la publicación».
  - **Bots skip comment-origin messages** (`ingestChannelMessage()` never enqueues the bot when `isFromComment`); automations do run and their sends follow the same rules. The away message also skips comments.
  - **Dev testing:** `lib/meta-messaging.ts` follows `META_GRAPH_ORIGIN` (dev only, `lib/meta/graph.ts`), so a fake Graph can answer the sends. Not yet verified against a real Page: whether `from.id` equals the PSID/IGSID, and the ad-comment payloads.

### Conectar con Facebook (app de la plataforma, 2026-11-18)

Messenger e Instagram se conectan con la **app de Meta de Colibly**, como el Embedded Signup de WhatsApp: el cliente no crea una app ni pega tokens. La conexión manual (app propia: Page ID, token, App Secret, webhook y verify token del cliente) sigue disponible como «Conectar a mano».

- **Config:** `PlatformSettings.metaMessagingConfigId` (otra configuración de «Inicio de sesión para empresas» de la misma app; `/plataforma` → Configuración → App de Meta). Disponible solo con App ID + App Secret + ese ID + token de verificación del webhook (`messagingConnectConfig()`); si falta algo, el modal abre directo el formulario manual.
- **Flujo** (`lib/meta-messaging/platform-connect.ts`, rutas `/api/meta/messaging-connect/{config,pages,complete}`, UI `app/components/meta-messaging/facebook-connect-modal.tsx` dentro de `MetaChannelAccountFormModal`): `FB.login` con `config_id` + `response_type: "code"` → `pages` canjea el código (`exchangeCodeForToken`, luego `fb_exchange_token` para que los tokens de Página no venzan), lista `me/accounts` con su Instagram vinculado y guarda los tokens **cifrados en Redis 15 min** (`meta-msg-connect:<id>`, atado a quien lo abrió); al navegador solo van ids, nombres y el estado (libre / ya conectada aquí / en otra organización — `pageStates()`). `complete` crea una cuenta por elección con los mismos candados que el alta manual (correo verificado, `assertChannelEnabled`, `checkPlanLimit`, rate limit, sin `ejecutivo`) y `createMetaChannelAccount({ connection: "platform" })`.
- **Credenciales:** `credentials.connection = "platform"` y **sin `appSecret`**. El webhook (`/api/meta/webhook/messaging`, el mismo para todas) firma con el App Secret de la plataforma esas cuentas y con el del cliente las manuales — nunca al revés; el GET de verificación acepta primero el token de verificación de la plataforma.
- **Borrar** una cuenta solo desuscribe la Página si ninguna otra cuenta de la organización (el Messenger o el Instagram de la misma Página) la usa.
- **Operador, una vez en la app de Meta:** productos Messenger e Instagram con webhook `https://<app>/api/meta/webhook/messaging` y el token de verificación de la plataforma; campos de Página `messages`, `messaging_postbacks`, `feed`; de Instagram `messages`, `comments`. Configuración de Inicio de sesión para empresas con `pages_show_list`, `pages_messaging`, `pages_manage_metadata`, `pages_read_engagement`, `pages_manage_engagement`, `instagram_basic`, `instagram_manage_messages`, `instagram_manage_comments`, `business_management`, y **acceso avanzado aprobado por Meta (App Review)** para esos permisos: sin él solo funcionan las personas con rol en la app.
- **Dev:** `lib/meta-messaging.ts` y `validate-page-token.ts` siguen `META_GRAPH_ORIGIN` (solo dev), así que un Graph simulado cubre el flujo completo; probado así el 2026-11-18 (no contra Meta real).

### Live chat widget (`Channel.WEBCHAT`, roadmap P3-f)

Fourth generic channel, added 2026-08-06 — an embeddable chat bubble for the client's own website. Structurally different from Telegram/Messenger/Instagram in one key way: those three authenticate inbound webhooks from a real external provider (Meta, Telegram); here **we are the provider** — there's no external platform to trust, so the entire security model is self-issued.

- **Visitor identity** (reworked 2026-09-16, audit M3): the **server** assigns the `visitorId` (`lib/webchat/session-token.ts:generateVisitorId()`, crypto-random) and it becomes the `Conversation.externalId`. It used to be generated by the widget (`Math.random`) and `/session` signed any id the client sent — anyone who knew a visitor's id could read that conversation.
- **Session token**: `base64url(payload).hex(HMAC-SHA256)` signed with `ENCRYPTION_KEY`, carrying `{visitorId, channelAccountId, iat, exp}` (24h). `POST /api/webchat/[accountId]/session` issues a new visitor, or — when the widget sends its stored `renewToken` — the same visitor, accepting an expired token up to `WEBCHAT_RENEW_WINDOW_SECONDS` (30 days); a tampered token gets a brand-new visitor. The widget keeps only the token in `localStorage` and sends it as `Authorization: Bearer` (query/body still accepted for already-open tabs; `readWebchatToken()`), renewing on 401/403. The `Origin` check against `allowedOrigins` only stops *browsers* on other sites — scripts can spoof it — so abuse is bounded by limits: 30 sessions/min and 20 new visitors/h per IP, 20 msgs/min per visitor and 60/min per IP, 200 new conversations/h per account (each can trigger paid bot replies).
- **`ChannelAccount` for WEBCHAT**: `credentials` (same encrypted-JSON field as other channels, `lib/webchat/account.ts:WebchatCredentials`) holds only `{allowedOrigins: string[]}` — no provider secret exists to store. `externalAccountId`/`verifyTokenHash` stay null (no webhook handshake to disambiguate). Account creation (`POST /api/webchat/accounts`) skips the "validate against provider, then connect" two-step Telegram/Messenger do — there's no provider to validate against, so the account is `CONNECTED` immediately.
- **Public routes** (all under `/api/webchat/[accountId]/`, all outside any NextAuth session, all rate-limited): `POST session` (above), `POST/GET messages` (send / poll — same polling pattern as the rest of the app, no websockets; inbound messages reuse `ingestChannelMessage()` exactly like Telegram/Messenger), `GET widget.js` (the embeddable script itself, served as plain vanilla JS with no build step and no framework dependency — it runs inside an arbitrary third-party page we don't control). All three besides `widget.js` require real CORS handling (`lib/webchat/account.ts:corsHeaders()` + explicit `OPTIONS` handlers) since the visitor's browser calls them cross-origin from the client's own domain.
- **MVP scope, deliberately narrow**: text-only — no media upload/rendering in the widget, no interactive buttons, no lead scoring, no AI copilot (`score`/`scorers`/`suggest-reply` routes explicitly reject `WEBCHAT` alongside `MESSENGER`/`INSTAGRAM`). The chat composer disables the attach-media button for a `WEBCHAT` chat (`attachmentsDisabled` in `chat-workspace.tsx`) since the backend would reject media anyway.
- **Bots work, agent sending is a no-op call**: `WABot.channelAccountId` can point at a WEBCHAT account exactly like Telegram — the shared `lib/channels/bot-worker.ts` serves it (same simple profile: plain text, no service-window restriction). The only real branch point is *sending*: `lib/channel-send.ts:sendChannelReplyText()` (also used by `bot-send-worker.ts`) special-cases `channel === "WEBCHAT"` to skip any outbound API call — there's nothing to call, the `ChannelMessage` row created right after **is** the delivery; the widget picks it up on its next poll. Manual agent replies follow the same shape (`sendWebchatReply()` in `chats/[chatId]/send/route.ts` just persists the row).
- **Widget UX detail that already caused a bug**: the widget must NOT optimistically render the visitor's own outbound message and then also show it again when the next poll brings it back from the server (confirmed) — that duplicated the bubble. Fixed by never rendering optimistically; `sendMessage()` triggers an immediate `poll()` right after the POST resolves instead.
- **UI**: `/webchat/cuentas` (nav "Cuentas Web" under Canales, same EntityList-based CRUD shape as `/telegram/cuentas`) — creating/editing an account shows the copy-paste `<script>` snippet (`app/(dashboard)/webchat/cuentas/_form.tsx`), not a webhook URL + verify token like WhatsApp's flow (there's no provider-side webhook to configure — the snippet itself is the entire integration).
- **Not built yet**: Instagram-style story/comment capture doesn't apply here (no such concept for a website); a visible "typing..." indicator or read receipts back to the visitor; per-account branding (widget color/greeting are hardcoded, teal to match the app's own accent).

## WhatsApp por QR (`Channel.WHATSAPP_WEB`, GoWA, 2026-11-17)

WhatsApp **no oficial**: un número se vincula escaneando un QR, como WhatsApp Web, a través de [GoWA](https://github.com/aldinokemal/go-whatsapp-web-multidevice) (MIT). WhatsApp puede suspender el número; por eso es **solo por invitación** y no se anuncia (el sitio sigue diciendo "API oficial de Meta"). Plan y decisiones: `docs/PLAN_GOWA_2026-11-17.md`.

- **Habilitación:** `Organization.channelWhatsappWebEnabled`, `false` por defecto y nunca encendida en el alta. Solo el operador la cambia (`/plataforma` → organización → "WhatsApp por QR", acción `set_whatsapp_web`, que llama a `invalidateAccountScopes()`). **Apagarla detiene el canal**, a diferencia de los demás: `getUserChannelAccountIds()` deja fuera sus cuentas (bandeja, contadores, envíos, búsqueda), `lib/gowa/send.ts` no envía (`GowaChannelDisabledError`, 403), el webhook descarta (200 sin guardar), la pestaña y `/whatsapp-web/cuentas` desaparecen (`layout.tsx` → 404) y la fila no aparece en Configuración → Canales. No hay límite de plan propio: decide el operador.
- **Infraestructura:** contenedor `gowa` en `docker-compose.yml` (imagen fija `aldinokemal2104/go-whatsapp-web-multidevice:v9.9.0`), **sin puertos publicados**: solo la app lo alcanza por la red interna. Su panel (`APP_UI_ENABLED=false`) y su WebSocket no separan números entre sí, y `/statics` (QR, medios) no pide Basic Auth — nada fuera de la app debe llegar a él. Basic Auth `colibly:${SERVICE_PASSWORD_GOWA}` (variable mágica de Coolify: la genera y la conserva sola; en dev va en `.env`); sin contraseña GoWA no arranca (`restart: on-failure:5`) y el canal se ve "no disponible". La app lee `GOWA_URL` (default `http://gowa:3000`), `GOWA_BASIC_AUTH` y `GOWA_WEBHOOK_BASE_URL` (default `http://app:5000`). Sesiones en el volumen `gowa_storages` (SQLite de GoWA; **no está en el respaldo de la base**: si se pierde, se vuelve a escanear el QR — el historial vive en Colibly). `statics` no tiene volumen: GoWA no limpia sus medios y nosotros ya los copiamos a `MEDIA_ROOT`, así que se vacía en cada despliegue. Estados y canales se filtran en GoWA (`WHATSAPP_WEBHOOK_IGNORE_JIDS`) y otra vez en `chatKey()`; los grupos sí llegan (el filtro de GoWA es global, no por número) y la app los descarta salvo en cuentas con `groupsEnabled` — ver «Grupos» abajo.
- **Cuenta = device de GoWA.** `ChannelAccount.credentials` (cifrado) = `{ deviceId, webhookSecret, phone, jid }` (`lib/gowa/account.ts`). `POST /api/whatsapp-web/accounts` crea la cuenta y el device con **su propio webhook y secreto** (`/api/gowa/webhook/[accountId]`, eventos en `GOWA_WEBHOOK_EVENTS`); si GoWA falla, borra la cuenta. `GET /api/whatsapp-web/accounts/[id]/conexion` consulta el estado (usePoll cada 3 s) y con `?qr=1` devuelve un QR nuevo como data URL (el navegador nunca habla con GoWA; el QR se pide solo al abrir y al vencer, para no reiniciar un escaneo); `POST` con `{ phone }` da el código de 8 caracteres. Al vincularse, `syncGowaLink()` pone `CONNECTED` y `externalAccountId` = número (`@@unique([channel, externalAccountId])`: un número en una sola cuenta → 409). Borrar la cuenta o la organización (`lib/org-data/delete.ts`) cierra la sesión y borra el device (`lib/gowa/lifecycle.ts`, best effort).
- **Webhook** (`app/api/gowa/webhook/[accountId]`): HMAC-SHA256 del cuerpo crudo con el secreto de esa cuenta (`X-Hub-Signature-256`), `session_id` (el id del device; `device_id` es el JID del número) debe ser el `deviceId` de la cuenta — los eventos de mensaje pueden omitirlo, entonces la firma basta —, y luego `parseGowaEvent()` (puro, `lib/gowa/webhook.ts`, pruebas en `lib/gowa/__tests__/webhook.test.ts`) → `handleGowaEvent()` (`lib/gowa/ingest.ts`). GoWA reintenta 5 veces ante un 5xx.
  - Entrante → `ingestChannelMessage(…, "WHATSAPP_WEB")` (automatizaciones antes que el bot, dedup por conversación). Los medios se descargan por la cola `media-download` (`mediaId` = id del mensaje → `GET /message/:id/download` de GoWA), con `WHATSAPP_AUTO_DOWNLOAD_MEDIA=false`.
  - **El chat se identifica por el JID de teléfono** cuando se conoce (`chatKey()`): el mismo contacto puede llegar como `…@lid` y luego como número; usar el que venga duplicaría la conversación.
  - Mensaje propio (`is_from_me`, escrito desde el teléfono vinculado) → saliente con `sentVia: "business_app"`: cuenta como respuesta humana (pausa el bot, `lib/bots/guards.ts`) y quita la espera, sin notificar. Los envíos de la app ya están guardados y el dedup los descarta. Contacto y conversación se crean con `upsertChannelThread()` (`lib/telegram/ingest-message.ts`), el mismo de la ingesta entrante, sin sumar no leídos.
  - `message.ack` sube el estado (sent → delivered → read, nunca baja). Los acuses propios se ignoran: `read-self` (recibos de lectura apagados) y cualquier `read` cuyo `from` sea el propio número (`device_id`), que traen ids de mensajes *entrantes*. `message.reaction` → `reactionEmoji`; `message.revoked` marca el mensaje sin borrarlo.
  - `device.logged_out` / `device.temporary_ban` → cuenta `ERROR` con el motivo + `Notification` ACCOUNT_STATUS (y push) al dueño y admins, una sola vez (la fecha de fin de una suspensión, en la zona horaria de la organización); `device.reachout_timelock` deja la cuenta `CONNECTED` con el aviso en `errorMessage`.
- **Envío:** `lib/gowa/send.ts` (`assertOrgCanSend` + bandera) desde la bandeja (`chats/[chatId]/send`, misma rama que Telegram, con cita), `sendOutbound()` (API, automatizaciones; los botones van numerados en el texto), el bot (`lib/channel-send.ts`, `bot-send-worker`; el bot-worker compartido `lib/channels/bot-worker.ts`). Sin ventana de 24 h ni plantillas. Los errores de GoWA se traducen en `gowaMessage()` y la ruta responde 422.
- **No tiene** (como los demás canales genéricos): campañas, plantillas, calificación de contactos, copiloto de IA, reacciones del agente ni etiquetas de chat. Tampoco se ofrece para dar de alta contactos a mano ni en campañas/recuperación: escribir en frío es lo que más suspensiones causa.
- **API pública y webhooks: misma capa que WhatsApp.** No hay valor nuevo en el contrato (ni en `lib/api/openapi.ts`, ni en el changelog, ni en `API_SCHEMA_VERSION`). `lib/api/public-channel.ts` hace que hacia afuera estos chats, contactos y cuentas salgan como `channel: "WHATSAPP"`, con el número en `phone`/`phoneE164` (cuenta: `externalAccountId`) en `serializeContact`, `serializeConversation`, `GET /api/v1/accounts(/[id])` y `buildPublicEvent()`. `GET /api/v1/conversations?channel=WHATSAPP` incluye los de QR. Crear contactos por la API en una de estas cuentas responde 400 sin nombrar el canal. Con la bandera apagada, sus cuentas ni siquiera entran en el alcance de la API (`resolveIntegrationScope` → `getUserChannelAccountIds`). No documentarlo en ningún lugar público (sitio, guías, docs de la API).
- **Diagnóstico:** `channels.gowa` en el doctor (`lib/platform/diagnostics.ts`): ok sin configurar si ninguna organización lo usa; `fail` si alguna lo tiene y falta la contraseña; `warn` si GoWA no responde o hay números en error.

### Grupos de WhatsApp por QR (2026-11-18)

- **Interruptor por número**: `ChannelAccount.groupsEnabled` (apagado por defecto), en el menú de la cuenta en `/whatsapp-web/cuentas` (`PATCH /api/whatsapp-web/accounts/[id]`, admin o dueño). Al encenderlo se vuelve a registrar el webhook del device (`setDeviceWebhook`) para que GoWA mande también `group.info`; si GoWA no responde, el interruptor se guarda igual.
- **Webhook** (`lib/gowa/webhook.ts`): con `chat_id` `…@g.us` el chat es el grupo (`chatKey()`), `isGroup: true`, y `senderName`/`senderExternalId` dicen quién escribió (`sender_display_name` → `from_name` → número; un remitente `@lid` usa `sender_alt` si trae el teléfono). `group.info` cambia el nombre de la conversación.
- **Ingesta** (`lib/gowa/ingest.ts:ingestGroupMessage`): un grupo es **solo conversación** — decisión de producto: sin `Contact` (no cuenta en el CRM, embudo ni conteos), sin bot, automatizaciones, aviso fuera de horario ni recuperación, sin `waitingSince` ni SLA (`lib/sla/tick.ts` filtra `isGroup: false`), no se autorresuelve (`lib/inbox/auto-resolve.ts`), sin eventos de dominio (`message.received/sent/updated`: la API y los webhooks hablan de clientes; `emitMessageSent` los salta) y sin notificación por mensaje: solo suma no leídos. Un mensaje nuevo reabre el grupo resuelto o pospuesto. El nombre se pide a GoWA (`GET /group/info`, `getGroupName`) solo al crear la conversación; si falla queda «Grupo de WhatsApp» hasta el siguiente `group.info`. Lo escrito desde el teléfono en el grupo se guarda como saliente `business_app`.
- **Bandeja**: el remitente va arriba de cada burbuja entrante (`ChannelMessage.senderName`, en `CHANNEL_MESSAGE_SELECT`); la vista previa del chat lleva «Nombre: texto». Contestar desde la bandeja manda al JID del grupo por el mismo `sendGowaMessage`.
- **Regla:** nada automático actúa en un grupo. Un flujo automático nuevo sobre conversaciones genéricas (tick, worker, aviso) debe excluir `isGroup`.
