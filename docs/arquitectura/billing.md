## Per-user licenses (in progress since 2026-11-04)

Plan: [`docs/PLAN_LICENCIAS_2026-11-04.md`](../PLAN_LICENCIAS_2026-11-04.md). Every person pays a **license** (Básico/Avanzado/Pro, same `PlanId` enum and prices as `PLANS`); an organization mixes licenses; price rises by features, and every license holds **one channel of each type** (WhatsApp, Instagram, Messenger, Telegram, web chat).

**Phase 1 (done, dev): data and catalog.**
- Catalog and pure rules: `lib/billing/licenses.ts` (tests `__tests__/licenses.test.ts`) — `LICENSES` (features set, per-license `contacts`/`activeLeads`/`aiCreditsPerMonth`, org-level `funnels`/`customFields` taken from the org's highest license), `hasFeature()`, `minLicenseFor()`, `orgLicenseLimits(counts)`, `channelLicense(owner)` (no owner or disabled owner ⇒ Básico), `canOwnChannel()`, `userAiCreditLimit()` (trial: 500 per person; Básico 0 even with bonus), `licenseAvailability()`, `licenseChangeImpact()`, `monthlyTotalForLicenses()`, `isLegacyActive()`.
- Data (`20261105004333_user_licenses` + `_backfill`): `User.license` (backfilled with the org plan) and per-user `aiCredits*` (unused until Phase 2); `AuthToken.license` on invitations; `WAAccount.ownerId` (`@unique`) and `ChannelAccount.ownerId` (`@@unique([ownerId, channel])`) — the **owner**, whose license the channel uses, separate from `userId` (who connected it; still drives `accountManageWhere`). NULL owner = ownerless (orgs that had more channels than people). `TopicMonitor.createdById`; `Organization.licensesEssential/Business/Pro` (purchased, backfilled from `seatQuantity` for subscribed orgs) and `legacyUntil` (grandfathering, set in Phase 5).
- Writers: signup gives the owner `TRIAL_LICENSE`; invitations and admin-created users get `defaultLicenseFor(org)` (the org plan) until Phase 3 adds the picker; every channel creation calls `lib/billing/user-license.ts:claimChannelOwner()` **after** the create — the unique index decides concurrent claims and the loser stays ownerless instead of failing.

**Phase 2 (done, dev, 2026-11-05): gates and credits read the licenses.** Not deployed: deploy only with Phase 5, which sets `legacyUntil` on current customers first — without it a paying Básico org would lose AI the moment this code ships.
- **Which catalog rules an org**: `licenses.ts:catalogMode()` — `internal` (no caps), `legacy` (`legacyUntil` in the future: the old org-level `PLANS` gates and the shared credit pool, via `legacyHasFeature(planLimits(org), f)`) or `license`. Every gate below branches on it, so legacy orgs keep exactly what they had.
- **Feature gates live in `lib/billing/entitlements.ts`** (15 s in-process cache of each user and each channel's owner; `invalidateUserEntitlement()` / `invalidateChannelEntitlement()` — `claimChannelOwner()` already calls the latter). Three shapes, each with a `has…` boolean, a `check…` 402 (`code: "plan_limit"`, `limit: <feature>`, message from `featureBlockedMessage()`) and a `…Message` for services that throw their own errors:
  - **per person** (`userHasFeature` / `checkUserFeature`): AI assist (rewrite, task suggestion, reply suggestion, manual transcription, bot test), create automations/sequences/macros/lead sources/scorers/monitors, apply a macro, create or send a campaign, publish/activate an automation, manual "Calificar".
  - **per channel owner** (`channelHasFeature` / `checkChannelFeature`; ownerless or disabled owner ⇒ Básico): bot create/activate/move (`aiAgent`, rule 7 — config follows the channel, not the admin), the three bot workers, `bot-mode`, campaign create/send and the scheduled tick + job (a campaign whose number lost `campaigns` goes back to DRAFT and its creator gets a bell notice), automation dispatch and the delayed-run tick, sequences tick (skipped items are pushed 1 h so they don't fill the batch), lead recovery (per account), scheduled scoring, auto-transcription, auto-assign (both stacks), CSAT, WhatsApp calls.
  - **per integration owner** (`integrationOwnerHas` / `checkIntegrationFeature`; in `license` mode the owner must also be an active admin): API (`authenticateApiKey`, key creation), webhooks (`createWebhook`/`updateWebhook` reactivation or takeover, `replayDelivery`, test delivery, fanout per endpoint), Meta Ads (account creation, `sendLeadConversionEvent`). The create and replay checks sit inside `lib/webhooks/crud.ts` and `lib/webhooks/replay.ts`, so the screen and `/api/v1` can't diverge — that closed the two holes where the API skipped the plan check.
  - `orgHasAnyFeature()` only decides whether a configuration screen shows (`AiPlanGate`).
- **Org limits** (`gates.ts:effectiveOrgLimits()`, used by `evaluatePlanLimit`, the contact-limit helpers and the plan screen): in `license` mode contacts/active leads add up the licenses of active people, funnels/custom fields come from the highest one, every channel type (web chat included, `"webchat"` limit key) allows one per license, and `activeAutomations`/`aiAgents` have no count cap (the license of the publisher and of the channel owner decide). `seats` is unchanged until Phase 3.
- **AI credits are personal** (`lib/ai/credits.ts`): `reserveAiCredit(payer)` / `hasAiCredits(payer)` / `aiCreditStatus(payer)` with `payer = { userId }` (what a person asks for; a monitor → its creator, else the org owner) or `{ channel }` (anything automatic on a chat → the channel owner; ownerless ⇒ nobody pays ⇒ no AI). Atomic capped increment on `User.aiCreditsUsed` against `userAiCreditLimit()`; 80 %/100 % notices go to that person (bell; email at 100 %). Legacy orgs keep `Organization.aiCredits*`; internal orgs aren't counted. `resetAiCredits()` (paid invoice) resets the org pool and every member; `orgAiCreditSummary()` sums members for the screens (`/configuracion/plan`, `/configuracion/ia`, stats). Monitors make one AI call per chat **per creator**.
- Tests: `licenses.test.ts` (catalog mode, legacy mapping, messages), `entitlements.test.ts`, `ai/__tests__/credits.test.ts`, license-mode limits in `seat-channel-limits.test.ts`, owner gating in `webhooks/__tests__/fanout.test.ts`. Verified against the dev DB with a throwaway org (one person per license, an ownerless channel): every gate, credits per person and per channel owner, 5 concurrent reservations with 2 credits left → exactly 2 pass, limits, and legacy falling back to the org plan and pool.


**Phase 3 (done, dev, 2026-11-05): Stripe with one line per plan and the screens.** Same three Stripe prices as before, so an old single-item subscription already *is* "N licenses of that plan".
- **Pure rules** (`stripe-rules.ts`, tested): `licenseLineItems()` (Checkout), `licenseItemsUpdate(current, target)` (update quantities, add missing lines, `deleted: true` for zeros, merge duplicates, never touch an unknown price), `licenseCountsFromItems()`, `licenseProrationBehavior()` (higher monthly total ⇒ `always_invoice` + `pending_if_incomplete`, else `create_prorations`), idempotency keys per counts + request id. `licenses.ts`: `licenseTargetBlockers()` (never fewer of a plan than assigned = active people + pending invitations), `licenseAssignBlocker()` (trial without subscription: any license up to `TRIAL_MAX_USERS`; otherwise a free one of that plan), `purchasedAfterLicenseChange()` (buy the target if none is free, drop the one freed).
- **Stripe** (`stripe.ts`): `updateSubscriptionLicenses(subId, {target})`; `syncSubscription()` writes `licensesEssential/Business/Pro` from all items, `seatQuantity` = total and `plan` = highest (legacy screens and copy still read it), and clears `legacyUntil` when the subscription carries `metadata.catalog = "licenses"` (every license checkout/update sets it).
- **Server** (`lib/billing/license-billing.ts`): `getLicenseState()` (mode, purchased, assigned, free, over-assigned), `checkLicenseAvailable(org, license)` (402 `limit: "licenses"`; legacy orgs fall back to the old `seats` check) used by invite, admin create and reactivate; `suggestedLicense()` (a free one, else the trial license); `applyLicenseChange(org, target)` (also the "pasar a licencias" path for legacy orgs); `changeUserLicense(org, user, to, {confirm, adjustBilling})` — `licenseChangeImpact()` warnings need `confirm`, nothing is deleted (the gates pause what the new license lacks), and with `adjustBilling` it buys/releases the Stripe lines first and aborts on `payment_pending`. Refused for legacy orgs (`code: "legacy"`).
- **Routes**: `POST /api/billing/checkout` takes `{licenses: {ESSENTIAL, BUSINESS, PRO}}` (still accepts `{plan, seats}`), validates every price, blocks below the assignment and warns about channels that would end up ownerless; `GET/POST /api/billing/licenses` (state / change the live subscription); `PATCH /api/usuarios/[id]/licencia`; `GET/PATCH /api/canales/dueno` (admin; current owner + candidates; P2002 ⇒ 409 "ya es dueña de un canal de este tipo"); invitations and `POST /api/usuarios` accept `license`; account list APIs return `owner`.
- **Screens**: `/configuracion/plan` → `_licencias.tsx` (a stepper per plan with "Todo lo de X, más…" from `LICENSE_FEATURE_NAMES`/`licenseAddedFeatures()`, monthly total, blockers linking to Usuarios, Checkout or update, AI credits per person); legacy orgs keep the old plan cards plus "Pasar a licencias". `/usuarios`: license badge per person and invitation, the licenses bar (assigned of purchased), a license picker when inviting/creating (`_licenses.tsx`) and the "Licencia" modal (`_license.tsx`, offers to buy one when none is free). Channel lists (WhatsApp, Telegram, Messenger, Instagram, web chat) show `ChannelOwnerBadge` ("Pro · Ana" or "Sin dueño · Básico") and "Dueño (licencia)" opens `ChannelOwnerModal`; the WhatsApp detail page has a "Dueño y licencia" section. `/plataforma` shows license counts per org, summed credits, and MRR from the license columns.
- **Verified** against Stripe **test mode** (2026-11-05): a 2 Básico + 1 Pro subscription synced to the columns; changing a person Básico→Avanzado with `adjustBilling` charged a 30 MXN proration and left 1/1/1; upgrade to 2 Pro, blocked downgrade below the assignment, downgrade back, and a legacy org converted (`legacyUntil` cleared); a 3+1+1 Checkout session with a deferred trial. Routes exercised with a real admin session (trial cap of 3, confirm warnings, owner assignment, 404 on another org's channel). Not done: a click-through in a browser and the Checkout → webhook round trip (dev has no webhook secret).
, `lib/billing/plans.ts` is the single place to change prices/limits; read by the plan screen, every gate, the public pages and the platform panel; since the license model, functions and quotas per license live in `licenses.ts` and the public offer is built from it in `app/(marketing)/_landing-offer-data.ts`). Price is MXN per user per month (`pricePerSeatMxn`): Básico 59 (ESSENTIAL), Avanzado 89 (BUSINESS), Pro 149 (PRO) — the Prisma enum ids never changed, only the public names. A seat = every active user (owner/admins included) + every pending invitation. `perSeat` allowances are **per user**: WhatsApp/Instagram are `included + 1 per extra seat` (Básico 1+1, Avanzado 3+1, Pro unlimited), contacts/activeLeads/AI credits are a flat number per user, Telegram/Messenger never cap. `perOrg` ones (active automations, API, webhooks, campaigns, bots, lead scoring, webchat, funnels 50, custom fields, AI agents) do not multiply. Everything is multiplied by `seatCap()` (internal ∞; `TRIALING` → `TRIAL_MAX_SEATS` = 3; otherwise `Organization.seatQuantity` = Stripe quantity). Básico has no bots, campaigns, automations nor lead scoring; Avanzado adds bots/campaigns/automations/webhooks; Pro adds lead scoring and the highest contact/credit pools. Tax wording is one switch, `PRICE_TAX_NOTE` (null: no IVA claims). New organizations start `TRIALING` on PRO for `TRIAL_DAYS` (14) without a card; in trial contacts/AI credits are the flat `TRIAL_POOL` (5,000 / 1,000) for the whole org, not × seats.

- **Rules are pure functions** in `lib/billing/state.ts` (unit-tested): `accessMode()` (`full` / `read_only` / `suspended` — a trial or grace period that already expired counts as read-only *immediately*, without waiting for the tick), `planLimits()` (internal orgs are unlimited), `billingNotice()` (banner), `tickTransition()`, `deriveFromSubscription()` (Stripe status → org fields: `active`/`trialing` → ACTIVE, `past_due`/`unpaid` → PAST_DUE with `GRACE_DAYS` (7) of grace, then READ_ONLY; `canceled` → CANCELED + `canceledAt`; `SUSPENDED` is never lifted by Stripe).
- **Gates** (`lib/billing/gates.ts`, 15s in-process cache of the org's billing row, invalidated on change): every 402 carries `code: "read_only"` or `code: "plan_limit"` (+ `limit`, `current`, `max`).
  - **Read-only** blocks writes, not reads: `proxy.ts` now also runs on `/api` and answers 402 to any non-GET from a session whose org isn't `full` (allowlist: `/api/auth`, `/api/billing`, `/api/usuarios`, `/api/whatsapp/notifications`); the public API allows only GET; **every low-level sender** (`sendWhatsAppMessage`, template/interactive, Telegram, Messenger/Instagram, `sendChannelReplyText`, `sendOutbound`, the webchat bot chunk) calls `assertOrgCanSend()`; and each worker skips gracefully before spending AI (bot workers ×3, humanized send, campaigns, scheduled campaigns, sequences, lead recovery, scheduled scoring, automation dispatch/tick, outgoing webhooks). Inbound messages keep being stored.
  - **Limits** are checked where the resource is created: `seats` (members + pending invitations: create, invite, reactivate, accept — the 402 carries `billingUrl` to `/configuracion/plan#asientos`), `whatsapp` / `instagram` (per-seat `includedPlus`: Básico 1+1, Avanzado 3+1, Pro unlimited; manual create + Embedded Signup — `WAAccount.userId` is who connected it, not the ejecutivo), `telegram` / `messenger` (unlimited in every plan, the key is checked anyway), contacts / `activeLeads` (public API create + campaign creation counts recipients that aren't contacts yet; inbound never gets dropped — the tick notifies admins once a month instead), `activeAutomations` (publish / PATCH to ACTIVE; Básico has 0), `aiAgents` (bot create), `funnels` (pipeline create), `customFields` (definition create), and API + outgoing webhooks (`apiAccess` is on all three plans today; `webhooks` starts at Avanzado). The feature flags (`campaigns`, `bots`, `leadScoring`, `aiAccess`, API, webhooks) are now checked through `entitlements.ts` (see "Per-user licenses" above); only `checkWebchatAccess` remains in `gates.ts`. Every per-seat limit is resolved against `channelSeatBase()` (trial → `TRIAL_MAX_SEATS`, never less than 1), not the raw seat quantity.
- **Stripe** (`lib/billing/stripe.ts`, configured from `/plataforma` — secret key, webhook secret, `stripePriceEssential`/`stripePriceBusiness` (column `stripe_price_basic`)/`stripePricePro` — never env vars, see "Development"): `POST /api/billing/checkout` (admin, verified email, `{plan, seats, confirm}` → one item with `quantity = seats` ≥ seats in use; during a trial with >48h left the first charge is deferred to the trial end via `trial_end`; opening a session expires the customer's other open ones so two can't be paid), `POST /api/billing/subscription` (change plan and/or seats of the live subscription — `lib/billing/seats.ts:applyPlanChange()`; going up (higher monthly total) is `always_invoice` + `pending_if_incomplete`, going down `create_prorations` (`stripe-rules.ts`). If the immediate charge fails Stripe does **not** apply the change (`pending_update` until the invoice is paid): the route answers 402 `payment_pending` with the invoice's `invoiceUrl`, never "updated". The idempotency key is origin→destination **plus a per-request id** — without it, 3→4→3→4 within 24 h replayed the first response and changed nothing; `state.ts:planChangeImpact()` blocks going below seats in use / WhatsApp numbers / the automations, funnels or custom fields the target plan allows, and asks `confirm` for losses such as API/webhooks), `POST /api/billing/portal` (card/invoices/cancel), `POST /api/billing/webhook` (signature on the raw body; every relevant event re-reads the subscription with `syncSubscription()`, so event order doesn't matter; `StripeEvent` dedupes by `event.id`; if an organization ends up with two live subscriptions the newest wins, events of the older one no longer overwrite it, and `PLATFORM_ADMIN_EMAILS` get an email to cancel/refund it by hand). **Exercised end-to-end in Stripe test mode** (2026-10-29: checkout 4 seats, upgrade 4→5, downgrade 5→4, plan swap BUSINESS↔PRO, proration and all webhooks); **live still pending**. Prices: the price IDs configured in `/plataforma` win; the lookup keys `colibly_esencial_monthly`/`colibly_negocio_monthly`/`colibly_pro_monthly` are only the fallback. `lib/billing/stripe.ts:planPriceError()` rejects before checkout or a plan change if the resolved price's amount/currency/interval doesn't match `lib/billing/plans.ts` (59/89/149 MXN monthly per user), answering 503 `price_mismatch` — this caught a real catalog with old 99/199/349 prices under the canonical keys. Test with test-mode keys (webhook endpoint or `stripe listen`) before going live. Without that configuration the routes answer 503.
- **Tick** `billing-tick` (hourly at :07, `lib/billing/tick.ts`): expired trial/grace → READ_ONLY with notice; "trial ends in N days" (7, 3, 1: `TRIAL_REMINDER_DAYS`) once per day; with a failed payment, "read-only in N days" (3, 1: `PAST_DUE_REMINDER_DAYS`, keys `past_due:N`) besides the notice when it fails — both point to "Administrar facturación" (Stripe portal) to change the card; contact limit reached once per month; **purge** (`purgeDue()`, 5 per tick — what the terms and privacy notice promise; it didn't exist until 2026-09-27) of organizations `CANCELED` for `RETENTION_DAYS_AFTER_CANCEL` (60) days and of **expired trials that never paid** (`READ_ONLY` with no `stripeSubscriptionId`) `RETENTION_DAYS_AFTER_TRIAL` (60) days after `trialEndsAt`. A `READ_ONLY` org *with* a subscription (unpaid) is never purged this way — Stripe decides (it recovers or ends `CANCELED`). The trial-ended notice, the plan screen and both legal pages state the retention. `Organization.lastBillingNotice` + an atomic claim keep notices from repeating. Notices (`lib/billing/notify.ts`) go to the bell (`NotificationType.BILLING`) and by email to active admins.
- **UI**: `/configuracion/plan` (admin only — blocked for `user`/`ejecutivo` in `proxy.ts`): status, seats used/paid, price per user and monthly total, usage bars vs pooled limits, plan cards + seat stepper (`#asientos`) → Checkout or `/api/billing/subscription`, with the same `planChangeImpact()` blockers/warnings shown live; "Administrar facturación" → Portal. The dashboard layout shows a `BillingBanner` only for notices that need action now (admins: trial with ≤ 3 days / past due / read-only / canceling; others only when the account no longer works); a trial with more days left is a neutral `TrialCard` (`app/components/billing/trial-card.tsx`, "Prueba Pro · quedan N días" + 4 px bar + "Elegir plan") at the foot of the sidebar, which phones see inside "Más" (D-01, 2026-11-14).
- **Your data** (bottom of `/configuracion/plan`, `_datos.tsx`): **export** — `GET /api/organizacion/exportar` (any admin, 5/h), one streamed JSON (`lib/org-data/export.ts`: users, accounts, contacts with tags/custom fields/notes/appointments, every conversation with its messages; never secrets, hashes or media files). **Delete** — `DELETE /api/organizacion` (owner only, confirms with the org name + password): `lib/org-data/delete.ts:deleteOrganizationData()`, shared with the purge. It cancels the Stripe subscription first (if that fails nothing is deleted; the Stripe customer is kept for invoices), deletes the org (every required relation cascades — keep it that way for new models: a relation without `onDelete: Cascade` makes deletion fail), plus what cascade can't reach: RAG chunks (`WABotKnowledge`, linked only through the join table) and the media folders (`MEDIA_ROOT/<accountId>`, `removeAccountMedia()`). `/api/organizacion` is in `READ_ONLY_ALLOWED`: a read-only or canceled org can still leave. Internal orgs can't be deleted. Verified 2026-09-27 with a populated org: every table back to its exact row counts.

## Activation (since 2026-11-05)

Know how far each new organization gets and nudge it when it stalls. Code: `lib/activation/` (`rules.ts` pure + tests, `tick.ts`, `report.ts`, `unsubscribe.ts`).

- **`OrgActivation`** (1:1 with `Organization`, cascade): one-shot stamps with the date of the *first real fact* — `emailVerifiedAt` (owner), `channelAt` (first `WAAccount`/`ChannelAccount`), `firstInboundAt` (first inbound; WhatsApp `origin: API` only, so coexistence history doesn't count), `firstReplyAt` (first outbound by a person or the bot: `senderId` or `sentVia` agent/bot), `automationAt` (first `WABot`/`Automation`), `teamAt` (second member or an invitation), `paidAt` (first time the tick sees `ACTIVE` + subscription). Stamps never get erased, even if the account/bot is deleted later.
- **Tick**: `processActivationTick()` runs inside the `billing-tick` job, after `processBillingTick()` (its errors don't retry billing). It follows non-internal orgs created in the last `ACTIVATION_WINDOW_DAYS` (120): creates missing rows, fills only the empty stamps (aggregate `MIN`, never `findFirst` + `orderBy createdAt`, which can scan the whole `createdAt` index for an org without messages), 100 per tick, oldest `checkedAt` first. The first pass backfills history with real dates.
- **Nudges** (`nextNudge()`): one email to the **owner** at most every 48 h, each key once, only `TRIALING`, owner verified and not disabled, not opted out, never on a `TRIAL_REMINDER_DAYS` day nor once the trial is over. Order: `channel` (24 h without a channel — the only nudge until they connect) → `first_message` (channel 24 h old, no inbound) → `automation` (day 3+) → `team` (day 5+, after a first reply). Atomic claim on `lastNudgeAt` + `nudgesSent`. Template `activationNudgeTemplate()`.
- **Opt-out**: every nudge carries `List-Unsubscribe` + `List-Unsubscribe-Post` (RFC 8058) to `/api/correos/consejos/baja?o=<orgId>&s=<HMAC(AUTH_SECRET)>`. GET only shows a confirmation page (mail scanners open links); POST sets `nudgesOptOut`. Only nudges stop; account and billing notices keep coming.
- **Funnel**: `/plataforma` → "Activación" (`GET /api/plataforma/activacion?dias=7|30|90`, operators only): count, % of signups, % of the previous step and median time per step, plus the trialing orgs sorted by least progress / least trial left, with the nudges sent and a mailto to the owner. Each step counts whoever reached it even if they skipped an earlier one.

## Prueba sin canal: bolsa de mensajes de IA de prueba (2026-11-10)

Una organización en `TRIALING`, no interna y **sin ningún canal** (0 `WAAccount` y 0 `ChannelAccount`) paga lo que **pide una persona** (probar el bot, simular una automatización, el asistente de escritura) con una bolsa de la ORGANIZACIÓN de `TRIAL_AI_TEST_CREDITS = 10` (`plans.ts`, junto a `TRIAL_DAYS`), `Organization.trialTestAiUsed`. No toca los créditos personales. Al conectar el primer canal aplican los de siempre (`TRIAL_AI_CREDITS_PER_USER`, 500 por persona), sin tocar la bolsa.

- `lib/billing/trial-test.ts`: modo (`isChannellessTrial`), reserva atómica (`updateMany` con tope) y reembolso si el proveedor falla.
- `lib/ai/credits.ts:reservePersonAiCredit(userId, orgId)` decide entre la bolsa y `reserveAiCredit({ userId })`. **Los workers y todo lo automático siguen con `reserveAiCredit`** (nunca pasan por la bolsa). Un uso nuevo de IA que pide una persona usa `reservePersonAiCredit`.
- Agotada: 402 `code: "trial_test_exhausted"` con `actionUrl: /whatsapp/cuentas`; `GET /api/whatsapp/bots/[id]/test` y la respuesta del POST traen `testCredits { used, max, remaining, mode }`.
- Aviso del plan: `lib/billing/banner-copy.ts` (textos y reglas del cierre); el admin ve también los días de prueba que quedan; info y warning se pueden cerrar (sessionStorage por día), el rojo no.
