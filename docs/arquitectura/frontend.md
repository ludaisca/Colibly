# Frontend: quirks de Next, Server Components y design system

> Detalle técnico movido desde `AGENTS.md` (2026-11-01). Las reglas esenciales siguen en [`AGENTS.md`](../../AGENTS.md) y [`CLAUDE.md`](../../CLAUDE.md); aquí está el detalle completo. Mantén este archivo al día en el mismo cambio que el código.

## Framework quirks

- `proxy.ts` IS the middleware — Next.js 16 convention. Not `middleware.ts`
- `params` in page/layout props is `Promise<>` — must `await` before destructuring
- Server Components **cannot** pass Lucide/React components to Client Components as props. Error: "Functions cannot be passed directly to Client Components". Fix: convert the page to `"use client"` or render icons inside the client boundary. This includes `<Button icon={SomeIcon}>` written directly inside a Server Component — extract it into a small `"use client"` wrapper (e.g. `whatsapp/_add-account-button.tsx`) instead.
- `rm -rf .next` after adding/removing routes (stale Turbopack cache causes 404s/500s). In dev `.next` is the **named volume `next_cache`**, so deleting the directory itself hits a busy mount point: stop the app and clear the volume contents instead — `docker compose stop app && docker run --rm -v colibly_next_cache:/cache alpine sh -c 'rm -rf /cache/* /cache/.[!.]*' && docker compose start app`. The same stale cache can show up as an **infinite reload loop**: Turbopack keeps sending `restart` for the same chunk (`_1anvha4rlo79g._.js` or similar) with `next-server` burning CPU and `GET /` every ~300 ms in the log; clear the volume as above. **After a container recreate (e.g. adding a new volume), Turbopack's server-side chunk cache may not invalidate the client chunk unless you also do a hard refresh in the browser with DevTools "Disable cache" enabled** — HMR cannot bridge that gap; the client keeps loading the stale on-disk chunk with HTTP 200 (from disk cache) instead of asking for a fresh one.
- Pages using `useSearchParams()` must be wrapped in `<Suspense>`. See `app/(auth)/login/page.tsx` for pattern.
- Media URLs in chat UI are **server-proxied**, never raw Meta URLs. Always render `<img src=\`/api/whatsapp/messages/${msg.id}/media\`>` (or `<audio>`/`<video>`/download link). The endpoint authenticates via `getUserAccountIds` and streams bytes from `/app/media`. Never expose Meta's short-lived download URLs to the browser.
- `app/components/ui/modal.tsx`'s `visible` state must be initialized from the `open` prop (`useState(open)`), not `useState(false)` — the old code only flipped `visible` true on an `open: false→true` *transition*, so a modal mounted with `open={true}` from the start (e.g. reached via a `?param=1` URL instead of a button click) never became visible. Any new "auto-open via URL" modal pattern relies on this fix already being in place.
- Tailwind's `dark:` variant does **not** track this app's own light/dark toggle — this project uses a custom token system (`.light` class override on top of dark-by-default `:root` tokens in `app/globals.css`, no `@custom-variant dark` defined), so `dark:` falls back to Tailwind v4's default `prefers-color-scheme` media query, which reads the OS setting instead. Never use `dark:` classes; use the semantic tokens (`bg-surface`, `text-foreground`, etc.) which already respond correctly to the app's toggle. Exception: components that must always render in a *fixed* palette regardless of the app's theme (e.g. `<TemplatePreview>`, which mimics WhatsApp's own light chat UI) should hardcode their colors rather than use either `dark:` or the app's tokens.

### Server Components for top-level pages

`dashboard/page.tsx` and `estadisticas/page.tsx` are Server Components: they call `await auth()` + Prisma directly instead of `fetch()`-ing their own API routes (avoids a redundant HTTP round-trip). Reuse `getUserAccountIds()`/the same `where` clauses as the equivalent API route so the data scope doesn't silently diverge between the RSC and the JSON endpoint other pages still call.

Because `<Table>` (and any component using `render: (row) => JSX`) is `"use client"`, a Server Component **cannot** build its columns inline — that hits the "functions cannot be passed to Client Components" error. The fix used here: split into `page.tsx` (Server Component, fetches data) + `_view.tsx` (`"use client"`, receives the fetched data as a plain serializable prop and owns the `<Table>`/column definitions). See `estadisticas/page.tsx` + `estadisticas/_view.tsx`.

`lib/estadisticas/get-stats.ts` (`getEstadisticas(userId)`) feeds `estadisticas/page.tsx` directly (in-memory cache, 60s TTL, keyed by `userId`). The old `app/api/estadisticas` GET route was removed (2026-07) — it had no consumers; if an external integration ever needs stats over HTTP, re-add a thin route that calls `getEstadisticas()`. Global counters (accounts/chats/messages/bots/campaigns) shared by `/dashboard`, `/whatsapp` hub and `get-stats.ts` live in `lib/estadisticas/global-counts.ts` — always extend that module instead of re-writing the count queries inline, so the shared-accounts scope can't diverge between screens. `monthlyCost` reuses `lib/ai/budget.ts:getOrgAiCost()` (the platform's estimated AI cost for the organization — never reimplement that aggregate); the AI card shows the org's credits (`aiCredits`), not a USD budget.

RSC pages should have a sibling `loading.tsx` with skeleton placeholders — Next.js streams this automatically while the async page fetches data.

## Polling (`usePoll`)

Everything live is polled (no websockets) through `app/components/ui/use-poll.ts:usePoll(poll, { intervalMs, hiddenMs?, maxIntervalMs?, immediate?, enabled? })`: it schedules the next tick only after the previous one finishes, skips (or slows to `hiddenMs`) while the tab is hidden and fires immediately on return, and stretches the interval ×3 after 2 min and ×6 after 10 min without user activity (capped at `maxIntervalMs`), firing again on the first interaction. `poll` gets `{ hidden }`. Users today: the inbox sync, the bell, `ChatBotMode`, the live reports panel. The server side of a polled GET answers with `lib/http/etag.ts:jsonWithEtag()`. Detail and numbers: `docs/RENDIMIENTO_2026-11-04.md`.

## Design system

All tokens in `app/globals.css` as CSS custom properties, in **two layers** (since 2026-09-27; **"Laguna + coral" since 2026-10-25** — blue-teal accent `#0E7490`, coral `#C21E4C` as `--accent-2`, cyan `#67E8F9` decorative only, cool grey neutrals without sky tint; replaced Laguna monocroma 2026-10-24, which had replaced "Menta y grafito" green `#0F766E` and "Colibrí" violet): **primitives** (`--teal-*`, `--coral-*`, `--graphite-*`, `--ink-*` neutrals, `--green/orange/red/blue-*`) are only referenced inside `globals.css`; **semantic tokens** (`--accent`, `--surface`, `--muted`, `--success`…) are what components use through Tailwind utilities. Change a color by repointing a semantic token, never by adding hex in a component. The same palette in hex for what can't read CSS (emails, generated images, favicon, the webchat widget) lives in `lib/brand-colors.ts` — change both together. Lab notes: `docs/COLOR.md`.
- **The accent keeps four roles** (born when the accent was yellow and couldn't be text; components depend on the names): `bg-accent` (fills: primary button, switch, active nav, progress) always with `text-on-accent` (white); `text-accent-ink` for brand-colored text/icons/links; `border-accent-strong` / `ring-accent-strong` / chart strokes (`var(--accent-strong)`) for selected borders, focus and lines; `bg-accent-subtle` (soft fills, selected rows) and `accent-muted` (decorative borders, focus halos, hover fills, own chat bubbles). **Never `text-accent`, and never opacity modifiers on the accent** (`bg-accent/10`, `border-accent/30`) — use the named tokens.
- `--accent-2` is coral (`--coral-600` `#C21E4C`) for secondary icon tones and highlights — not a CTA color. Status text colors are darkened to pass AA on their own `-bg`.
- **Contrast is tested**: `lib/design/__tests__/contrast.test.ts` resolves the `:root` tokens (`lib/design/contrast.ts`) and checks every text/background pair (4.5, or 3 for borders/focus). Add a pair there when you add a semantic token.
- The logo is `BrandMark` (`app/components/ui/logo.tsx`, Nexo mark colored by tokens), used by `Logo` and the app shell; see "Brand and public site".
- **Two themes**: primitives live in `:root`, light semantics in `:root, .theme-light`; `.dark` (set on `<html>` by `app/components/theme-provider.tsx` — own provider since 2026-11-08, replacing next-themes; the init script lives in the root layout's `<head>`, same `theme` localStorage key. Next 16.4 serves every `notFound()` as an error document rendered on the client (`<html id="__next_error__">`, even in production), so that script never runs there: `useApplyStoredTheme()` in `Providers` applies the saved theme on mount, and React's dev-only "script tag" warning on those pages is expected; since 2026-11-01 **AMOLED**: `--background` pure `#000`, neutral greys without the old blue tint, surfaces barely above black so hierarchy comes from borders — shadows include a faint 1px white ring because black shadows vanish on black; accent fill `#0E7490` still with white text, coral `--accent-2` lightened) redefines only the semantic layer, plus a `.dark .hue-N` set. **There must be exactly one `.dark {` block**: a duplicate existed until 2026-09-27 — the browser applies the last one while the contrast test reads the first, so a palette change could ship untested. **Marketing and the panel share the same toggle** (`ThemeToggle` in the public header and in `app-shell`); default remains `light`. Gradients/decors on the landing must use semantic tokens (`--background`, `--accent-subtle`, `--accent-2-bg`…), not light-only primitives (`--ink-25`, `--teal-100`), or they ignore `.dark`. `.theme-light` still exists for surfaces that must stay light (e.g. public status pages). The contrast test runs every pair in both themes. Text that sits on a solid status/secondary fill (`bg-danger`, `bg-info`, `bg-warning`, `bg-accent-2`) uses `text-surface`, which flips correctly per theme; own chat bubbles are `bg-accent-muted text-foreground` for the same reason.
- **Bubble corner retiring**: `rounded-bubble`/`rounded-bubble-br` (defined as `@utility` in `globals.css`) was the previous redesign's signature corner, whitelisted to `EntityAvatar`, primary `Button`, the active sidebar item, and own chat bubbles. All four have migrated to generous standard corners + soft shadow instead (`EntityAvatar`/`Button` → `rounded-lg`/`rounded-xl`, sidebar active item → `rounded-full` solid pill, chat bubbles → `rounded-2xl` with one corner squared via `rounded-tr-sm`/`rounded-tl-sm`). The utilities stay defined for now — **don't add new usages**; if you find one outside those four call sites it's leftover drift, migrate it the same way.
- **Per-entity hue**: 8 `.hue-0`…`.hue-7` classes set `--entity`/`--entity-bg` (oklch, lighter set under `.dark`; hues avoid success-green ~140°), consumed via `bg-entity`/`text-entity`/`bg-entity-bg` utilities. `--entity-bg` mixes against `var(--surface)` (not `transparent`) so the tint stays visible on the new near-white surface. **Only** assign via `HUE_CLASS[hueIndex(id)]`/`hueClassFor(id)` from `app/components/ui/hue.ts` (hash keyed by `accountId` so one WhatsApp number = one color everywhere) — never interpolate `hue-${n}`.
- **Type scale**: `text-hero` (2.75rem, hero numbers), `text-page-title` (h1, rendered via `PageHeader`), `text-eyebrow` (section eyebrows). Display/body fonts are **Barlow Condensed** (`--font-display`) / **Barlow** (`--font-body`) everywhere since 2026-11-08 (Andén); Newsreader + Figtree (2026-10-25) are no longer loaded — see `docs/TIPOGRAFIA.md`. IBM Plex Mono was dropped; `font-mono` is a **temporary bridge** aliased to the body font while remaining shared components migrate off it; figures/phones/dates use `tabular-nums` plus a weight class, not `font-mono` — already done in `KpiStrip`, `dashboard/page.tsx`, `chat-composer.tsx`, `estadisticas/_view.tsx`/`_charts.tsx`, `contactos/page.tsx`.

**Never** write inline button/card/input classes. **Never** use Tailwind color literals. Use semantic tokens: `text-accent`, `bg-surface`, `text-muted`, `text-success`, etc.

Form pattern: `<FormField label="…" error={…}>{(id) => (<Input id={id} … />)}</FormField>`

Toast: `const { success, error } = useToast()` → `success("text")`

Three select flavors in `app/components/ui/` — pick by need, don't build a fourth: `select.tsx` (styled native `<select>`, short lists), `multi-select.tsx` (multi-select with removable chips, on Base UI `Combobox` `multiple`; typing filters), `searchable-select.tsx` (`SearchableSelect`, single-select on Base UI `Combobox` with the search input inside the popup; it only starts filtering at ≥3 chars — below that the full list stays visible; used for long lists like the template picker in `campanas/nueva`).

**Type floor (2026-11-07).** `text-micro` (0.6875rem / 1rem, `globals.css` `@theme`) is the smallest size in the panel: metadata, badges, counters. Don't write `text-[10px]`-style sizes: 9–11px → `text-micro`, 12 → `text-xs`, 13 → `text-sm`, 15 → `text-base` (99 replaced in 40 files; CSS files use `var(--text-micro)` / rem). The public site (`app/(marketing)`) has its own display ramp (`DESIGN.md` → "El sitio público") and the same 11px floor.

**Tabs (2026-11-07).** `ui/tabs.tsx`: `Tabs` (Base UI; same API the old `HeroTabs` had: `items`, `value`, `onChange`, `label`) with the active tab in ink and only the active panel rendered. Page-level tabs live in the URL (Web Design Guidelines): `const [tab, setTab] = useUrlTab(ids, fallback)` reads/writes `?tab=` with `router.replace` (the default tab leaves the URL clean; other params are kept) and **skips the navigation when the URL wouldn't change** — without that guard a repeated `onValueChange` caused a request loop. The page must be inside `<Suspense>` (`useSearchParams`). Used by Campañas, Calificadores, Bots (detail), Plataforma and API (via `DetailPage`); the contact drawer keeps its own `?` handling. **HeroUI, `react-aria-components` and `@internationalized/date` are gone** from the project.

**Dates (2026-11-07).** One calendar for everything: `ui/calendar.tsx` (ported from Tesela's `tsl-calendar`; pure logic in `lib/format/calendar.ts`, tested). `ui/date-picker.tsx` exports `DatePicker` (single date, same props as before) and `DateRangePicker` (`{ value: {start,end}, onChange, label }`, replaces `HeroDateRange`; two months from 640 px). Values are ISO `AAAA-MM-DD` built in local time; display uses `Intl.DateTimeFormat("es-MX", { dateStyle: "medium" })` with a fixed locale so server and browser agree. Keyboard: arrows, Home/End, PageUp/PageDown (Shift = year), roving tabindex; selection in ink (Andén). Typing a date by hand was dropped: the calendar covers it by keyboard.

**Tooltips (Base UI, 2026-11-07).** `ui/tooltip.tsx` (`<Tooltip label side?>{<button aria-label=…/>}</Tooltip>`) replaces the native `title` on controls: it shows on keyboard focus too, stays on screen and follows the theme. Rules: an icon-only control always carries its own `aria-label` (the tooltip is visual help, never its name); don't wrap a `Dropdown` trigger (its `aria-label` is enough); in a `.map()` the `key` goes on the `Tooltip`. `title` stays only on non-interactive truncated text (`span`, `p`, `td`). The collapsed sidebar shows each section's name as a tooltip (`side="right"`).

**Clickable rows (2026-11-07).** `Table` and `EntityList` share `ui/row-activation.ts`: an activable row is focusable (`tabIndex=0`, inner focus ring via `[data-row]` in `globals.css`) and opens with Enter/Space. A row that **navigates** passes `rowHref={(row) => url}` instead of `onRowClick={… router.push …}` so it behaves like a link (Ctrl/⌘/Shift+click and middle click open a new tab). A click that starts on a control inside the row (button, link, checkbox, menu) or inside a portal (row-action menus, dialogs — React events cross portals) never opens the row, so per-cell `stopPropagation()` is no longer needed. The row has no `role="button"/"link"` on purpose: it contains other controls.

**Small controls (2026-11-07).** Before writing a `<button className=…>`: text action → `<Button variant="link" | "link-danger" size="sm">` (no box, `sm` = `text-xs`); icon-only → `<Button variant="ghost" size="icon" icon={X} aria-label=…>` (32 px); exclusive options for a view or filter → `ui/segmented.tsx` (`<Segmented label value onChange options>`, active option in ink); on/off state of an entity → `Switch`; `Banner` retry → its `action` prop. Busy icon for `Button`/`DropdownItem` → `SpinningLoader` (`ui/spinner.tsx`). Items inside a `Dropdown panel` are `DropdownItem` (it renders a plain button there). `Select compact` is the 32 px / `text-xs` version for cards. Native buttons stay only in bespoke surfaces: inbox list and board header, composer toolbar, message bubbles (transcribe, reactions), flow-builder canvas (own CSS), selectable tiles/options in pickers, chip-remove ✕, drag handles and titles that act as buttons.

**Dates, times and focus rings (2026-11-07, screen review).** No native `type="date"`/`datetime-local`/`time` in the panel: Chrome draws them in US format (`mm/dd/yyyy`) whatever the app language. Date → `DatePicker`; period → `DateRangePicker` (`clearable={false}` when the period always has a value; picking the last day applies it); date + time → `DatePicker` + `ui/time-select.tsx` (`TimeSelect`, `HH:MM`, 15-min steps, es-MX labels) over one local `"AAAA-MM-DDTHH:MM"` string, converted with `new Date(local).toISOString()` **before sending** — a bare `AAAA-MM-DD` is read by the server as UTC midnight (18:00 the day before in Mexico; that bug shipped in campaign scheduling). "Today" in the browser is `localISODaysAgo()` (`lib/format/calendar.ts`), never `toISOString().slice(0, 10)`. Focus: the global `:focus-visible` outline is the ring for buttons and links; a control that draws its own ring (fields, `DatePicker`/`SearchableSelect` triggers, chat composer inputs) carries `data-focus-ring` so the global outline steps aside — one ring, never two. The global rule no longer forces a `border-radius` (it squared pills and switches on focus). `Switch` requires `label` (its accessible name).

**Copy helpers (2026-11-07, screen review).** Counts go through `plural(n, "chat")` / `plural(n, "canal", "canales")` (`lib/format/plural.ts`) — never `chat(s)` or a fixed plural. Template language/category are shown with `templateLanguageLabel()` / `templateCategoryLabel()` (`lib/whatsapp/template-labels.ts`), never Meta's codes; IANA zones with `timeZoneLabel()` (`lib/format/time-zone.ts`); "Channel · Account" with `channelAndAccount()` (`lib/chats/display-name.ts`), which drops the account when it repeats the channel. The channel owner is "titular" in customer-facing text. Chart series use `--chart-1…4` (`globals.css`, light and dark), never hex in a component and never amber/red (those are the waiting lamps); per-account bars use `EntityBars` (`estadisticas/_charts.tsx`) with `hueClassFor`. The 8 account hues are 45° apart. If a `globals.css` change doesn't reach the browser, clear the `next_cache` volume (seen 2026-11-07: new custom properties missing from the served CSS).

**Lead status (2026-11-07).** A lead's status is a station of the sales route, never a status color: `LeadStatusBadge` / `StationMark` (`ui/lead-status.tsx`) over the pure `leadStation()` / `stageStation()` (`lib/pipeline/stages.ts`, tested) — neutral with filled dots, success only for Cliente/won, Perdido muted without dots. Pipeline columns all use `STAGE_COLUMN_CLASS`; the old `STAGE_COLOR_*` / `stageChrome` (blue/amber/teal/green/red) are gone. Amber/red stay for waiting, SLA and real errors only.

**Account hues without collisions (2026-11-07).** The plain hash (`hueIndex`) put two accounts of the same organization on the same hue 1 time in 8. `assignAccountHues()` (`ui/hue.ts`, tested) walks the org's accounts (WhatsApp + channel) oldest first: each keeps its hash hue if free, else the next free one — adding an account never recolors older ones; past 8 the hues recycle. `lib/accounts/hues.ts:getOrgAccountHues(orgId)` (React `cache`) runs in the dashboard layout and reaches the client through `AccountHuesProvider` (in `DashboardShell`); components read it with `useHueClass()`, server components with `hueClassIn(map, id)`. A brand-new account uses its hash hue until the next navigation reloads the layout. `EntityAvatar` is a client component because of this.

**Overlay.** Modals, drawers and the command palette share the `--overlay` token (`globals.css`); don't hard-code a backdrop color.

**Menus and floating panels (Base UI, 2026-11-07).** `dropdown.tsx` keeps its API but no longer positions anything by hand. `<Dropdown>` is an **action menu** on Base UI `Menu` (roles `menu`/`menuitem`, arrows, Home/End, typeahead, Escape, focus back to the trigger, collision-aware placement, always portalled). Its children are `DropdownItem` (becomes `Menu.Item`; `keepOpen` to not close), `DropdownDivider`, `DropdownLabel` or plain text. `<Dropdown panel panelLabel="…">` is a **panel with its own content** (search, fields, several actions per row) on Base UI `Popover`; inside it `DropdownItem` is a plain button. Rule: if the content has an input or more than one control per row, it's a `panel`. The trigger is used as-is when it is a native `<button>` or a `DropdownButton` (now a real `forwardRef` button); anything else gets wrapped in an unstyled button. `portal` is accepted and ignored. `user-dropdown.tsx` is a Base UI `Menu` with `RadioGroup` (availability), `CheckboxItem` (push) and `LinkItem`. The global `:focus-visible` rule in `globals.css` is unlayered, so it beats Tailwind's `outline-none`: an input whose container draws the focus ring sets `style={{ outline: "none" }}`. `pagination.tsx` (`<Pagination currentPage totalPages onPageChange>`) is the shared pager for client-side paginated lists.

### Layout: workbench (overview pages) + `EntityList` (entity lists)

The 2026-07 redesign replaced the old BentoGrid/TileGrid tile system (deleted: `bento-grid.tsx`, `tile-grid.tsx`, `stat-card.tsx`, `SkeletonCard`) with an editorial "workbench" layout. Primitives, all in `app/components/ui/`:

- **`kpi-strip.tsx`** (`KpiStrip`, `KpiItem`) — grid of bordered, shadowed cards (2 cols mobile, 4 on `lg:+`; was a flat divided row pre-"fresco y cercano"). - **`section-header.tsx`** (`SectionHeader`) — eyebrow (uppercase `text-eyebrow`) + display-font (Barlow Condensed) title + optional `action` ReactNode. Sections separate by typography, not bordered cards. Server-safe.
- **`workbench.tsx`** (`Workbench`/`WorkbenchMain`/`WorkbenchAside`) — the `lg:grid-cols-3` editorial split (main 2/3 + aside 1/3, collapses to 1 col below `lg`). Server-safe.
- **`avatar.tsx`** (`EntityAvatar`) — initials avatar, `rounded-lg`, hue keyed by `id` (pass `accountId` for anything WhatsApp-scoped so one number = one color across inbox/lists/overviews). Server-safe.
- **`entity-list.tsx`** (`EntityList` + `EntityRow`, `"use client"`) — dense database-style rows replacing TileGrid on entity list pages (Contactos, Plantillas, Bots, Campañas ×2 tabs, Usuarios). **Same contract TileGrid had** (`rows`/`rowKey`/`loading`/`error`/`onRetry`/`emptyIcon`/`emptyTitle`/`emptyDescription`/`emptyAction`/`onRowClick`/`rowActions`, reusing `ListErrorState`/`EmptyState`/`SkeletonRow`), with `renderTile`→`renderRow` and no `columns`. `rowActions` renders inside the same `Dropdown` (row activation ignores clicks from controls and portals), revealed on hover/focus on `md:+` and always visible on touch. For inline (non-dropdown) per-row actions, return a fragment from `renderRow`: `<><EntityRow …/><span onClick={stopPropagation}>…buttons…</span></>` (see Bots/Usuarios/Campañas). `EntityRow` gives the standard anatomy: `leading` (usually `EntityAvatar`), `title`, `subtitle`, `badges`, `meta` (right-aligned, hidden below `sm`, figures in `font-mono`). No sort headers — pages needing ordering keep a toolbar `<Select>`.

Overview page shape (see `dashboard/page.tsx`, `estadisticas/_view.tsx`): `PageHeader` → `KpiStrip` → `Workbench` with `SectionHeader`-separated sections. **No entrance animations** in the panel (D-07, 2026-11-14: `animate-fade-in-up`, `animation-delay-*` and the page fade were removed): only 120 ms color transitions and menu/modal opening. `loading.tsx` files mirror the same skeleton shape — update them in the same change as their page.

The `mx-auto` is mandatory whenever a page root sets a `max-w-*`; text inside stays left-aligned.

`table.tsx`/`<Table>` is **not deprecated** — still the right tool for dense multi-column numeric reports; used inside workbench sections in `estadisticas/_view.tsx` (campaign breakdown, bot usage, agent performance).

`app/components/ui/page-header.tsx` (`title`/`description`/`actions`) renders the h1 in `font-display text-page-title` (Barlow Condensed). Use it on every top-level list/dashboard page; detail pages with a back-link (`bots/[id]`, `campanas/[id]`, `cuentas/[id]`) keep their own back-link + heading instead.

### Create/edit modal pattern

Standard entity CRUD lives in a `_form.tsx` file next to the list's `page.tsx`, exporting a single `<XxxFormModal open onClose onSaved initialData? />` that handles both create and edit (`initialData` present ⇒ edit). Structure: `<Modal size="md|lg|xl" footer={Cancelar/Guardar}>` + `{error && <Banner tone="danger">}` + `<FormField>` blocks. See `whatsapp/plantillas/_form.tsx` as the reference implementation.

**Modal vs. drawer vs. inline (2026-11-07, Impeccable: "no modal for a task that needs neither interruption nor protected focus").** `Modal` runs on Base UI `Dialog` (`kind="alert"` → `AlertDialog`, used by `ConfirmDialog`; no outside-click close). On phones a dialog is a bottom sheet. Pick:
- `<Modal>` — short create/edit (≤5 fields) and anything that must interrupt: one-time secrets (`persistent`), security, irreversible actions, a blocking step ("Completa antes de resolver"), the media viewer.
- `<Modal layout="drawer">` — forms of 6+ fields and read-only detail panels: right-side panel on desktop (width from `size`: md 480, lg 560, xl 720), full screen on phones. 18 today (bots, secuencias, citas, Meta Ads, agregar número, nuevo usuario, calificadores, webhooks, API keys, atributos, campos, equipos, plataforma, reportes, detalle de calificación, "Agregar paso").
- Inline — a single field (e.g. "Guardar vista" inside the Vistas panel).
Both layouts set `overscroll-behavior: contain`. The full classification is in `docs/INVENTARIO_MODALES_2026-11-07.md`.

Exceptions that stay as a dedicated page instead of a modal:
- Unbounded dynamic content (`whatsapp/campanas/nueva` — recipient list can grow to hundreds of rows via CSV import; doesn't fit a modal's `max-h-[90vh]`).

Account creation (`whatsapp/cuentas/_form.tsx:CuentaFormModal`) follows the standard modal pattern but has a two-step render: the create form, then (on success) a read-only "here are your values" step showing the webhook URL and the auto-generated verify token — `verifyToken` is never typed by the user and never stored in plaintext (`WAAccount.verifyTokenHash` only), so that success step is the *only* place it's ever visible. External entry points link to `/whatsapp/cuentas?nueva=1`, which auto-opens the modal (`cuentas/page.tsx` reads the `nueva` search param into the modal's initial `open` state — wrapped in `<Suspense>` per the `useSearchParams()` rule above).

### Componentes portados de Tesela (2026-11-01)

Tesela (`/data/Proyectos/Tesela`, biblioteca propia de Custom Elements) **no se importa**: tiene su propio sistema de tokens (`--tsl-*`). Se portan componentes puntuales a React con los tokens de Colibly:
- `ui/otp-input.tsx` (de `tsl-otp`): casillas por dígito, avanza solo, Retroceso/flechas, pegar o autocompletar (`one-time-code`) reparte el código, `onComplete` al llenar la última. - `ui/currency-input.tsx` (de `tsl-currency`): importe en MXN con miles mientras se escribe, cursor estable, coma del teclado numérico como punto, ↑/↓ por `step`, decimales al salir. Lógica pura en `lib/format/currency-input.ts` (con tests); `amountValue()` da el valor canónico. Se usa en el valor del trato de la ficha.

- `ui/context-menu.tsx` (patrón `context-menu-nested`): menú de clic derecho y pulsación larga (500 ms en táctil) con submenús, sobre `@base-ui/react/context-menu`. API por datos (`items: ContextMenuEntry[]`: item con `icon`/`checked`/`danger`, `separator`, `label`, `submenu`); el trigger se compone con `render` sobre el hijo (sin envoltorio, conserva su `ref`, p. ej. el de dnd-kit). Ignora el click que el navegador dispara al soltar la pulsación larga; `nativeWhenTextSelected` deja el menú del navegador si hay texto seleccionado dentro. **Regla: es un atajo** — todo lo que ofrece existe también en un botón visible. No se agrega a tablas que ya tienen sus botones a la vista.
- `ui/format-toolbar.tsx` (patrón `floating-toolbar`): barra flotante sobre un `<textarea>` cuando hay texto seleccionado; pone el formato de WhatsApp (`lib/whatsapp/format.ts:toggleFormat`, alterna y deja fuera los espacios de los bordes) y agrega Ctrl/⌘+B, I, Shift+X, Shift+M. Va anclada encima del campo (no a la selección: un textarea no da su posición sin un clon). El contenedor debe ser `relative`. Solo donde el texto sale por WhatsApp: compositor de chats WhatsApp y cuerpo de plantillas.

### Figuras para personas y bots (blobatar, 2026-11-01)

`EntityAvatar` acepta `figure` (y `seed`, por defecto `name`): en vez de iniciales dibuja una figura determinista de [blobatar](https://github.com/Alain00/blobatar) (MIT, sin dependencias). Regla: **personas y bots llevan figura; las cosas llevan iniciales.**
- Contactos: `ChannelAvatar` siempre la usa, sembrada con el nombre visible (un visitante "Visitante web · XXXX" tiene su propia cara).
- Usuarios: menú de perfil (`user-dropdown.tsx`), `/configuracion`, `/usuarios` (también invitaciones, por correo) y el asignado en la tarjeta del pipeline, sembrados con el **id** del usuario para no cambiar de cara al renombrarse.
- Bots IA: sembrados con el id del bot.
- Cuentas, plantillas, campañas, secuencias, automatizaciones y Meta Ads siguen con iniciales: ahí el nombre es lo que se busca con la vista (el riel de cuentas sobre todo).
- Versión **fija** (`"blobatar": "2.7.0"`, sin `^`): la librería solo garantiza las mismas caras dentro de una versión mayor, y una actualización cambiaría el avatar de cada contacto. Subirla es una decisión explícita.
- Sin fondo propio (`background: false`): va sobre el recuadro con el hue de la cuenta (`hueClassFor`), así se conserva la señal de cuenta y funciona en ambos temas. Sus colores son de su propia paleta, la misma excepción que los logos de canal.
- Se pinta como `<img>` con data URI (el SVG sale solo de un hash; no contiene el nombre ni se inserta markup) y se cachea por semilla. Funciona en Server Components (panel) sin desajuste de hidratación.
