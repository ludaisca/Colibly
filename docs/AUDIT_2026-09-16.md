## 1. Dependencias y plataforma

### C1 🔴 Paquetes con vulnerabilidades críticas
`npm audit --omit=dev`: **10 vulnerabilidades (4 críticas, 4 altas, 2 moderadas)**.

- **`next` 16.2.7** — entre otros: *Unauthenticated RCE in Image Optimization API when AVIF files are used* (crítica, `<16.3.3`), *Middleware / Proxy bypass in App Router applications using Turbopack* (alta, `<16.2.11`), SSRF en Server Actions/rewrites, DoS. El bypass importa aquí: **`proxy.ts` es la única barrera de rol para las páginas** (`EXECUTIVE_BLOCKED`/`USER_BLOCKED`), y el build de producción usa Turbopack. Las APIs no dependen de `proxy.ts` (excluye `/api`), así que los datos siguen protegidos por los handlers, pero un `ejecutivo` podría renderizar páginas RSC bloqueadas como `/estadisticas`.
- **`next-auth` 5.0.0-beta.31** (vía `@auth/core`) — *Configuration errors can cause existence-based auth checks to fail open* (crítica) y *Email normalizer validates the address before Unicode normalization* (crítica).
- **`@auth/prisma-adapter`** — dependencia directa **sin ningún import** (el proyecto usa JWT sin adapter), arrastra `@auth/core` vulnerable.
- Transitivas: `postcss`, `sharp` (libvips), `brace-expansion`, `nanoid`, `qs`.

**Recomendación:** `next@16.3.5` (no es mayor), `next-auth@5.0.0-beta.32` (beta actual), eliminar `@auth/prisma-adapter`, y volver a correr `npm audit` + build de producción. Es el cambio de mayor impacto por menor esfuerzo de todo el documento.

### B10 🟢 Dependencias sin uso
`@auth/prisma-adapter`, `@hapi/boom` (resto de Baileys) y `@dnd-kit/sortable` no se importan en ningún archivo. Eliminarlas.

## 2. Autenticación y roles

### A2 🟠 Email con mayúsculas bloquea el login — ✅ verificado
- `lib/auth.ts:25` normaliza a minúsculas al iniciar sesión, pero **ninguna de las 3 vías de alta normaliza**: `app/api/auth/register/route.ts:29`, `app/api/onboarding/route.ts:33`, `app/api/usuarios/route.ts:127`.
- Reproducción: registro con `QA.Mayus@SundayCRM.test` → 201; login con **exactamente el mismo texto** → sesión `null`. La DB guarda `QA.Mayus@SundayCRM.test` y el `findUnique` busca `qa.mayus@sundaycrm.test`.
- Efecto colateral: `Luis@x.com` y `luis@x.com` pueden coexistir como usuarios distintos.
- **Recomendación:** `.transform((e) => e.toLowerCase().trim())` en los 3 schemas zod + script único que normalice los emails existentes (revisando colisiones antes).

### M1 🟡 El rol vive 30 días en el JWT y no hay forma de revocar acceso
- `lib/auth.ts:45-58`: `role` se copia al token al iniciar sesión y nunca se relee de la DB. Degradar a un admin o cambiar de rol a un usuario no tiene efecto hasta que expire la sesión (30 días por defecto).
- `app/api/usuarios/route.ts` solo tiene `GET/PATCH/POST`: **no existe desactivar ni eliminar usuario**, ni reset de contraseña por admin. Un ejecutivo que deja la empresa conserva acceso completo.
- **Recomendación:** campo `User.disabledAt` + `tokenVersion`; en el callback `jwt` releer `role/disabledAt/tokenVersion` cada N minutos (o en cada request si el costo es aceptable) e invalidar si cambió.

### M2 🟡 Registro público abierto por defecto
- `prisma/schema.prisma:47` → `allowRegistration Boolean @default(true)`. Tras el onboarding, cualquier persona en internet puede crear una cuenta `user` en producción (con acceso a Panel, Chats, Cuentas, Plantillas, Campañas y a crear sus propias cuentas/bots).
- **Recomendación:** default `false`, o apagarlo automáticamente al completar `/api/onboarding`. Crítico antes de vender el producto.

### A4 🟠 El rol `ejecutivo` salta sus restricciones llamando a la API
`proxy.ts` excluye `/api`, así que la restricción de rol debe repetirse en cada handler (patrón documentado "hide nav → block route → 403 API"). No se repite en:
- `app/api/whatsapp/campaigns/route.ts:7` (crear) y `app/api/whatsapp/campaigns/[id]/send/route.ts:8` (**enviar campaña masiva** sobre una cuenta compartida).
- `app/api/whatsapp/templates/create/route.ts` (crear plantillas en Meta).
- `app/api/whatsapp/sequences/route.ts` y `[id]` (crear automatizaciones que mandan mensajes).
- `app/api/whatsapp/accounts/route.ts:10` (crear números de WhatsApp) — inconsistente con `app/api/telegram/accounts/route.ts:14`, que sí bloquea `ejecutivo`.
- `app/api/whatsapp/lead-scorers/**`: el rol `user` no ve el CRUD en la UI pero la API lo permite.

**Recomendación:** helper `requireRole(session, [...])` en `lib/` y aplicarlo a todas las rutas cuyo equivalente de página esté en `EXECUTIVE_BLOCKED`/`USER_BLOCKED`.

### B1 🟢 "Primer usuario = admin" no es atómico
`app/api/auth/register/route.ts:58` y `app/api/onboarding/route.ts`: `count()` + `create()` dentro de `$transaction` con aislamiento READ COMMITTED no bloquea — dos registros simultáneos en una DB vacía pueden crear dos admins (AGENTS.md afirma lo contrario). Improbable en la práctica. Fix: `isolationLevel: Serializable` o un advisory lock.

## 3. Multi-tenant y autorización por cuenta

### A3 🟠 Etiquetas globales entre todos los clientes
- `prisma/schema.prisma:1033-1035`: `Tag` no tiene `userId`/cuenta y `name` es `@unique`. `GET /api/whatsapp/tags` (`app/api/whatsapp/tags/route.ts:13`) devuelve **todas** las etiquetas del sistema a cualquier usuario autenticado.
- `campaign-worker.ts` crea etiquetas `Campaña: <nombre>` → **los nombres de campañas de un cliente son visibles para todos los demás**.
- Colisión: si un cliente crea "VIP", ningún otro puede crear "VIP" (409), y ambos terminan compartiendo el mismo `tagId`.
- Mitigado (no cruza envíos): secuencias y reglas de enrutamiento por etiqueta filtran por la cuenta del contacto.
- **Recomendación:** scoping de `Tag` por cuenta (`waAccountId`/`channelAccountId`, igual que `CannedResponse`) con `@@unique([scope, name])` y migración de datos. **Bloqueante para el modelo de producto de pago** (ver `docs/PLAN_ROADMAP.md`).

### M11 🟡 Compartir cuentas de canal está a medio implementar
- Existe `ChannelAccountShare` y `getUserChannelAccountIds()`, pero **ninguna ruta crea un share** (`grep channelAccountShare.create` → vacío).
- El scoping es inconsistente: secuencias, campos personalizados, respuestas rápidas y calificadores honran shares; el inbox (`lib/channel-chats.ts:29`), la media (`lib/channel-media.ts:48`), el envío (`chats/[chatId]/send/route.ts:140,225,278`) y los contactos (`contacts/[id]/*`) filtran solo por dueño.
- Consecuencia práctica hoy: **Telegram/Messenger/Instagram/Web solo los puede atender el dueño de la cuenta** — ni `user` ni `ejecutivo` pueden trabajar esos chats. AGENTS.md documenta lo contrario.
- **Recomendación:** decidir si se completa (API + UI de compartir + unificar scoping con `getUserChannelAccountIds()`) o se documenta como limitación.

### B3 🟢 `localMediaPath` se acepta tal cual del cliente
`app/api/whatsapp/chats/[chatId]/send/route.ts:167,327` leen el archivo indicado por el body. `resolveAbsolutePath()` impide salir de `MEDIA_ROOT` (probado por lectura), pero no impide apuntar a la carpeta de **otra cuenta** si se conoce el UUID. Validar que empiece con `${accountId}/`.

### B4 🟢 Media servida inline sin sandbox
Las rutas de media sirven `image/*` inline desde el origen de la app. Un `image/svg+xml` abierto directamente ejecutaría scripts (la CSP permite `'unsafe-inline'`). El vector hoy es estrecho (requiere usuario interno + que el proveedor acepte el SVG), pero conviene forzar `attachment` para SVG o añadir `Content-Security-Policy: sandbox` a esas respuestas.

## 4. Webhooks y endpoints públicos

### A1 🟠 WhatsApp sin App Secret = cero mensajes entrantes — ✅ verificado
- `lib/meta/webhook-signature.ts:37`: sin secreto la validación devuelve `false`; `app/api/whatsapp/webhook/route.ts:474` hace `continue`. Se descartan mensajes **y** estados (entregado/leído/fallido de campañas), respondiendo `200 {"success":true}` — no hay log ni aviso.
- Pero el form lo marca opcional (`app/(dashboard)/whatsapp/cuentas/_form.tsx:213` "App Secret (opcional)"), la API lo acepta vacío y AGENTS.md dice que la validación "se omite" sin secreto.
- Reproducción: cuenta con `phoneNumberId` y sin `appSecret` → POST de un mensaje de texto al webhook → HTTP 200, `wa_messages=0`, `wa_chats=0`.
- No es regresión: el código siempre se comportó así.
- **Decisión requerida** (AGENTS.md pide consultarla): (a) hacer el App Secret obligatorio en form/API + banner en cuentas existentes sin él — **recomendado**, es lo seguro; o (b) implementar el "skip" documentado.

### M3 🟡 Chat web: identidad elegida por el visitante y costo de IA abusable
- `app/api/webchat/[accountId]/session/route.ts:52`: el servidor firma un token para **cualquier `visitorId` que mande el cliente**. El chequeo de `Origin` solo frena a navegadores; con `curl` se falsifica. Quien obtenga el `visitorId` de otra persona (dispositivo compartido, XSS en el sitio del cliente) puede **leer su conversación** (incluidas respuestas del agente con datos personales) y escribir como ella.
- El `visitorId` del widget se genera con `Math.random()`, no con una fuente criptográfica.
- Abuso de costo: rotando `visitorId` desde una IP → 30 sesiones/min × 20 mensajes/min cada una ≈ 600 mensajes/min, y cada uno dispara el bot de IA si la cuenta tiene uno. El tope de presupuesto mensual lo frena, pero apagando también a los bots legítimos.
- El token viaja en query string en el polling (`?token=`) → queda en logs de acceso.
- **Recomendación:** que el servidor genere el `visitorId` (aleatorio criptográfico) y lo devuelva junto al token; límite por IP también en envío; límite diario de conversaciones nuevas por cuenta; token en header.

### M5 🟡 Los comentarios de la propia Página entran como si fueran de un lead
`app/api/meta/webhook/messaging/route.ts:193` no descarta `value.from.id === entry.id` (la Página). Cuando la Página o un community manager responde un comentario desde Facebook, se crea un `Contact`/`Conversation` con la Página como cliente. Añadir ese filtro.

### M7 🟡 Webhooks que responden 200 ante cualquier error pierden mensajes
- Telegram (`app/api/telegram/webhook/[accountId]/route.ts:166`) y Messenger/Instagram (`app/api/meta/webhook/messaging/route.ts:213-218`) devuelven 200 también cuando falla la DB o Redis → el proveedor no reintenta → **el mensaje se pierde para siempre**. El comentario justifica esto para errores de parseo, pero aplica a todo.
- **Recomendación:** 200 solo para payloads inválidos; 5xx para errores transitorios (el dedup por `externalMessageId` ya hace seguros los reintentos).

### M8 🟡 Rate limit del webhook de WhatsApp demasiado bajo para campañas
`app/api/whatsapp/webhook/route.ts:399`: 300 req/min **por IP**, compartido por todas las cuentas. Una campaña de 1,000 destinatarios genera ~3,000 callbacks de estado (sent/delivered/read) desde pocas IPs de Meta → 429 → Meta reintenta con backoff → métricas y estados atrasados varios minutos, y peor con varios clientes a la vez. Subir el límite o eliminarlo (la firma HMAC ya autentica).

### B2 🟢 Comparación de firma no constante
`lib/meta/webhook-signature.ts` usa `expected === received`. Usar `timingSafeEqual` (como ya hace `lib/webchat/session-token.ts`).

## 5. Ingesta de mensajes y bots de IA

### A5 🟠 Los bots no conviven bien con humanos ni entre sí
1. **Sin "human takeover"**: `lib/whatsapp/ingest-message.ts:194` y `lib/telegram/ingest-message.ts:192` encolan al bot en **cada** mensaje entrante, aunque el chat esté asignado o un agente acabe de responder. Bot y agente se pisan en la misma conversación.
2. **Varios bots activos en la misma cuenta responden todos**: ninguna ruta de creación/activación impide más de un bot activo por cuenta; cada uno encola su job → N respuestas por mensaje.
3. **Reintento = respuesta duplicada**: en `lib/workers/bot-worker.ts:301` se envía el mensaje y *después* se escriben `WAMessage`, uso, cita, etc. Si cualquiera de esos pasos lanza, BullMQ reintenta (3 intentos) → nueva llamada de IA (costo) y **nuevo envío al cliente**.
4. **Ráfagas**: `bot-messages` tiene concurrencia 3 sin agrupar por chat — un lead que manda "hola" + "quiero info" seguido recibe dos respuestas independientes, cada una sin el contexto de la otra.
- **Recomendación:** (1) pausar el bot si `assignedToId` o si hubo un OUTBOUND humano (`senderId != null`) en los últimos X minutos, con toggle por cuenta; (2) restringir a un bot activo por cuenta; (3) marcar el mensaje como enviado antes de pasos secundarios o usar `jobId` idempotente; (4) debounce por chat (`jobId: chatId` + `delay` de unos segundos).

### M4 🟡 Los chats resueltos no se reabren cuando el cliente vuelve a escribir
`lib/whatsapp/ingest-message.ts:107-125` y `lib/telegram/ingest-message.ts:104-124` actualizan `lastMessage`/`unreadCount` pero no `status`. Un chat `RESOLVED` con mensajes nuevos queda fuera de la calificación programada y de la recuperación de leads (ambas filtran `OPEN`/`PENDING`), y sus métricas de resolución quedan desactualizadas. Reabrir a `OPEN` (y limpiar `resolvedAt`) en el `update`.

### B6 🟢 Respuesta vacía tras quitar el bloque de cita
Si el modelo responde solo con el bloque ` ```appointment `, `parseAppointmentMarker()` deja `cleanText = ""` y `bot-worker` intenta enviar un texto vacío → error de Meta → 3 reintentos con costo de IA → bot en `ERROR`. Usar un texto de confirmación por defecto cuando `cleanText` quede vacío.

### B5 🟢 Endpoints de IA sin rate limit
`chats/[chatId]/suggest-reply` y `chats/[chatId]/score` no tienen `rateLimit()` (solo el tope de presupuesto mensual). `bots/[id]/test` no registra uso, así que las pruebas no cuentan para el presupuesto.

## 6. Workers y colas

### A7 🟠 Secuencias: reintentos infinitos e inscripciones que nunca terminan
- `lib/sequences.ts:237-243`: si el envío lanza (token inválido, número bloqueado, error de Telegram), solo se registra en log; `nextRunAt` queda vencido → **se reintenta cada 5 minutos para siempre**, sin contador ni backoff.
- `lib/sequences.ts:228-230`: `findMany` con `take: 200` **sin `orderBy`** → con 200 inscripciones que fallan permanentemente, las sanas nunca se procesan (inanición).
- `lib/sequences.ts:157-165`: un paso de WhatsApp fuera de la ventana de 24h se reprograma +60 min indefinidamente. Con `exitOnReply` activo (default), si el lead no responde **nunca** vuelve a abrirse la ventana → la inscripción queda `ACTIVE` para siempre y cualquier paso con `delayMinutes` > 24h es imposible de entregar.
- **Recomendación:** contador de intentos + estado `FAILED` tras N; `orderBy: { nextRunAt: "asc" }`; expirar la inscripción (`EXPIRED`) cuando la ventana no puede reabrirse, y advertir en el form que en WhatsApp los retrasos > 24h requieren plantilla.

### M6 🟡 El `timeout` de las colas no existe y las llamadas HTTP no tienen timeout
- `lib/queue.ts:12,20`: `timeout: 60_000` / `90_000` **no es una opción de BullMQ 5.79** (se eliminó) → no hace nada, aunque AGENTS.md documenta timeouts por cola.
- `lib/`: 27 `await fetch(...)` y **ninguno** con `AbortSignal`. Una llamada colgada a Meta/Telegram/Google retiene el job hasta el timeout de undici (~5 min); el SDK de OpenAI espera hasta 10 min × 2 reintentos.
- Las colas con concurrencia 1 (`campaign-send`, ticks de recuperación, calificación, secuencias, recordatorios) se bloquean completas mientras tanto.
- **Recomendación:** `AbortSignal.timeout(15_000)` en `lib/whatsapp.ts`, `lib/telegram.ts`, `lib/meta-messaging.ts`, `lib/meta/*`; `timeout` explícito en los clientes de IA; quitar la opción muerta y corregir AGENTS.md.

### M9 🟡 Campañas
- `lib/workers/index.ts:53`: el envío completo de la campaña y el tick de campañas programadas comparten una cola con concurrencia 1 → **una campaña grande retrasa todas las campañas programadas** (y cualquier otra campaña) hasta que termina.
- `lib/workers/campaign-worker.ts:210`: si Meta aceptó el envío pero falla un paso posterior (upsert de contacto/chat/etiqueta), el `catch` sobrescribe el destinatario a `FAILED` — el cliente **sí recibió** el mensaje, pero las métricas lo cuentan como fallido y el webhook ya no lo corrige (no avanza desde `FAILED`).
- **Recomendación:** separar la cola del tick; separar el `try` del envío del `try` de la contabilidad CRM.

### M10 🟡 Recuperación de leads
- `app/api/configuracion/ia/route.ts:99-104`: horas sin tope superior y sin validación zod (un valor no numérico produce `NaN` → 500). Con ≥ 24 h, en WhatsApp **nunca se envía nada**: `sendRecoveryMessage` lanza por la ventana de 24h y solo queda un error en log cada 15 min por chat.
- `lib/workers/lead-recovery-worker.ts:49-65`: los candidatos son los 200 chats más recientes por `lastMessageAt`. En cuentas con más de 200 chats activos, los silencios más antiguos —justo los que hay que recuperar— nunca entran al pool.
- **Recomendación:** validar `1 ≤ horas < 24` para cuentas de WhatsApp (o avisar en la UI); filtrar el pool en SQL por `lastMessageAt < now - firstMessageHours`.

### M12 🟡 La media de Telegram/Messenger/Instagram nunca se purga
`lib/workers/media-cleanup-worker.ts:15` solo recorre `WAMessage`. Los archivos de `ChannelMessage` se acumulan sin límite en el volumen `media_data`.

## 7. Frontend (inbox)

### A6 🟠 El inbox no se actualiza y puede mostrar mensajes del chat equivocado
- **Lista de chats estática** — `app/components/whatsapp/chat-workspace.tsx:410-448`: el único polling es el de *mensajes del chat abierto*; la lista solo se refresca cuando ese chat recibe algo. Sin chat seleccionado, o mirando un chat inactivo, **las conversaciones nuevas de otros leads no aparecen** hasta recargar.
- **Condición de carrera al cambiar de chat** — `chat-workspace.tsx:347-366` (carga inicial) y `:411-445` (polling) no cancelan ni descartan respuestas de un chat anterior (sin `AbortController` ni bandera `ignore`). Si la respuesta del chat A llega después de abrir B, `setMessages` **reemplaza los mensajes de B por los de A** (carga inicial) o **los anexa** (polling). El agente vería la conversación de A bajo el encabezado de B y respondería a B.
- **Recomendación:** poll de la lista (p. ej. cada 10–15 s, o solo "hay nuevos" con `updatedSince`); `AbortController` en ambos efectos + comparar `selectedChatId` antes de `setMessages`.

### B9 🟢 Polling con la pestaña oculta
Ningún polling (`chat-workspace` 5 s, campaña 2 s, campana de notificaciones 25 s) se pausa con `document.hidden`. Con varios agentes y pestañas abiertas multiplica la carga sin beneficio.

## 8. Infraestructura y operación

### C2 🔴 `db push --accept-data-loss` en cada deploy de producción
- `scripts/startup.sh:19`. Sin `prisma/migrations/`, cada arranque sincroniza el schema **aceptando pérdida de datos**. Un renombre de campo en `schema.prisma` (que Prisma interpreta como *drop + add*), un modelo borrado por error o un merge equivocado **eliminan columnas/tablas con datos reales sin preguntar** al redeployar en Coolify.
- **Recomendación:** adoptar `prisma migrate` (baseline con `migrate diff` desde la DB de producción, `migrate deploy` en `startup.sh`), respaldo automático de Postgres antes de cada deploy, y quitar el flag. Prioritario antes de tener clientes pagando.

### B7 🟢 Healthcheck superficial
`app/api/health/route.ts` responde `ok` sin tocar Postgres ni Redis → el contenedor queda `healthy` con la base caída. Añadir `SELECT 1` + `PING` con timeout corto.

### B8 🟢 Mensajes de error internos en respuestas 500
La mayoría de rutas devuelve `error.message` crudo (errores de Prisma incluidos, con nombres de tablas/campos). Loggear el detalle y devolver un mensaje genérico.

### B11 🟢 `PATCH /api/configuracion/ia` sin schema zod
Valida a mano con `Math.round`/`Math.max`; tipos incorrectos producen `NaN` y 500. Alinear con el resto de rutas (`lib/validations.ts`).

## Falsos positivos descartados (no volver a investigar)

- **Reglas de enrutamiento** (`accounts/[id]/routing-rules`): no filtran por `getUserAccountIds()` a propósito — son solo del dueño, con `userId` en el `where`. Correcto.

## Propuestas de librerías para UI y animación

**Contexto del proyecto que condiciona la elección:**
- Ya usa **`motion` 12.42** (`motion/react` en `chat-thread-panel.tsx`), keyframes CSS propios en `app/globals.css` (`fade-in-up`, `scale-in`, `slide-*`, `pulse-live`…) y un sistema de toasts propio (`app/components/ui/toast.tsx`, `useToast()` usado en **41 archivos**).
- Sistema de diseño por tokens semánticos (`--accent` teal, `--success`, etc.) — cualquier librería con estilos propios debe poder mapearse a esos tokens.
- CSP actual (`next.config.ts`) permite scripts empaquetados y estilos inline: ninguna de las propuestas requiere CDN ni cambios de CSP.
- Next 16 App Router: todo lo animado va en componentes `"use client"`.

### 1. Sileo — toasts con morphing SVG y física de resortes ✅ recomendada (con adaptador)
- **Qué es:** componente de toasts para React ("gooey SVG morphing, spring physics"). `sileo@0.1.5`, MIT, repo `hiaaryan/sileo` (~1.7k estrellas).
- **Por qué encaja:**
  - **Su única dependencia es `motion ^12.34`**, que el proyecto ya tiene → peso adicional mínimo.
  - API completa: `sileo.success/error/warning/info/action/promise/dismiss/clear`, título + descripción, botón de acción, íconos, duración, 6 posiciones, `theme="light|dark|system"`.
  - Estilos por **variables CSS** (`--sileo-state-success`, `--sileo-state-error`, `--sileo-tone`, `--sileo-btn-bg`…) → se mapean a los tokens de la app.
  - Accesibilidad incluida: `aria-live="polite"` y respeta `prefers-reduced-motion` (verificado en el paquete publicado).
- **Dónde aporta valor real:**
  - `sileo.promise()` para operaciones largas: enviar campaña, sincronizar plantillas, subir conocimiento al RAG, "Sugerir respuesta con IA" (loading → éxito/error en el mismo toast).
  - `sileo.action()` para deshacer: eliminar etiqueta, cancelar cita, mover lead en el pipeline.
  - Notificaciones entrantes (`CHAT_MESSAGE`, `APPOINTMENT_REMINDER`) como toast con botón "Abrir chat", además de la campana.
- **Riesgos:** versión 0.x con un solo mantenedor y sin releases desde feb-2026; estética "opinionated" que hay que validar contra el diseño "fresco y cercano"; si en el futuro se sube `motion` a 13, Sileo traería su propia copia de motion 12.
- **Integración propuesta (bajo riesgo):** no tocar los 41 consumidores. Reimplementar `useToast()` en `app/components/ui/toast.tsx` sobre `sileo` (misma firma `success(msg)`), montar `<Toaster theme=…>` en `app/providers.tsx`, importar `sileo/styles.css` y mapear las `--sileo-state-*` a `--success/--danger/--warning/--info` en `globals.css`. Exponer `toast.promise`/`toast.action` como extensiones nuevas. Si Sileo se abandona, el cambio se revierte en un solo archivo.
- **Alternativa conservadora:** `sonner@2.0.8` (MIT, soporte explícito de React 19, muy adoptada) con el mismo patrón de adaptador — menos espectacular visualmente, mucho más madura.

### 2. Anime.js — motor de animación general ⚠️ recomendada solo para el sitio de marketing
- **Qué es:** `animejs@4.5.0`, MIT, módulos ES con tree-shaking (~24.5 KB total; timers, animaciones, timelines, `stagger`, Scroll Observer, Draggable, utilidades SVG de morph/dibujo de líneas/motion path, Scope API para media queries). Mantenimiento activo (release ago-2026).
- **Dentro de la app (CRM): no recomendada.** Se solapa casi por completo con `motion`, que ya está instalado y es idiomático en React (`AnimatePresence`, layout animations, `useReducedMotion`). Tener dos motores duplica peso, patrones y conocimiento necesario para mantener. Anime.js manipula el DOM de forma imperativa; en React exige `createScope` + limpieza en `useEffect` en cada componente.
- **Donde sí brilla:** el pendiente del roadmap **"Sitio web de marketing/ventas"** (`docs/PLAN_ROADMAP.md`):
  - Hero con texto por letras/palabras en `stagger`.
  - Dibujo de líneas SVG que ilustre el flujo "anuncio → WhatsApp → bot → lead calificado → venta".
  - Animaciones sincronizadas al scroll (Scroll Observer) para la sección de funcionalidades.
  - Contadores animados en la sección de pricing y métricas.
  Si ese sitio vive en un repo aparte (decisión pendiente), no hay conflicto con `motion`.
- **Uso puntual aceptable en la app:** ilustraciones SVG "dibujadas" en estados vacíos u onboarding, encapsuladas en un solo componente cliente.

### Reglas para cualquier integración
1. Mantener **una sola librería por responsabilidad**: `motion` para animación en React, Sileo **o** Sonner para toasts. No sumar Anime.js dentro de la app.
2. Respetar `prefers-reduced-motion` (Sileo y `motion` lo hacen; en animaciones propias usar `useReducedMotion()`).
3. Encapsular detrás de los primitivos existentes (`useToast`, `KpiStrip`, `EntityList`) para no esparcir imports de terceros por las páginas.
4. Tokens semánticos únicamente — nada de colores literales en la configuración de las librerías.
5. Verificar con build de producción: lo animado debe quedar en componentes `"use client"`.
